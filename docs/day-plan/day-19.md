# Day 19 — Multi-Agent Architecture

## Objective

Day 18 handed the curriculum a loaded question: the natural next consumer of a store that "knows who wrote every fact and how old every lesson is" is another agent — but the curriculum is explicit about the trap, and its one-line objective is a commandment, not a feature request: **"Determine whether multiple agents are actually useful. Do not assume they are."** Its comparison is **single agent vs specialized agents** (Knowledge / Data / Engineering), its deliverable is *either* a **justified single-agent architecture** *or* a **justified multi-agent architecture**, and the closing clause is the day's whole discipline: **"the justification matters more than the number of agents."** Day 19 does not build a multi-agent system. Day 19 builds the **comparison that decides whether one is called for** — and the default is already standing. Rule 6 of the apprenticeship is *no premature complexity*, and its first three examples are *Kubernetes, microservices, multi-agent systems*; §9 admonishes that multi-agent hype is to be used *only if it solves an actual problem*. The day's burden of proof runs from the curriculum's own text: the number of agents is a **decision to be measured**, and the series already gave the day everything a measurement needs — Day 11's tool groups (docs / code / SQL / git), Day 15's privilege boundaries (roles, not agents), Day 16's planner, Day 17's store, and Day 18's memory that makes "sharing" cheap enough to genuinely *wonder* whether splitting pays. The deliverable is a **verdict with the table that forces it**: either the single loop wins on the measured axes and the justified architecture is *one agent with role-context routing and the Day 15 policy already in place* — or a scoped subset of the curriculum's three-agent split wins, and the justified architecture is *that subset*, built and no larger.

The day's architectural truth, stated up front and never dropped: **an "agent" is a loop** (Day 12) **with tools** (Day 11), **a plan** (Day 16), **a policy** (Day 15), **and memory** (Days 17–18). The single agent this series built is *already* the curriculum's three specialists fused into one loop — its knowledge tools (search docs, search code), its data tools (SQL), and its engineering tools (git, run) all hang off one transcript, one budget, one planner. So the honest phrasing of Day 19 is not "should we add agents" but "**should we *duplicate the loop* per role?**" A second agent is not *one more tool group* — it is a **second loop**: a new context window, a new budget ledger, a new failure surface, a new termination problem, and a *new seam between loops* (a handoff) that the single loop does not have at all. The series' own reflexes mark the moment: Day 13 proved the loop needs guards *inside*; Day 19 must decide whether putting guards *between* loops buys anything. And Day 15 already drew the line the naive argument crosses: **specialization is done by role and privilege, not by loop count** — a data *role* with a read-only SQL policy was the Day 14/15 guarantee, and it was delivered on *one* loop. Day 19's question is whether the loop itself must be split for the roles to be real; the day's honest hypothesis, seeded by Day 18's own "Tomorrow," is that **a single agent with Day 18's memory and Day 15's roles out-competes three agents with no memory** — and the day's discipline is to *let the fixture table say it* rather than to assert it.

## Duties Outline

### 1. Learn: The Loaded Question — "Multiple Agents" vs "More Code" (45 min)

- [ ] Parse the curriculum's objective as the discipline it is: **"Determine whether multiple agents are actually useful"** and **"do not assume they are"** are one sentence, and the day's first learn item is that the *null hypothesis is the single agent*. Not the naive null, the *cheapest* null: the single loop Days 12–18 already runs, already carries the three tool groups, already carries the roles, and already remembers. Multi-agent carries the **burden of proof** (Rule 6's *no premature complexity*, asserted on multi-agent by name), and the day's job is to hand it a court, not to sentence it.
- [ ] Learn the loaded word: **"useful"** is Rule 4's word. It is not "clever" or "clean" or "architecture-shaped." Useful means: on the measured axes — task success, evidence grounding, cost, latency, failure containment — the split **beats the single agent it replaces, on tasks that actually occur**, and the improvement is real enough to pay for what splitting costs. The curriculum's deliverable clause is the check: *justification matters more than the number of agents* — so a multi-agent system that cannot justify each loop over its monolith on the table is not a "justified multi-agent architecture," it is a violation of Rule 6 wearing a diagram.
- [ ] Name the three candidate "agents" the curriculum proposes and what they *already are* in this series: **Knowledge** (Days 6–10: doc retrieval, code retrieval, reranked evidence), **Data** (Days 14–15: schema-grounded read-only SQL), **Engineering** (Day 11's git/run tools, Day 10's code questions). Each is a **tool group and a privilege set on one loop** — which is precisely the "specialization" the series already did *without* duplicating the loop. Day 19 must therefore take the curriculum's diagram seriously as a *claim*, not receive it as a blueprint: the diagram's `Orchestrator → {Knowledge, Data, Engineering}` is a hypothesis that loop-duplication earns its cost; the day runs it against the null.
- [ ] Pre-commit the day's ruling vocabulary, so no argument can blur it: **role** = a tool set + a policy (Day 11 + Day 15 — exists today on one loop); **agent** = a role + its own loop (Day 12) + its own budget + its own memory + its own termination (Day 19's candidate duplication); **orchestrator** = a loop whose *tools are other loops* — a delegation surface that can fail and must be audited like any tool (Day 11's schema as interface, now with the interface being another agent's exit).
- [ ] Pre-commit the failure-shape grammar the day will reuse: **over-orchestration** (a delegation decision that adds cost and risk to a task the single loop already answers — the day's cardinal sin, Day 16's `over-planned?` counterweight, promoted to the architecture level) and **the handoff leak** (a specialist's finding mis-stated when it crosses the boundary — the day's "Chinese whispers," a Day 13 fabrication mode on the delegation seam).

### 2. Learn: Rule 6 and the Burden of Proof — Single Is the Default (45 min)

- [ ] Learn the three costs of a second loop that the naive "add an agent" pitch omits, because each becomes a measured column later: **(a) context duplication** — the orchestrator's context does not shrink when it delegates; it *grows* by the receipt it must hold to ground its answer, and the specialist's context is separate, so the same facts are billed twice; **(b) a new failure surface** — a handoff can fail like a tool call can fail (Day 13), but with *three* new failure shapes of its own: routing to the wrong specialist, a specialist that returns ungrounded evidence, and an orchestrator that fabricates a delegation it never made; **(c) shared-state coordination** — two loops touching Day 17/18's store (or two stores, or one closing the other's file) is a concurrency problem the single loop never had, and Day 17 explicitly deferred multi-process synchronization as *named, not built*.
- [ ] Learn the only two honest reasons specialization might *still* pay, and hold one standard for them: **(1) context isolation** — a task mixing data-heavy and knowledge-heavy work crowds a single context until the reranker's evidence is squeezed out (Day 9's budget floor, applied to the whole loop); a specialist keeps each surface clean, but the *measurable* claim is *total tokens for equal grounding*, not "looks cleaner"; **(2) independent concurrency** — two specialists investigating in parallel genuinely cut wall-clock latency *if* their work is independent, and *only if* the orchestrator's aggregation does not serialize it back (Day 16's DAG is the honest test: parallelizable branches of the plan, measured end-to-end). Everything else — "one agent per concern," "separation of duties," "scalability" — was already delivered by role-policies and tool groups at zero loop-cost.
- [ ] Learn the counterweight Rule 6 imposes and the series has been honoring since Day 16 (P9), Day 17 (S9), and Day 18 (M8): **the control.** Whatever Day 19 concludes, a topology change that changes a memory-free, delegation-free answer is a bug. The justified architecture, single or multi, must run Days 12–18's fixture set *exactly as green* when the new machinery is off — over-orchestration is measured the same way over-memory was measured: as a no-change row.
- [ ] Pre-commit the ordering: **measure before building the topology.** The comparison harness (a single fixture router that can present any task to either topology) is the day's *first* build — not the orchestrator, not the specialists. You cannot measure what you have not been able to present identically to both sides; the harness is the experiment, the agents are treatments.
- [ ] Pre-commit the exit criterion, in the curriculum's own words: the deliverable is *justified*, and the first page of the deliverable is a **verdict line** — `justified architecture = single` or `justified architecture = multi (scoped to: …)` — with the fixture table beneath it. A day that ends without the verdict line failed; a day that ends with a verdict the table cannot support failed worse.

### 3. Design: The Comparison — Two Topologies, Same Fixtures, One Judge (30 min)

- [ ] Design the day as an **A/B with one fixture router**, so the only variable is topology:
  ```text
                         the day's question set (Q-families + orchestration fixtures)
                                              │
                          ┌───────────────────┴────────────────────┐
                          ▼                                        ▼
              Topology A — the single loop            Topology B — orchestrator + specialists
   (Days 12–18 as-built, + role-context routing)     (Knowledge / Data / Engineering loops
   one context · one budget · one planner ·             under an orchestrator; role-scoped tools,
   Day 15 policy by tool group · Day 18 memory)        per-loop budgets, shared Day 18 store)
                          │                                        │
                          └───────────────────┬────────────────────┘
                                              ▼
                       the judge: identical exit checks
           (expected evidence ⊆ retrieved · cited ⊆ retrieved · conclusion ⊆ evidence
            · delegated ⊆ returned · cost · latency · steps · failures)
                           →  the verdict row, per fixture
   ```
- [ ] Design decision #1 — **the single loop is Topology A, not "no architecture."** It is the curriculum's allowed deliverable *and* the null hypothesis at once: Days 12–18 plus the one upgrade Day 19 may genuinely owe it, **role-context routing** — a deterministic layer (Day 8's rule machinery, reused) that picks the *entry surface* (knowledge / data / engineering) for a question before the loop starts, so the loop's first context is the right tool group's. That is the honest half of specialization: route the *context*, keep the *loop*. It is `MECH` (a rule-table decision, no chat), and it is the single-agent answer's whole claim to "specialist-grade context."
- [ ] Design decision #2 — **Topology B is the curriculum's diagram, built as honestly as the comparison demands**: an orchestrator whose tools are three specialist loops, each with exactly Topology A's tool group and policy (Knowledge = doc/code retrieval + rerank; Data = schema-grounded read-only SQL; Engineering = git/run/test). Each specialist is a full Day 12 loop with its own budget, its own termination, and — the day's first real joint — **Day 18's store, shared** (the curriculum's candidate split is precisely "agents sharing the memory Day 18 made worth sharing"; the alternative, N private stores, is G6's comparison row, not a default).
- [ ] Design decision #3 — **the delegation contract is a receipt, not prose** (the day's headline, `delegated ⊆ returned`): the only thing that may cross the orchestrator↔specialist boundary is a **receipt** — a result carrying the specialist's `task_id` (Day 12), its evidence, its conclusion, and its provenance (Day 17), the exact episodic record Day 18 already defines. The orchestrator *cites the receipt*; it never paraphrases it. A paraphrase is the day's cardinal leak, and it is rejected by construction — the same way Day 18 refused to let a receipt read as a lesson. The receipt makes `delegated ⊆ returned` checkable in code: every fact the orchestrator's answer asserts that it attributes to a specialist must be present in that specialist's returned evidence.
- [ ] Design decision #4 — **failure is a return value of the delegation, and only the delegation**: when a specialist refuses, times out, or crashes (Day 13's shapes, now at loop granularity), the orchestrator receives a **failed-delegation receipt** — it can retry (bounded, Day 13's ladder), route around (delegate to another role, if Day 16's plan allows), or answer with the failure named. It **cannot** fabricate a specialist run it never received (G8). This is Day 11's refusal-as-a-return-value, promoted to the agent seam, and the trace must show a delegation `attempted → returned | failed(reason)`, never a hole.
- [ ] Pre-commit the day's invariants: **(a)** `delegated ⊆ returned` — an orchestrator's answer cites only receipted evidence from its specialists (the day's headline, a fourth translation of `cited ⊆ retrieved` across the loop boundary); **(b)** ballots, then verdicts — every fixture is measured on **both** topologies before any conclusion, and a fixture that only one topology can run is a routing bug, not a win; **(c)** the control — machinery off ≡ Days 12–18, with memory *and* orchestration both switchable, both measured (G9); **(d)** no loop without a ledger — every agent, real or candidate, books its chats and tokens to the per-fixture row, because the whole question is *cost for equal grounding*, and cost is the day's first fact.

### 4. Build: The Baseline — Topology A, Single Loop with Role-Context Routing (1 hour)

- [ ] Treat Days 12–18 as the baseline's *implementation done*, and add only the one seam the comparison needs: **the role-context router** — a deterministic rule layer (Day 8's `rule_section` machinery, re-pointed at tool groups) that classifies a question into `knowledge | data | engineering` and seeds the loop's first context (and, optionally, its tool list) accordingly. It is `MECH`, costs 0 chats, and it is the honest claim behind "specialized context without specialized agents."
- [ ] Prove the baseline is the *same* machine: with routing off (or routing neutral), Topology A is byte-for-byte Days 12–18 — same answers, same fixtures, same ledger. The role-context router must be **transparent** (a `routed_to` field in the trace, a `MECH` rule-table decision) and **overridable** (question explicitly names a surface → that surface wins), exactly as Day 8's section filter was debuggable. Days 12–18's no-regression set is the baseline's unit test, and it must pass *before* Day 19 builds a single line of Topology B.
- [ ] Baseline the cost truth-teller: a per-fixture row for Topology A (success, steps, chats, tokens, latency, `cited ⊆ retrieved`, `conclusion ⊆ evidence`) — the *a priori* expectation recorded now, before Topology B exists, so the comparison cannot be rigged by measuring B first. Rule 4's discipline, Day 7's "expected before any run," at the architecture level.
- [ ] Keep the honest seam: if Day 19's table ends with **single**, Topology A *is* the deliverable (the justified single-agent architecture), and the day's only new artifact is the role-context router plus the verdict document — a small day by design, and a *correct* one (Day 16's "over-planned?" reflex at the architecture level: the smallest justified change wins).
- [ ] Do not pre-build B's inside-out guesses: the specialists' internals are *already built* (they are Day 12's loop with narrower tool sets); B's only genuinely new code is the **orchestration seam** (a loop whose tools return receipts) and the **sharing policy** (§7). Build order: harness → A → B-seam → measure → verdict.

### 5. Build: Topology B — the Orchestrator and the Specialists (1 hour)

- [ ] Build the three specialists as **parameterized single loops, not new agents by hand**: `make_agent(role)` = a Day 12 loop bound to `role`'s tool group (Knowledge: doc/code retrieval; Data: schema + read-only SQL, Day 14/15's policy embedded; Engineering: git/run/test) with its own budget, termination, and Day 15 policy — the same factory a single agent already *is*, narrowed by one argument. This is the architectural honesty that keeps B cheap: **a specialist is the existing loop with a tool-list slice**, so B is not "three new systems," it is one seam (orchestration) over the existing one.
- [ ] Build the **orchestrator as a loop whose tool list is `[delegate(role, question)]`**, reusing every guard the series already proved: the orchestrator plans first (Day 16 — the delegation DAG *is* a plan), routes each plan node to a role by the rule-table sketch of §4, receives **receipts**, and aggregates them into the answer by citation. The orchestrator's own loop must respect Day 12's transcript-state rule, Day 13's guards (bounded delegations, timeouts, retry ladder with one rung — *reroute*, Day 16's replan at the delegation level), and Day 6's citation contract applied to receipts.
- [ ] Wire **bounded delegation**: `MAX_DELEGATIONS` per question (Day 12's `max_steps` at the orchestration level), a per-delegation `HANDOFF_TIMEOUT` (Day 13's timeout, between loops), and a `DELEGATION_RETRY` of exactly 1 (Day 4's gateway retry discipline for a manual seam: one retry, then a named failure). A delegation chain that exceeds `MAX_DELEGATIONS` terminates with a **named failing receipt**, not an infinite handoff ping-pong — Day 13's non-termination fixture, reproduced between loops.
- [ ] Preserve **per-specialist grounding end-to-end** (G7): each specialist answers only from *its own* retrieval (`cited ⊆ retrieved` inside its loop), and the receipt it returns is its Day 18-style episodic record — evidence, conclusion, provenance — *not* a summary sentence. The orchestrator's answer cites the receipts; the day's trace carries both the specialist's internal `cited ⊆ retrieved` rows and the orchestrator's `delegated ⊆ returned` row, so a leak is locatable to the exact hop (the Chinese-whispers fixture, G3).
- [ ] Keep the honest ledger: the cost of a delegation is measured as the **union of both contexts** (`orchestrator_context + specialist_context`, minus overlap), because delegation does not *replace* context it *duplicates* it — G5's column, and the number that most often kills B's excuse.

### 6. Build: The Delegation Contract — Receipts Across the Boundary (45 min)

- [ ] Encode the contract Day 19 owns, the day's headline made mechanical: a **receipt** is a struct with `task_id`, `principal`, `role`, `question_asked`, `evidence[]` (the specialist's grounded citations, each `cited ⊆ retrieved` inside its loop), `conclusion`, `provenance {run_id, step, source: "specialist:{role}"}`, and a `rejected`/`refused`/`failed`/`returned` status — the exact `kind=episodic` record of Day 17, now the *unit of delegation*. Nothing else crosses the boundary; a specialist's "finding" that is not a receipt is not a finding.
- [ ] Build **`delegated ⊆ returned` as a code check**, the day's fourth honesty invariant, symmetric with Days 6/14/16/17/18: after the orchestrator answers, every fact it attributes to a specialist (the trace's `attributed_to: {role, task_id}` fields) is checked against that specialist's receipt evidence — a fact attributed but not in the receipt is a **handoff fabrication**, flagged in red, the Chinese whisper caught like a fabricated citation was caught (Day 13's `fabricated? = no`, across the seam).
- [ ] Aggregate by **citation, not by absorption** (Day 6's rule, at the loop seam): the orchestrator merges receipts into the answer context as *blocks to cite*, exactly as Day 18's recall served episodes as episodes — it may combine two specialists' evidence to support one conclusion, but it never re-voices a specialist's finding as its own un-cited prose. M7's rule ("a receipt is never a lesson") is inherited across the boundary.
- [ ] Make the **orchestrator's refusal honest**: a question that routes to no role (or to a role with nothing covering it) is refused like Day 7 refused — the orchestrator cannot soften a gap by adding hops (G8). "I decomposed, delegated, and nothing returned evidence" is a *valid terminated answer*; "I commissioned a specialist who must have found something" is the cardinal lie.
- [ ] Record the seam's honest limit, Day 18's way: **the orchestrator cannot see inside a specialist's loop.** It holds the receipt, not the transcript. For a contested conclusion the orchestrator has exactly Day 18's re-distillation move — delegate *again* with a pointed question — or it surfaces the disagreement. A delegation receipt is Day 17's closed store, not an open window; "you cannot see inside" is the day's honest note beside "you cannot un-distill."

### 7. Build: Shared Memory and Policy Across Roles (45 min)

- [ ] Wire **Day 18's store as the sharing substrate, not a second system**: specialists read `.recall(question, principal)` against the shared store (each principal-bounded, Day 18's keying untouched), and the distiller (Day 18) may run over a specialist's finished task records exactly as it ran over the single loop's — the receipt a specialist returns *is* the episodic record the store already holds. The curriculum's split (agents sharing memory) thus costs **zero new memory machinery**: Day 19 reuses §5's make_agent + Day 18's store, and the only genuinely new policy is *who may write*.
- [ ] Decide the **write policy as the day's one real security decision** (Day 15's "privileges beat parsers," applied to authorship): Default — every specialist writes episodic records **only under its own `principal` + `role` provenance**, exactly as the single loop did; the orchestrator may read all its specialists' records (it is the coordinator) but may it write? The day's rule: **the orchestrator writes only orchestration records (routing, delegations, verdicts), never specialist-episodes** — the orchestrator is a router, and a router that authors investigations claims evidence it never personally grounded (M7's boundary, reproduced).
- [ ] Compare the sharing regimes as **measured rows, not prose** (G6): Topology B with a **shared** store vs B with **private per-role stores** vs A with Day 18 memory — three columns answering Day 18's own question ("is a single agent with real memory strictly cheaper than N agents with N private stores?"), scored by success, grounding, and tokens. The day *expects* shared > private (a private store is N copies of the distiller and N shelf-sized recall pools), but the expectation is a hypothesis until the row is filled.
- [ ] Apply Day 17/18's retention invariants unchanged across roles: receipts expire and delete like any episodic record; `forget` re-grounds every concept that cites a deleted receipt (Day 18's M5) even when the *concept* lives on the shared shelf and the *receipt* was authored by one specialist; cross-principal reads stay empty (M6); and the M8 control (memory off ≡ days-without) is re-run through Topology B's loops, because a shared store must not change a memory-free specialist's answer either.
- [ ] Record the day's honest `PENDING` same as every day since Day 14: the *routing* (role-context table, delegation plan) and the *contract* (`delegated ⊆ returned`, cost ledger, failure containment) are `MECH` — deterministic functions of topologies, receipts, and roles, offline and free. Whether a **real model's orchestrator actually delegates better than the single loop answers** on real Saleor questions is the real-gateway question → **Day 21/22's benchmarks** on Day 19's harness (the same days that own Day 18's distiller and Day 16's planner); Day 19 ships the court and the verdict line, and the real-verdict column stays `PENDING` exactly where the series has always parked the semantic truth.

### 8. Test: The Architecture Set (G1…G9) (1 hour)

- [ ] Pre-register the architecture fixtures (**G1…G9** — *group* fixtures: the properties of the split-vs-monolith decision, two of them hostile, plus a control) with expectations written **before** either topology runs:
  - **G1** the specialist wins: a two-surface task that genuinely benefits from context isolation (a data-heavy question that also needs a doc concept — e.g. "which products generated the most revenue, and does Saleor's docs say revenue reports use `total_net`?" — where crowding one context squeezes one surface's evidence) → Topology B beats Topology A on the measured row (total tokens for equal grounding, or latency when truly parallel), and the win is **scoped**: exactly the split that won, no more.
  - **G2** the monolith holds: a single-surface task (the Days 12–18 fixture families unchanged) → Topology B does **not** beat Topology A on success, and its cost row shows the duplication; a multi row that merely ties is **recorded as a loss** (tie = the single agent was cheaper); over-orchestration on a one-step question is the fixture's failure shape (Day 16's `over-planned?`, architecture-scale).
  - **G3** no handoff without a receipt (`delegated ⊆ returned`): the orchestrator's answer cites only receipted specialist evidence (pass), and the **Chinese-whispers injection** — a receipt that is paraphrased into the answer with a fact the specialist never returned → the handoff-fabrication check fires; an orchestrator that attributes a specialist result it never received → rejected.
  - **G4** privilege containment: a specialist exposes only its role's tool group (data cannot call git, engineering cannot run SQL, knowledge cannot write); a delegation that tries an out-of-role tool is **refused at the specialist's policy gate** (Day 15's X-set, re-run through both topologies); no escalation via a crafted delegation question.
  - **G5** the cost ledger is the judge: per-fixture tokens/latency for **both** topologies, with B's row billed as *union of both contexts* per delegation; a fixture B "wins" only when its total row beats A's total row on the stated axis — never on "cleaner architecture."
  - **G6** the memory reducer: single agent with Day 18 memory vs B-shared vs B-private stores vs B-with-no-memory — four columns, one question set; Day 18's suspicion ("one agent with memory beats N agents without") measured, not asserted.
  - **G7** per-hop grounding: each specialist's answer is `cited ⊆ retrieved` inside its loop, and the receipts carry that evidence verbatim into the orchestrator's context; total leaked hops (evidence claimed at a hop its bearer never returned) **== 0**.
  - **G8** failure containment: a specialist refuses / times out / crashes (Day 13's shapes at loop granularity) → the orchestrator returns a **failed-delegation receipt** or a named fallback; it never fabricates a specialist run; a crashed specialist does not take down the conversation's other delegations.
  - **G9** **control**: all machinery **off** (orchestration off, routing neutral, shared store empty) → Days 12–18 fixture set runs *unchanged and exactly as green* (A1…A8, F1…F9, Q1…Q8, T1…T7, X1…X11, P1…P9, S1…S9, M1…M9) — over-orchestration, a topology that changes a memory-free, delegation-free answer, is a bug (Rule 6 measured the M8/S9/P9 way).
- [ ] Split the day honestly, Day 7's way: **G1, G2, G3's check, G4, G5, G6's routing+ledger, G7, G8, G9 are `MECH`** — deterministic functions of the harness, the router, the delegation contract, the shared-store keying, and stored payloads: offline, free, reproducible, and the *whole* day's deliberative payload. **The real verdicts are `PENDING`**: whether a *real* model's orchestrator delegates better than the single loop on real Saleor questions, whether real recall beats fresh-investigation *through* a specialist's split context, and whether B's cost row stays below A's at real token prices — all → **Day 21/22's benchmarks on Day 19's harness**. The stub proves the **court**; a real key proves the **verdict**.
- [ ] Re-run Days 7–18's fixtures as the no-regression gate through **both** topologies: Days 12–18 through A (the first build's unit test) and — the day's real question — the same set through B, where the expectation is that B must **at least tie** every fixture A answers, and any fixture B fails that A answers is a **topology failure to fix, not a fixture to weaken** (the routing/context bug owns it).
- [ ] Apply Day 7's isolation, one owner per symptom: a **handoff that leaks evidence** → the receipt contract (`delegated ⊆ returned`) owns it; **a specialist that answers ungrounded** → that specialist's own `cited ⊆ retrieved` owner (Day 6/7); **over-orchestration** → the router (it delegated when the rule-table said single-path) owns it; **a cross-role privilege escape** → the specialist's policy gate (Day 15) owns it; **a shared-store cross-principal read** → Day 18's keying owns it; **a topology that changed a memory-free answer** → the G9 control owns it. One owner per symptom, in the trace.

### 9. Measure + Documentation (45 min + 20 min)

- [ ] Rule-4 as an architecture table, one row per fixture, both topologies, every cell a real run's: `fixture | topology A | topology B | winner | steps | handoffs | tokens (A total / B union) | latency | failure? | routed_to | cited ⊆ retrieved | conclusion ⊆ evidence | delegated ⊆ returned | cost | verdict` — the day's three carried columns: **`delegated ⊆ returned = ok` on every B row** (the headline), **B ≥ A on every G2-family row or the row is a recorded A-win** (the cost truth), and **G9's row** (machinery off ≡ Days 12–18) as the counterweight — over-orchestration is measured exactly the way over-memory was.
- [ ] Record the cost shape honestly — **the whole day runs on the harness, not on billing**: Topology A adds **0 chats** past Days 12–18 (the role-context router is a rule-table); Topology B's *mechanics* are also **0 chats** (routing, receipts, ledger, containment are deterministic), but B's *operation* bills what delegation genuinely bills — the specialist's own loop chats **plus the duplicated orchestrator context**, and G5's rows put that number next to A's, because the question is *cost for equal grounding*, not "a clean diagram."
