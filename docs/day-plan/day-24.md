# Day 24 — Distributed AI Observability

## Objective

Twenty-three days built a machine that reads (Days 6–10), acts (11–12), survives failure (13), computes (14–15), plans (16), remembers (17–18), decides its own architecture (19), learns how it will be judged (20–22), and can explain one request from the inside (23). Day 23 gave a single in-process request one identity, one span tree, one monotonic clock, one prompt vocabulary, and one ledger-reconciled bill. The curriculum now turns the camera outward: **"Understand cross-component execution,"** with a required chain that leaves the process entirely — **User → AI API → Agent → RAG → Vector DB → Saleor API → PostgreSQL → Response** — four things to learn (**correlation IDs, distributed traces, structured logging, metrics**), and the deliverable **end-to-end request trace.** The repo is honest about where each hop lives today: `ai_os/server.py` is a real FastAPI boundary that accepts `/chat`, `/rag`, `/chat/stream`; `ModelGateway` makes real outbound HTTPS calls to OpenAI/Anthropic/Cloudflare; `RagStore` is currently a **local JSON file**, not a network service; `ai_os/data.py` reaches Postgres through `psycopg` on a read-only DSN with a server-side `statement_timeout`; and the Saleor API is reachable as GraphQL through the same process. So "distributed" is not yet a claim about five microservices. It is a claim about **five boundaries**: one inbound HTTP edge, three outbound client edges (provider, Saleor GraphQL, Postgres), one component boundary where work genuinely leaves this process, and one response edge. What Day 23 could not do is cross any of them: a span tree is only as wide as the process that built it, `trace_id` is a Python value that dies at the socket, and the provider's own work, Saleor's resolver time, and Postgres's plan are all invisible because **we do not own them.** The genuine build is therefore propagation and honest incompleteness: a wire format both ends agree on, a continuation rule instead of a new root, client-side spans for calls we initiate, an explicit "I did not instrument that" marker for hops we cannot see, an assembly step that tolerates out-of-order, duplicated, and lost span reports, and two derived views — structured logs and metrics — that share the identity without pretending to be the trace.

Day 24's first principle is **identity must survive the wire, and it must continue rather than restart.** When a request arrives with a `traceparent`, the server is not a new root; it is a remote child of a span that lives somewhere else, and the correct act is to adopt the incoming `trace_id` while minting a fresh `span_id` whose parent is the caller's span. Every outbound call must then carry that context onward. The second principle is **the topology you do not own is still part of the topology.** A provider call, a Saleor resolver, and a Postgres query all have real time and real failure modes that no amount of client instrumentation can see. The honest record says so: a `client` span owns *our* wait time, carries the status and error we received, and names the remote system — and the gap between "we sent it" and "the database planned it" is labeled, not rounded away. The third principle is **a missing span is data.** Telemetry fails: a worker dies before reporting, a hop is not instrumented, a report arrives ten minutes late. A trace that silently omits those spans is lying by omission, so Day 24 makes completeness explicit — expected-but-absent spans are recorded as gaps, late reports are recorded as late, duplicates are idempotent, and a trace reports `complete: false` with the missing component named. **Never invent a zero-duration success.**

The day's fourth principle is that **logs and metrics are not the trace.** Structured logging is the durable, greppable, per-event view that shares `trace_id`/`span_id` and carries the same redaction rules; metrics are the aggregated view (counts, latency distributions, tokens, cost, error rates by bounded label) that answers *how many* and *how slow* without preserving instances. Neither can answer *which request*, and metrics labels must never carry `trace_id`, user identity, or question text — that is how one request becomes a billion time series. And the control returns: **D9.** Propagation, logging, and metrics must be **fail-open** — if the collector is down, the request still succeeds with the same answer, the same SQL, the same tool results, the same attempts, and the same ledger cost. Telemetry that can fail the request is not observability; it is a dependency with no user. Headers added, bodies unchanged. Day 23 earned "traceable"; Day 24 earns **"end-to-end"** — and it will earn it honestly, with a visible list of what is still outside the trace.

## Duties Outline

### 1. Learn: The Loaded Objective — "Understand Cross-Component Execution" (45 min)

- [ ] Parse **"cross-component execution"** as a claim about **boundaries, not boxes**: a component boundary is any place where work leaves this process's control — an inbound HTTP request, an outbound provider call, a database session, a queue, a second service. The question at each boundary is always the same three: *did context cross? what did the far side cost us? what did we never get to see?*
- [ ] Map the curriculum chain onto the repository as it actually is, without inflating it: **User** (outside) → **AI API** (`server.py`, real FastAPI edge) → **Agent** (`agent.py`, in-process) → **RAG** (`rag.py`/`retrieval.py`, in-process) → **Vector DB** (`RagStore`, **a local JSON file today** — a `client` hop the day names but does not yet have) → **Saleor API** (GraphQL, outbound client) → **PostgreSQL** (`data.py` + `psycopg`, read-only DSN, server-side timeout) → **Response** (stream or JSON body, plus headers).
- [ ] Inventory what Day 23 already gives Day 24 and what it structurally cannot: trace/span/event, monotonic timing, status and error taxonomy, prompt refs, ledger-linked cost totals, bounded local store, `GET /traces/{trace_id}` — all **process-local**. Missing: a wire format, a continuation rule, span kinds, a remote flag, a report/assembly path, gap representation, structured logs, and metrics. Day 24 extends the grammar; it does not replace it.
- [ ] Pre-commit the day's split, inherited from Day 7 and unchanged by Day 23: **propagation, assembly, reconciliation, and metric arithmetic are `MECH`** — parse/format determinism, parent linking, idempotent merge, gap detection, count/latency/cost arithmetic, log-line validity. **Meaning is not silently promoted**: knowing a Postgres span took 412 ms does not tell you whether the plan was good, and knowing a trace is complete does not tell you the answer was correct. Quality verdicts stay Days 20–22.
- [ ] Pre-commit six invariants before any build: **(a) continue, don't restart** — an inbound correlation id is adopted, not replaced; **(b) every outbound call carries context**; **(c) gaps are visible** — an expected-but-absent span is a recorded gap, never an implied success; **(d) fail-open** — telemetry failure never changes the answer, the SQL, the retry, or the cost; **(e) metadata-safe continues** — cross-process does not relax redaction, and untrusted inbound headers are validated, never obeyed; **(f) D9** — tracing on/off is behaviorally and financially identical except for added fields and headers.
- [ ] Name the negatives with owners: **a production collector, backend, or vendor APM** is deployment work, not today; **real sampling/retention policy** stays a named boundary; **instrumenting Postgres, Saleor's internals, or the provider from the inside** is impossible for us and stays a labeled gap; **client-side spans in the user's browser** are `PENDING` until a client is instrumented; **authentication and authorization for an ingest endpoint** belong to Day 26; **prompt-injection and tool-permission threats** are Days 25–26. Day 24 builds propagation and honest assembly, not an observability vendor.

### 2. Learn: Correlation IDs and Context Propagation — The Wire Format (45 min)

- [ ] Learn the difference between a **correlation id** and a **trace id**, and why the industry conflated them: a correlation id is any id that stitches records together (a request id, a job id); a trace id names one distributed trace and must be globally unique, fixed-size, and never reused. One request has one trace id; many log lines, spans, and metrics windows may reference it.
- [ ] Learn the W3C Trace Context shape and why the format is a contract rather than a convenience: `version-trace_id(32 hex)-parent_id(16 hex)-trace-flags`, e.g. `00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`. `trace_id` = 16 bytes, `parent_id` = 8 bytes, flags carry the sampled bit. All-zero ids are invalid; uppercase hex is illegal; a future version must be parsed leniently and preserved, not rejected.
- [ ] Learn **sampling as a propagated decision, not a local one.** The sampled flag travels with the context so downstream components do not each roll their own dice; a component that receives an unsampled context does not emit sampled spans. Day 24 keeps the bit honest and the policy trivial (everything sampled locally, one explicit knob), because a real head sampler needs a cost model Day 24 does not have.
- [ ] Learn **baggage as a bounded, untrusted, non-secret channel.** Day 24 allows a tiny allow-listed set of non-sensitive keys (e.g. `tenant`, `surface`, `request_kind`) with a hard size cap, propagated onward. It must never carry API keys, user PII, SQL text, prompts, or unbounded values; it must never be used to select a store, tenant, index, or permission — a forged inbound header is data to validate, not authority to obey.
- [ ] Learn the two directions precisely: **extract** on inbound (parse and validate the incoming header, decide continuation vs fresh root, record why) and **inject** on outbound (write the current context into the request headers of the provider call, the Saleor GraphQL call, the Postgres wrapper's client-info, and the worker RPC). Forgetting to inject is the single most common way a distributed trace silently becomes two disconnected local traces.
- [ ] Learn the transports available without new infrastructure: HTTP headers (primary), plus explicit carrier arguments for in-process and CLI paths, and a documented, deliberate "no header possible" case (a third-party SDK that owns its own transport) where the gap is recorded rather than faked.

### 3. Learn: Distributed Traces — Remote Parents, Span Kinds, and the Topology You Do Not Own (45 min)

- [ ] Learn **span kinds** as an honest statement about who did the work: `server` (we handled an inbound request), `client` (we called something else), `producer`/`consumer` (message boundaries), `internal` (local computation, e.g. today's `RagStore` read or reranking). A chain where every span claims `server` is a chain that has not left the building.
- [ ] Learn **remote-ness as data, not as a different schema**: a child created from a remote parent's context keeps its own `span_id`, records `parent_span_id` as the remote span, and marks the edge remote. Remote and local children assemble identically; the flag exists so nobody later claims an external system's internal work was measured locally.
- [ ] Learn **the client/server double-count trap**: for one provider call there are two truthful spans — our `client` span (what we waited) and, if the far side is instrumented, its `server` span (what it did). Both are real; summing them double-counts one interaction. The end-to-end number is the **critical path**, never the sum of all hop durations, and any report that adds hops together is wrong.
- [ ] Learn the four states of a span report in a lossy world: **delivered** (normal), **late** (arrived after its parent closed or after assembly), **duplicate** (same `span_id` re-sent), and **missing** (expected, never arrived). Assembly must be idempotent on `span_id`, order-independent, and must represent a missing span as a first-class record naming the component and the reason we expected it.
- [ ] Learn what client-side instrumentation can and cannot see for the three real external hops. **Provider:** we know requested/actual model, attempt, latency, tokens, cost, status, error kind, finish reason — we do not know queue time, internal retries, or safety filtering. **Saleor GraphQL:** we know operation name, latency, status, error class, returned field count — not resolver-level timing or N+1 behavior. **PostgreSQL:** we know the statement hash, allow-list verdict, row count, truncation, `statement_timeout`, and total latency — not the plan, the indexes used, or lock waits. Saying "the DB took 412 ms" when we measured our own socket wait is the exact overclaim to avoid.
- [ ] Learn that **the end-to-end number is bounded by the trace**. Root span duration is server-side. The user's stopwatch additionally contains DNS, TLS, proxy, and queueing before our first byte and after our last — and, for streaming, time-to-first-byte plus the stream itself. Report server-side root duration, first-hop and last-hop spans, TTFT for streams, and name the outside-the-trace remainder explicitly.

### 4. Learn: Structured Logging and Metrics — Three Views, One Identity (45 min)

- [ ] Learn why logs, traces, and metrics are three different questions and must not be collapsed. **Logs** answer "what happened at this instant, in this order, with these fields" and are the right place for rare, high-cardinality, human-read detail. **Traces** answer "what happened to this one request, causally" and are the right place for a single slow/failing case. **Metrics** answer "how many, how slow, how expensive, how often broken" over a window and cannot name an instance. A log line with no `trace_id` is a receipt; a metric labeled with `trace_id` is a cardinality bug.
- [ ] Learn the structured-log contract: one JSON object per line with a fixed spine (`ts`, `level`, `logger`, `component`, `event`, `msg`, `trace_id`, `span_id`, `parent_span_id`, `duration_ms`, `status`, plus safe attributes). No f-string prose that a machine must parse; free-text detail goes in a `msg` field with the structured facts beside it. Bind ids from the same Day-23 context variable that binds spans, so a log line always lands in the tree without a second plumbing mechanism.
- [ ] Learn that **logging is not tracing and must not double-write**. A span records an operation's boundaries; a log line records a discrete fact or a decision. Emitting both for the same fact is acceptable only when they serve different readers, and the rule against redaction relaxation is absolute: no authorization headers, API keys, SQL text, row contents, prompts, document text, or customer records in either view. The existing `gateway.py` logger is the first thing to migrate.
- [ ] Learn the metrics model without a vendor: counters (requests, errors, tokens, cost, tool calls, SQL executions by verdict) and histograms with **fixed, declared buckets** for latency (root, per hop, TTFT), with labels drawn from a small bounded set (component, operation, model, provider, status, error kind, corpus). Metrics must be derivable from spans so trace and metrics cannot disagree about the same window.
- [ ] Learn the cardinality and cost traps by name: never label by `trace_id`, user, session, question text, document id, SQL string, or error message; bounds must be enumerable in the code; a metric registry needs a reset/inspection path for tests; and the honest line is that **metrics cannot answer "which request was slow"** — they can only tell you it was 3% of requests, and then the trace is where you go.
- [ ] Learn the operational shape honestly: `GET /metrics` exposing a snapshot (JSON, with a documented Prometheus-text option) and a bounded local ring for logs/traces is a local development surface, **not** a production metrics stack. Durable log shipping, a real collector, and scrape-based alerting remain deployment concerns.

### 5. Design: The Cross-Component Contract (30 min)

- [ ] Design the wire contract before touching callers:
  ```text
  INBOUND                                    OUTBOUND
  headers ──▶ extract()                       inject(headers) ──▶ provider / Saleor / worker
              │  validate hex, version, zeros      │
              ▼                                     ▼
        adopt trace_id                       child span kind=client, parent=current
        new span_id, parent=remote span          │
        kind=server, remote edge                 │  work happens (possibly unseen)
              ▼                                   ▼
        assemble(tree) ◀── span report ──◀── ingest(span)   [out-of-order | late | duplicate | missing]
              │
              ├── structured log lines (same ids)
              └── metric increments (from spans, bounded labels)
  ```
- [ ] Design decision #1 — **one grammar, two scopes**: Day 24 reuses Day 23's `Trace`/`Span`/event schema and adds only what crossing a boundary requires: `kind`, `remote`, an optional `remote_endpoint`, and gap records. No second trace type, no second store, no schema fork. A `schema_version` bump is expected and honest; a parallel model is not.
- [ ] Design decision #2 — **continuation, with a recorded reason**: inbound context is adopted when valid; when absent, malformed, all-zero, or refused, a fresh root is created and the reason (`no_header`, `malformed`, `all_zero`, `version_unsupported`, `rejected_untrusted`) is recorded on the root. A forged header must never let a caller attach spans to someone else's trace or influence which store/tenant is used.
- [ ] Design decision #3 — **assembly is idempotent, order-free, and loss-aware**: the assembler merges reports by `(trace_id, span_id)`, tolerates a child arriving before its parent, records duplicates as counts rather than double-counting durations, marks late arrivals, and materializes `missing` entries for spans the topology expected. A trace exposes `complete`, `span_count`, `gap_count`, and `components_seen`.
- [ ] Design decision #4 — **the far side we do not own is a labeled gap, not a span we fake**: client spans describe *our* wait, status, and result shape; remote internals are described as unobserved. The one exception is a component we genuinely run (a worker process we deploy ourselves), which is instrumented end to end and marked as such.
- [ ] Design decision #5 — **fail-open telemetry**: report delivery, the ingest endpoint, and metric writes are wrapped so any failure is recorded locally and swallowed. The application's own policy (SQL allow-list, tool rejection, budget) stays fail-closed; observability never becomes a reason to fail a request.
- [ ] Design decision #6 — **local before platform**: the transport is a bounded in-process/hybrid collector (plus a loopback-only HTTP ingest for the real second process in the fixtures), with no broker, no vendor SDK, no OpenTelemetry dependency. The schema and algorithm must survive a later move to a real backend.

### 6. Build: Propagation Core, Span Reporting, and the Assembler (1 hour 5 min)

- [ ] Extend `ai_os/observability.py` with `TraceContext` (parse/format/validate W3C traceparent, trace flags, `new_root`, `child`, `remote_child`), `inject`/`extract` for headers and explicit carriers, span kinds (`server`/`client`/`internal`/`producer`/`consumer`), a `remote` flag, and an endpoint attribute that names a system without leaking credentials or full URLs with secrets.
- [ ] Build `SpanReport` and `TraceAssembler`: merge by `(trace_id, span_id)`, order-independent, idempotent, with `late`, `duplicate`, and `missing` bookkeeping; expose `complete`, `span_count`, `gap_count`, `components_seen`, and a deterministic JSON serialization that `GET /traces/{trace_id}` already knows how to serve.
- [ ] Add a bounded, thread-safe **collector** with an explicit maximum, oldest-first eviction, and a report path that cannot raise into the caller. Provide an in-process submit function plus an optional loopback-only HTTP ingest route that is **off by default**, with unauthenticated ingest named explicitly as a Day-26 boundary.
- [ ] Reuse Day 23's `TraceStore` as the read surface: assembled traces and locally built traces are the same artifact, so an inspector has one lookup, one schema, and one redaction path.
- [ ] Keep the core dependency-free. If propagation is later delegated to a vendor SDK, the schema, the validation rules, and the D-fixtures must remain the contract that adapter has to satisfy.

### 7. Build: Instrument the Edges — Inbound, Provider, Saleor, Postgres, Worker (1 hour 20 min)

- [ ] Instrument the inbound edge in `ai_os/server.py`: extract and validate the header on `/chat`, `/rag`, and `/chat/stream`; continue or mint with a recorded reason; open a `server` root; return `trace_id` in the response **body and a response header**; close the root after the response is produced, with a `response_sent` event and TTFT for streams. Malformed headers get a fresh trace and a 400-free, non-fatal path — a bad header must not fail a legitimate request.
- [ ] Instrument the outbound provider edge in `ai_os/gateway.py`: every attempt span becomes `kind=client`, injects the current context into the provider request, and records `remote_endpoint` as provider host only. If a provider SDK owns its transport and offers no header hook, record the gap explicitly instead of claiming propagation.
- [ ] Instrument the Saleor/Postgres edge in `ai_os/data.py`: `run_saleor_sql` and `describe_saleor_schema` get `client` spans carrying operation name, statement hash, allow-list/policy verdict, row count, truncation flag, `statement_timeout`, and duration — with **no SQL text, no row contents, no connection string**. Postgres client-info carries the correlation id when the driver allows it.
- [ ] Instrument the vector-store edge honestly: today's `RagStore` is a local file, so its read is an `internal` span with store version, k, budget, and candidate counts. Add the seam a real network vector DB will use (a client span with injection) and mark the remote store itself as `PENDING` until one exists — the day's chain names it, the code does not fake it.
- [ ] Build the genuinely-crossing component: a small worker/service process (a second FastAPI app or stdlib HTTP service) that **extracts** the header, continues the trace with a remote parent, does one piece of work (e.g. a tool-shaped or RAG-shaped job), and **reports its span back** through the collector. This is the fixture that makes "distributed" real: two processes, one trace id, one assembled tree.
- [ ] Add the topology declaration: each component registers the span kinds and child names it is expected to produce, so the assembler can name a missing hop instead of merely noticing a short tree. Keep it explicit and small — a hand-written topology per component, not an inferred service map.

### 8. Build: Structured Logging, Metrics, and the Inspection Surface (1 hour)

- [ ] Build `ai_os/structured_logging.py`: a JSON formatter with the fixed spine, a context-binding filter that pulls `trace_id`/`span_id` from the Day-23 context, a redaction filter that drops or masks forbidden keys before serialization, and a bounded in-memory ring with a `GET /logs?trace_id=…` lookup. Migrate the existing `ai_os.gateway` logger to it and show the before/after.
- [ ] Build `ai_os/metrics.py`: counters and fixed-bucket histograms, a registry with a snapshot and a deterministic reset, and increment points derived from **span close events** (so metrics and traces cannot disagree). Labels are drawn from a declared, enumerable allow-list; adding a high-cardinality label is a visible code change, not an accident.
- [ ] Expose `GET /metrics` (JSON snapshot, optional Prometheus text) and extend `GET /traces/{trace_id}` with completeness fields and remote spans. Unknown ids still fail cleanly; a trace assembled only from reports still renders the same schema.
- [ ] Keep every knob in env/config per Day 4: propagation on/off, log level and ring size, metrics enable, ingest route enable and bind address. Off must be genuinely off — no headers added, no counters incremented, no report submitted.

## Deliverable

The **end-to-end request trace** — one assembled, honest record of a request that crossed component boundaries:

```text
   USER ──▶ AI API (server, continues inbound traceparent)
              │
              ├── AGENT (internal steps · client → provider attempts w/ injected traceparent)
              ├── RAG (internal retrieval · vector-store edge: internal today, client when remote)
              ├── SALEOR API (client · operation · status · error class · duration)
              ├── POSTGRESQL (client · statement hash · policy verdict · rows · timeout · duration)
              └── RESPONSE (server close · ttft · trace_id in body + header)

   ASSEMBLY:  idempotent · order-free · late/duplicate counted · missing = explicit gap
   COMPLETE:  complete / gap_count / components_seen  (never silently short)
   VIEWS:     GET /traces/{trace_id} · GET /logs?trace_id=… · GET /metrics
   MONEY:     tokens/cost == exact linked ledger delta, across every component
   HYGIENE:   metadata-safe everywhere · no secrets, SQL text, rows, prompts, or docs
   CONTROL:   D9 — telemetry on/off is behaviorally and financially identical
```

Day 23 made one in-process request explainable; Day 4 made every provider attempt costed; Days 20–22 made quality measurable. Day 24 makes the explanation survive the wire. It does not install a collector, sample intelligently, authenticate its ingest endpoint, or claim to see inside Postgres, Saleor, or a provider — it labels those edges honestly and keeps the identity, the clock, and the bill consistent across every hop. Days 25–29 can then attack the system, constrain its tools, put a human in the loop, harden it, and deploy it. **The black box has a tree, a clock, and a bill; today the tree learns to cross doors — and to admit where it went dark.**
