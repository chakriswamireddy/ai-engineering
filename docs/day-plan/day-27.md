# Day 27 — Human-in-the-Loop

## Objective

Introduce controlled autonomy.

Twenty-six days built a machine that reads (Days 6–10), acts (11–12), fails honestly (13), computes (14–15), plans (16), remembers (17–18), splits into specialists (19), learns how it will be judged (20–22), explains one request from the inside (23) and across its boundaries (24), learned to be attacked (25), and yesterday learned who is allowed to open a door (26). Every one of those days added **authority**, and yesterday's finding was that authority held by a component which reads untrusted text is a *confused deputy's* authority — so the boundary was moved somewhere the model cannot edit, into a grant file, into a deny-by-default choke point in the registry, and into an append-only hash-chained audit of every decision. The curriculum now supplies the permission model's first real client: `Agent wants to refund customer → Policy check → Approval required → Human approves → Tool executes → Audit event`, with the learn list **approval workflows, reversible vs irreversible actions, confidence, authorization**, and the deliverable **human approval mechanism.** The repo's inventory for this day is the most consequential finding in the series so far, and it is not about the human at all: **there is no write path.** Not "no writes today" — no write path *at all*. `SqliteDataStore` (`data.py:463`) and `PostgresDataStore` (`data.py:557`) both expose exactly one query method and nothing else; `PostgresDataStore.__init__` runs `SET default_transaction_read_only = on` (`data.py:533`) and every path out of it is a `self._conn.rollback()` (`549`, `566`, `576`); the `saleor_read_only` role holds no write grant; `policy.yaml` says `statement_allow: [select, with]`; all seven registered tools are reads; and Day 26's grant file, as designed, contains **no `write` effect at all**, because Day 26 discovered that no write-shaped tool has ever been registered. The curriculum's diagram therefore ends at a step this system *cannot perform*, and the day's first job is not to build a refund — it is to decide, in writing, **what "executes" is allowed to mean here**, because a human-in-the-loop design that defers that question ends up with a human approving a message the system writes to a log and calls it a refund.

Day 27's first principle is that **controlled autonomy is a claim about reversibility, not a number.** The vocabulary everyone reaches for is a level — L0 manual, L1 suggested, L2 auto-with-approval, L3 autonomous — and the level is always a single scalar standing in for a set of facts the day actually needs: can this be undone, by whom, within what time, and does anybody find out if it was not. Two actions can sit at the same "level" and belong on opposite sides of a human: a `set_draft_label` on a product is one call and one field, and reversing it is one call; a `refund` is one call and reversing it is a second payment, a second ledger entry, and a customer's bank statement. The honest axis is a **classification of the action**, and the day builds three: **reversible** (another action of this system restores the prior world, bounded and cheap), **compensatable** (the prior world cannot be restored but the harm can be offset — a notification can be recalled, a discounted order can be re-charged), and **irreversible** (nothing the system does afterwards restores it). And the second principle falls straight out of that, and it is a **correction to yesterday's own model**: Day 26 attached `confirm: human` to `effect: write`, because the only write anybody could picture was a refund. That coupling is wrong, and this repository can prove it, because **an export of customer rows is an irreversible effect with `effect: read`.** Disclosure cannot be undone; the rows left the process. So the rule generalizes: **`reversibility: irreversible` requires `confirm: human`, whatever the effect**, and Day 26's write rule survives as the special case. That is the correction, and the day's first real client is therefore *not* a refund — it is a `export_customer_report` grant, which is a read, which means the shipped system's maximum authority is still a read on the Saleor side while its most consequential class of action is already covered.

Third principle, and it is the one that carries Day 25's lesson one layer down: **the approval request is opened by the permission layer, not by the model.** The obvious implementation is to teach the model that it may request approval — add a line to `REASONING_PROMPT`, let it emit an `request_approval` tool call, and let the loop open a record. That is a security regression wearing a workflow's clothes, and Day 25 spent a day refuting exactly this shape: `REASONING_PROMPT` rule 5 already treats a `policy` rejection as a STOP, and the one thing the model must never be able to do is *convert a stop into a request*. So the model's relationship to approval is strictly one-directional: it can **cause** an action, and the layer can **stop** it — and it can never open, request, escalate, forge, argue for, or re-open a request. `REASONING_PROMPT` stays byte-identical for the twenty-seventh time; the gate is a property of the grant, so no prompt text is involved in whether a human is asked.

Fourth principle: **an approval is a decision about a digest, not about a description.** Every human-in-the-loop system has the same time-of-check/time-of-use hole, and it is the most commonly shipped bug in the genre: the approver reads a rendered summary, the executor runs different arguments, and nobody notices because both halves are individually plausible. The fix is structural and cheap — the request carries a canonical, hashed rendering of `(tool, canonical args, effect, data class, reversibility, target ids)`, and **the executor recomputes the digest from the arguments it is about to run and refuses on mismatch** (`approval_digest_mismatch`). And the corollary that decides the whole design: **the approver's summary is not written by the model.** If the request body is a model-generated paragraph explaining what the action does, then the system has handed the model the pen on the one artifact a human is supposed to be reading; a model that wants an approval can write a persuasive one, which is a confused deputy with a keyboard. The approver gets a canonical rendering — tool name, arguments, target, effect, reversibility, the signal set, and nothing the model composed. Fifth principle: **a human is a principal, and `confirm: human` names a role rather than asserting an event.** Yesterday's `confirm: human` is best read as `required_approver_role: human` — the grant says *whose* approval is required, and the store checks that the deciding principal is granted that role, is not the requester, and is not the model's identity. Separation of duties is enforced in the store, not in a prompt: `approval_self_approved` is a `ValueError`, because a system that lets a run approve its own consequential action has not introduced a human at all. Sixth: **silence is never consent.** An approval has a mandatory expiry, an expiry is a *decision with a code* (`approval_expired`), a request that is already decided cannot be decided again (`approval_duplicate`), and a decision with no recorded actor is refused rather than stored — Day 26's residual register said the audit log "records a decision, not a person," and Day 27 makes that a hard refusal instead of a footnote, because a human decision is exactly the artifact where a missing actor is fatal rather than merely inconvenient. Seventh, and the learn item that most needs a position: **confidence is reported as a signal set, never as a score.** Every design in this genre wants a number on the request — `confidence: 0.87` — because a number is what a threshold consumes. But a single number cannot be audited, cannot be traced to a measurement, and hides the fact that the three confidences available in this repository measure completely different things: Day 7's `should_refuse(results, tau)` is a **cosine gate** with `DEFAULT_TAU = 0.55` and it measures similarity to a query, not correctness; Day 21's `cited ⊆ retrieved` is a **grounding** check and measures support, not truth; Day 26's `data: public|internal|pii` is a **declaration** and measures consequence, not likelihood. So the request carries `signals: {…}`, each labelled with what it measures and what it does not, **and there is no aggregate** — because an aggregate is a threshold somebody else wrote, and a red/amber/green chip is the model's opinion wearing a UI. A fourth candidate — the model's own stated confidence — is **not a signal at all**, and the notes must say so out loud: it is a generation artifact, it is trivially steered by the same injection Day 25 was about, and a system that asks a model how sure it is has asked the least reliable component in the pipeline. What replaces it is the check that matters and costs nothing: **the absence of a signal is never a green light** — no citation, no grounding, no gate result, and a target nobody has ever approved before means *more* scrutiny, not less. Eighth: **the human's decision belongs in the same audit chain as the model's request.** Day 26 built the chain and explicitly reserved it for decisions; today the request, the approval, the expiry, the application, and any compensation are all entries in that one chain, in order, hash-chained, so the model's ask and the human's answer end up in one timeline rather than two systems that have to be correlated during an incident.

Ninth, and it is what makes the day *possible* rather than aspirational: **this repository already has a durable, provenance-enforced, expiring, bounded record store, and the approval request is a record in it.** `StateStore` (`state.py:493`) is file-backed, keys every record by `(principal, kind, key)`, refuses a write whose author is not in `AUTHORED_SOURCES` (`state.py:293`, enforced at `545–557` by `_check_provenance`), expires on `ttl`, and has an `enabled=False` off-switch that makes every read return nothing and every write a no-op. Day 19's `orchestrator` is already in `AUTHORED_SOURCES` for exactly the reason that applies here: adding an author admits a writer whose writes are a *different kind*, and the write policy forbids it the shelves it did not ground. So Day 27 adds one string to a frozenset, one kind (`APPROVAL_KIND`), one key helper (`approval_key(request_id)`), and one writer (`write_approval`, mirroring `memory.write_orchestration` at `memory.py:179`) — and inherits durability, TTL, the size cap, the derived index, the compaction pass, and the fail-closed provenance check for free. There is no new database, no new file format, and no new persistence machinery; the day is a *new kind of record in a store that was built to hold records*, which is what twenty-five days of "build before abstracting" buys. Tenth, and the most uncomfortable: **an approval endpoint is the most attractive privilege target in the system, and in this repository it would be a `POST` on a server with no authentication whatsoever.** `server.py` exposes `/health`, `/chat`, `/chat/stream`, `/ledger`, `/rag` and nothing else — no agent route, no session, no `principal` header, no auth. Yesterday's whole layer authorizes a principal that is a caller-supplied string; today the same string can *approve a refund*, and the difference between the two days is the difference between reading a row and changing a business. The day therefore takes the position that the *current* approval surface is deliberately **not** an HTTP endpoint: it is a CLI (`tools/approvals.py`) whose operator is whoever already has the repository, so today's approvals are attributable by accident — a shell history, a git author, a filesystem ACL. The read-only JSON endpoints (`GET /approvals`, `GET /approvals/{id}`) are added because inspection is safe and blocking is not; the *decision* endpoint is deliberately **not** added, and the notes must record that as a design decision with an owner (Day 29) rather than as an oversight, because when Day 29 adds the authenticated surface it will have to re-earn the attribute that the absence of a network route currently provides for free.

Eleventh: **the executor is a different principal from the requester, and the agent may ask but never does.** The curriculum's diagram has one actor doing both; this repository splits it in two on purpose. The agent's `check_call` returns a decision with `code: approval_required`; the run **stops** with a new termination reason `awaiting_approval` and an answer that names the request id and says plainly that nothing was applied; the human decides out of band, hours or seconds later, in a different process; and a *separately granted* `executor` principal applies the staged effect afterwards, with the digest recomputed. The run does **not** block on the human, and the reason is worth a paragraph of its own: `run_agent` is synchronous, bounded by `DEFAULT_TOOL_TIMEOUT_S = 30.0` and `DEFAULT_MAX_STEPS = 6`, and `execute_bounded` (`agent.py:316`) implements its timeout *post hoc* — the call runs to completion and a late result is replaced by a `timeout` observation — so a blocking approval would put a person on the critical path of a process with no cancellation, would make the C9/H9 control ("identical answers, identical tokens, identical cents with the layer on and off") unstateable, and would mean the model holds the thread open while it waits, which converts an out-of-band control into a prompt-adjacent one. Approval is therefore **asynchronous by construction**, the state is durable, and resuming is an explicit, separately-authorized act — which is also the only shape that scales to a queue (Day 28) and an authenticated operator (Day 29) without a redesign. And the run's *last* honest note: **nothing in the shipped grant file changes today's authority.** The system after Day 27 still cannot write to Saleor, still has seven read tools, and still produces answers with zero approvals. What exists is a mechanism with a harness client, a general rule that a future `irreversible` action must pass through it, and a refusal path — the *capability*, not a fact about any running request. The day earns **"interruptible, and answerable to a person"** and must never write the sentence *"requests now require approval,"* which is the same class of overclaim as yesterday's forbidden *"the agent is secure."*

### 2. Learn: Reversible vs Irreversible — and Why `effect` Is the Wrong Axis (45 min)

- [ ] Learn the three classes, and insist on the operational test rather than the label: **reversible** — another action of *this* system restores the prior world, at bounded cost and within a stated window (set a label, then set it back; write an audit record, then append a correcting one); **compensatable** — the prior world cannot be restored but the harm can be offset (send a notification, then send an apology — the message is already in every inbox forever; grant a discount, then charge a surcharge — the customer still saw the discount); **irreversible** — nothing the system does afterwards restores the prior world (a payment is made; a row is disclosed; a customer is told something false). The reason this repo's classes are unusually clean today is that its only write is to its own log, and **appending a correcting record is what append-only means** — so the day's first action is genuinely reversible, and the day can *measure* that rather than assert it.
- [ ] Learn why **`effect` is the wrong axis**, from this repository's own counterexample rather than from a principle: Day 26 declared three effects (`read` / `write` / `none`) and three data classes (`public` / `internal` / `pii`) and attached `confirm: human` to the first of them. But `get_customer` is `effect: read, data: pii` and its result includes `u.email` (`data.py:694–703`) — and a *bulk export* of the same rows is `effect: read, data: pii` and irreversible the moment the rows leave the process. Meanwhile a `write` that only appends to the store's own action log is fully reversible. **So the risk ordering and the effect ordering disagree**, and the day resolves it by generalizing: a grant gains `reversibility: reversible | compensatable | irreversible`, and the load-time rule becomes `reversibility == irreversible ⇒ confirm: human`, whatever the effect. Day 26's `write ⇒ confirm: human` survives verbatim as the case `effect: write, reversibility: irreversible`, and a second clause joins it: `effect: write` **and** `reversibility == reversible` still requires an explicit `confirm: none` acknowledgement in the file, so nobody can downgrade a write to `reversible` by assertion alone without that assertion being visible in the reviewable artifact.
- [ ] Learn what a *reversibility declaration* is and is not, borrowing Day 26's own lesson that "a declaration nobody cross-checks is a comment." The declaration is a fact about *our* code, and it is only worth anything if something asserts it. So the day requires a **declared compensation** for every `reversible` grant: the named tool and arguments that undo it, stored beside the effect, and H2 asserts that a `reversible` action really does leave a system-reachable path back — by *applying the compensation* in the fixture and showing the record returns to its pre-action state. A reversibility field with no declared compensation is a wish, and the fixture that would catch it is cheap, so the day writes it.
- [ ] Learn where reversibility is genuinely *not* knowable in advance, and say so rather than pretending the field is a fact. A `read` is reversible while it stays in the process. It becomes irreversible at the moment the observation enters a **transcript** — because Day 23/24 made the transcript the artifact that reaches a human, and Day 26's rule is that values may not be promoted into the trace; but a refusal to a model is itself an observation, and a large legitimate result is inside the model's context, and **context is not a store you can revoke.** So the day draws an explicit line: an ordinary tool result is reversible in the sense that no *external* effect occurred; an **export** — any tool whose result leaves the process rather than entering a transcript — is `irreversible` by declaration, because disclosure is the point. That is a claim about *this* boundary, it is testable (an export client is harness-only, exactly as Day 26's `create_refund` was), and it is the reason the day's most consequential client is a read.
- [ ] Learn the failure direction, which is the argument that decides the class of bug: with `effect` as the axis, forgetting the `confirm` field on a new read means **no gate and no failure** — the export ships silently. With `reversibility` as the axis and deny-by-default inherited from Day 26, a grant that declares no `reversibility` is not "reversible"; it is **invalid at load time**, which is Day 26's loader rule (`PermissionSet.load` fails closed and names the key) applied to a new field. So forgetting produces a boot error, not a disclosure — the same directional argument as Day 26's allow-list versus deny-list, arriving one field over.

### 3. Learn: Approval Workflows — A State Machine With a Durable Record (45 min)

- [ ] Learn that an approval workflow is **not a UI, a prompt, or a callback — it is a state machine over a durable record**, and that the state machine is the entire deliverable. States, and the only legal edges: `requested → approved | rejected | expired` · `approved → applied | expired` · `applied → compensated` (reversible actions only) · `requested → superseded` (a newer request for the same target). Everything else is a refusal with a code. The invariant that shapes the design: **the request is immutable once submitted.** If the arguments change, that is not an edited request, it is a *new* request, and the old one is `superseded` — because an approval is of an *action*, and an action whose parameters can be edited after a human said yes was never approved.
- [ ] Learn the six properties a naive workflow gets wrong, each of which becomes a fixture: **(1) the request is a record with an id, not a notification** — a human approving at 3 a.m. must be shown exactly what the incident review will show, and a Slack ping is not that; **(2) expiry is mandatory** — an approval that never expires is a standing permission, which is the same object as no permission at all, so `APPROVAL_TTL_S` defaults to 900 seconds on Day 17's own reasoning ("a long TTL is a conscious config, not a default") and an expired request is `expired`, a decision with a code, never `approved`; **(3) one decision per request, and it is final** — a second decision is `approval_duplicate`, and a re-request after a rejection is a new id, so the audit shows both and neither is quietly overwritten; **(4) the executor re-checks** — digest recomputed from the arguments it is about to run, and a mismatch is `approval_digest_mismatch`; **(5) silence is a decision, and it is a *negative* one** — no response before `expires_at` is `expired`, never "assumed"; **(6) the apply is authorized independently of the approve** — an `executor`-granted principal applies, and the agent principal may not, so "who approved" and "who ran it" are two answerable questions.
- [ ] Learn the **digest** as the day's smallest and most load-bearing artifact, and be precise about it, because a digest that is not canonical is a digest that lies: `sha256` over canonical JSON of `{tool, args (keys sorted, no floats, UTF-8), effect, data, reversibility, targets}` — the same canonicalization Day 26 specified for its audit chain (`sort_keys`, fixed separators, no floats) so there is exactly one hashing convention in the repository. The digest is what the approver is shown (`digest: sha256:ab12…`, stable, greppable, reproducible by anyone with a shell), what the approval record stores, and what the executor recomputes. Note the deliberate exclusion: **the digest covers the action, not the model, and not its reasoning** — so a re-run that produces the same action with a different chain of thought is the *same* action, and the approval still applies, which is what an approver means by "yes, do that."
- [ ] Learn the **asynchronous shape** and the specific reasons this repository must use it, rather than choosing it by taste: `run_agent` is synchronous and bounded (`DEFAULT_MAX_STEPS = 6`, `DEFAULT_TOOL_TIMEOUT_S = 30.0`); `execute_bounded` measures elapsed time *after* the call returns and substitutes a `timeout` observation (`agent.py:316–341`), so there is no cancellation and no cooperative yield; `Ledger` has no wall-clock budget beyond `budget_usd`; and the H9 control requires byte-identical token and cost figures with the layer on and off, which a blocking callback inside a tool call makes unstateable because the *waiting* itself is a behaviour difference. Therefore: the run stops at `awaiting_approval` with a durable record, and the apply happens in a **different process, later, under a different principal**. The cost of that choice is real and must be written down — the operator's latency is now unbounded from the request's point of view, and the only mitigation available today is the expiry plus the answer's plain statement of the request id.
- [ ] Learn what a **human is** in this workflow, in the vocabulary the code already has, and the difference matters: Day 19 has `Receipt` with `status` in `{returned, refused, failed}` and an `attributable()` that checks `provenance.source ∈ AUTHORED_RECEIPT_SOURCES`. An approval decision is the same kind of object — a *derived status with honest provenance, never an asserted one* — and `receipt.py`'s own docstring contains the sentence the day needs: "an orchestrator may retry a `failed` (bounded) or route around it; it may **never fabricate a receipt it did not receive**." Today's version: a run may request an approval; it may never author, infer, backdate, or replay one. So `ApprovalDecision.attributable()` mirrors `Receipt.attributable()`, and the day states the limit plainly: `decided_by` is a string a shell user supplied, so this is *record-keeping*, not *forensics*, exactly as Day 26 said of the audit log — and the refusal to store a decision with no actor is where the day upgrades that footnote into a hard failure.

### 4. Learn: Confidence and Authorization — Two Words That Are Not What They Look Like (45 min)

- [ ] Learn what **confidence** actually means in a retrieval-backed agent, by naming the three measurements this repository already makes and refusing to merge them. **Similarity** — Day 7's `should_refuse(results, tau)` over `DEFAULT_TAU = 0.55` (env `TOOL_GATE_TAU`), a cosine gate whose failure mode is *plausible but off-target* text. **Support** — Day 21's `cited ⊆ retrieved` and Day 22's `conclusion ⊆ evidence`, which measure whether the answer is built from what was gathered, and whose failure mode is *gathering the wrong thing correctly*. **Consequence** — Day 26's `data: public|internal|pii`, which measures what the action *does* and is a declaration, not an estimate. These three are not commensurable and no threshold relates them. So the request carries `signals: {…}` and **no aggregate**, and each signal names both what it measures and what it does not — because `risk: 0.87` invites the reader to apply a threshold nobody in the system wrote, and a traffic-light chip is a *model's opinion rendered as a control*.
- [ ] Learn what the fourth candidate is and why it is excluded, because it is the one most designs ship first: **the model's self-reported confidence.** Ask the model "how sure are you" and it produces a fluent number that measures the *distribution of its next token*, not the truth of the world; it is steerable by exactly the indirect injection Day 25 catalogued (a document that says "this is certainly the right order to refund" shifts the number without shifting the facts); and it is a **confused deputy reporting on its own reliability to the person whose signature is being collected.** The day implements all three legitimate signals, prints the model's stated confidence *into the request for the record*, and marks it `not_a_signal: true` — so the exclusion is visible and auditable rather than a design decision buried in a diff. And state the rule that replaces the number: **absence of a signal is never a green light.** No citations, no grounding check, no gate result, a target with no approval history — each of these means *more* scrutiny, and the request says so in words rather than in arithmetic.
- [ ] Learn **authorization** here, in the specific and worse form Day 26 left open, because Day 27 changes the stakes without changing the substrate. Yesterday: the `principal` is a caller-supplied string, so the system is authorization without authentication, and an unauthenticated `principal=admin` is an admin. Today: **the same string can approve an irreversible action**, so an unauthenticated `principal=analyst` could be an approver, and the escalation is one string away from a disclosure. Three consequences, and the day implements all three rather than writing them down: (1) `confirm: human` is read as `required_approver_role` — a *grant*, so "who may approve" is answered by the same file that answers "who may call," and `approval_role_not_permitted` is a refusal with a code; (2) **separation of duties in the store** — `decided_by` must differ from `requested_by` for any non-reversible action, refused as `approval_self_approved` at `decide()` time, because the store is the one component the model cannot edit; (3) the decision surface is **a CLI, not a route** — `server.py` has no auth, no session, and no agent route, so adding `POST /approvals/approve` would place the most valuable single call in the system behind the least protected surface in the system. Read-only `GET` routes are fine (there is nothing to leak in a request: the digest, the tool name, the argument *shape*, the signal set — **not** the argument values, for Day 26's reason), and the day's notes record the decision endpoint as a deliberate absence owned by Day 29.
- [ ] Learn the **confused deputy at the approval desk**, which is the attack this day must be able to name. Day 25's deputy reads untrusted text and acts. Day 27 creates a new instance: the artifact a human reads is a description of a model-chosen action, so a model that wants an approval can try to shape the description. The mitigations are structural and each is a fixture, not a hope: the request body is **canonical and model-authored in zero fields** (tool, args, target, effect, reversibility, signals, digest — every one computed by the layer) · the human's view is byte-stable for a given digest, so two reviewers see the same bytes · the digest is printed *before* any prose, so the prose cannot be the only thing read · and the `proposal` field, if a model-written rationale is shown at all, is confined to a field that is not hashed into the digest and is explicitly labelled untrusted. The honest limit goes in the deliverable: a human is a poor verifier of a canonical rendering, and nothing in this repository measures how well.

### 5. Design: The Request, the Decision, the Executor, and the Audit Line (30 min)

- [ ] Design the record before touching the layer, because the record *is* the workflow:
  ```yaml
  # permissions.yaml — Day 27's addition. `confirm` names a *role*, never an event.
  #   * reversibility, not effect, is the axis: an irreversible READ (an export) is
  #     gated exactly like an irreversible write, because disclosure is the point.
  #   * a `reversible` grant must name the action that undoes it, or `load()` fails.
  #   * no write effect exists in this file. The one gated client is a read, and it
  #     is harness-only (H2) — so the system's maximum authority is still a read.
  tools:
    export_customer_report:            # effect: READ. irreversible: the rows leave.
      effect: read
      data: pii
      reversibility: irreversible
      confirm: human
      approver_role: support_lead       # a grant, not an assertion that a human said yes
      args: {customer_ids: {maxLength: 2048, pattern: "^[A-Za-z0-9_,-]{1,2048}$"}}
      result: {columns: [id, email, orders, currency], max_rows: 500, egress: external}
  ```
  And the refusal Day 26 built in, restated because it is now load-bearing for a different reason: `reversibility: irreversible` **without** `confirm: human` is a `ValueError` naming the tool, and `confirm: human` **without** `approver_role` is a `ValueError` naming the tool, because a gate that does not say *whose* approval is required is a prompt in a config file.
- [ ] Design decision #1 — **the layer opens the request; the model cannot.** `check_call` sees a grant with `confirm: human`, so it returns `Decision(allow=False, code="approval_required", …)` **and** has already written an `APPROVAL_KIND` record with `requested_by` = the calling principal and `digest` = `digest_action(...)`. No tool is called, no model turn is spent, and the model is told only that the call was refused pending approval. Rejected: a `request_approval` tool (the model would learn it could ask, and every refusal would become a request — which converts a stop into a turn); rejected: a `system`-role note in the transcript telling the model to escalate (a steerable instruction, i.e. Day 25's exact refutation); rejected: the loop pausing and polling (blocks on a human, breaks H9, puts a person on a 30-second wall).
- [ ] Design decision #2 — **the request body is canonical, and the digest covers the action and nothing else.** `digest_action(tool, args, grant) = "sha256:" + sha256(canonical_json({tool, args, effect, data, reversibility, targets}))`, with `args` canonicalized exactly as Day 26 canonicalized audit entries (`sort_keys=True`, fixed separators, UTF-8, no floats — one hashing convention in the repository, and a hash anyone with a shell can reproduce). The record carries `digest`, the rendered `subject` (tool, argument *names* and value *shapes*, effect, data, reversibility, targets), the `signals` dict, `ttl_s`, `expires_at`, and `proposal` (an optional model-authored rationale, explicitly *not* hashed and explicitly labelled untrusted). Argument **values** are stored in the record (an approver must see the order ids) and are **not** in the audit entry (Day 26's rule, unchanged).
- [ ] Design decision #3 — **the state machine is the store's, and every illegal edge is a `ValueError` naming the current and requested states.** `submit → requested` · `decide → approved | rejected` (only from `requested`, only once, only with an actor, only by a principal holding `approver_role`, only when `decided_by ≠ requested_by` for a non-reversible action, only while `now < expires_at`) · `apply → applied` (only from `approved`, only by a granted `executor`, only with a fresh digest match) · `compensate → compensated` (only from `applied`, only for a `reversible` action, producing a **new** record with `compensates: <request_id>` and leaving the original untouched — append-only means the correction is an addition, never an edit) · `expire → expired` (only from `requested` or `approved`, and a store pass may do it at any time) · `supersede → superseded`. An attempt to compensate an irreversible action is refused with `approval_reversal_impossible`, and the refusal is loud on purpose: a system that will "undo" an irreversible action will eventually tell a customer their refund was reversed.
- [ ] Design decision #4 — **the loop gains two lines and a termination reason; the prompt gains nothing.** The result is `ToolResult.failure(name, "…pending human approval…", error_kind=ERROR_APPROVAL_REQUIRED, rejection_class=POLICY_CLASS)`. Using `POLICY_CLASS` is deliberate and buys three things for free: Day 12's rule-5 STOP fires (no retry), the sibling substitution is skipped (it is gated on `result.rejection_class != POLICY_CLASS`), and `step_policy` already owns the terminal. Then the *ordering* is the one real change: in the loop, `if result.error_kind == ERROR_APPROVAL_REQUIRED: step_approval = True; step_policy = True`, and the termination check is `if step_approval: … elif step_policy: …` — because a run that stops for approval and a run that stops for a *forbidden* request must not share a terminal, since the first is resolvable and the second is not, and `TERMINATION_NOTE["policy"]` would tell the model the request was refused as a policy violation, which is **false**: nothing was forbidden. New keys: `TERMINATION_NOTE["awaiting_approval"]` and `AGENT_TERMINATIONS["awaiting_approval"]`. The run object gains `approval_request_id`, `approval_state`, `approval_digest`, and `awaiting_approval: bool`. `REASONING_PROMPT` **byte-identical** — and H8 asserts the byte equality rather than trusting it.
- [ ] Design decision #5 — **the apply is a different principal, and the substrate is `StateStore`, not a new file.** `"approver"` joins `AUTHORED_SOURCES` with the same argument Day 19 used for `"orchestrator"`: admitting a writer does not loosen the grounding rules for other shelves, and the write policy forbids it everything else. `APPROVAL_KIND = "approval"` with `approval_key(request_id) → f"/approval/{request_id}"`, `ttl` inherited from the store (so expiry is the *existing* mechanism, not a new one), and `write_approval(store, principal, request_id, payload, *, run_id, ttl)` mirroring `memory.write_orchestration` (`memory.py:179`). **What is explicitly refused:** a separate JSON file, a separate table, a bespoke expiry pass — because the day would then be maintaining a second store with a different provenance model, and Day 17's store already has durability, TTL, a size cap, a derived index, compaction, and a fail-closed author check. Day 27's persistence is four lines of glue.
- [ ] Design decision #6 — **every transition is an audit entry in Day 26's chain, in order, and the chain's exclusions are unchanged.** Six event codes: `approval_requested`, `approval_approved`, `approval_rejected`, `approval_expired`, `approval_applied`, `approval_compensated` — each with `seq`, `run_id`, `principal` (the *acting* principal), `tool`, `effect`, `reversibility`, `digest`, `code`, `prev_hash`, `hash`; no argument values, no row values, no `email`, no model prose, no `proposal` text. Reason: the request and the decision must be one timeline. A request in a JSON file and a decision in a different JSON file, correlated by an id, is two systems to join during an incident — and the whole reason Day 26 built the chain was that a security decision nobody can read is a rumour.
- [ ] Design decision #7 — **the surface is a CLI plus two read-only routes, and the decision route is deliberately absent.** `tools/approvals.py --list | --show <id> | --approve <id> --as <principal> | --reject <id> --as <principal> --reason "…"`; `GET /approvals?state=&tool=&principal=` and `GET /approvals/{id}` in `server.py`, both read-only, both returning the record with argument *values* masked by default. `POST /approvals/{id}/decide` is **not** added, and the omission is recorded in the notes at the point the routes are registered, with the owner (Day 29) and the reason (`server.py` has no auth, no session, no agent route, and no `principal` header — putting the single most valuable call in the system behind the least protected surface in the system would be a regression, not a feature). The environment knobs follow Day 26's shape: `APPROVALS_PATH` (a `state`-shaped store path, default beside `STATE_STORE_PATH`), `APPROVAL_TTL_S` (default 900), `APPROVALS=none` (the H9 control), and `APPROVAL_MAX_PER_RUN` (default 1) — which is the one *new* resource bound, because unlike Day 26 the model is not the only thing that can create requests: a caller can, so the per-run cap exists to keep a decision queue from being flooded by a loop, with rate limiting still Day 28's.

### 6. Build: `ai_os/approval.py` — Digests, States, Store, and the Refusals (1 hour 5 min)

- [ ] Add `ai_os/approval.py` as a **library of decisions about one record**, in the same register as Day 26's `permissions.py` (which was a library of decisions, not a framework): `REVERSIBILITY_REVERSIBLE` / `_COMPENSATABLE` / `_IRREVERSIBLE` · `STATE_REQUESTED` / `_APPROVED` / `_REJECTED` / `_EXPIRED` / `_APPLIED` / `_COMPENSATED` / `_SUPERSEDED` · `EVENT_REQUESTED` … `EVENT_COMPENSATED` (the six audit codes) · `ERROR_APPROVAL_REQUIRED` and the seven refusal codes · `Signals(as_dict, what_it_measures, what_it_does_not)` · `ApprovalRecord(request_id, tool, digest, subject, signals, requested_by, requested_at, expires_at, ttl_s, reversibility, effect, data, state, decided_by, decided_at, reason, applied_by, applied_at, compensates, proposal, provenance)` with `as_dict`/`from_dict` and the metadata-safe shape Day 23 established.
- [ ] Implement `digest_action(tool, args, *, effect, data, reversibility, targets) -> str` and make the canonicalization **literally Day 26's**, extracted rather than retyped: `json.dumps(payload, sort_keys=True, separators=(",", ":"), ensure_ascii=False, allow_nan=False)`, then `sha256` hexdigest, prefixed `sha256:`. Add a unit assertion that the digest is stable under argument key order, unchanged by a JSON-serialized proposal, and *changes* when any single field changes — because a digest that is stable under the wrong transformation is worse than no digest, since it looks like evidence.
- [ ] Implement `build_signals(*, last_result, cited_subset_retrieved, prior_approvals, declared_data, model_stated_confidence) -> dict`, with each entry a `{"value": …, "measures": …, "not": …}` triple and a module-level assertion that **no key named `score`, `risk`, `confidence`, or `probability` is produced** (H6 asserts the same thing from outside, because a rule that lives only inside the builder is a rule the next contributor can delete). `model_stated_confidence` is accepted, recorded, and marked `not_a_signal: true` with a one-line reason; the function has no branch that can turn it into a gate input.
- [ ] Implement `ApprovalStore(store: StateStore, *, clock=time.time, ttl_s=900.0, max_per_run=1)` with `submit`, `decide`, `apply`, `compensate`, `expire_due`, `get`, `list_for`, `pending`, and `counts`. Every method: reads the record, checks the legal edge, applies the preconditions, writes through `write_approval`, and returns a new record — **no in-place mutation and no update method**, because a record you can edit is a record whose approval you cannot reconstruct. Each refusal is a `ValueError` carrying a code (or a `Decision`-shaped failure for the registry seam) and a message that names the request id, the current state, and what was attempted.
- [ ] Implement the preconditions in one place, in this order, so that no caller can reorder them into a weaker check: actor present (no anonymous decision) · record exists · `state == requested` (else `approval_duplicate` / `approval_invalid_state`) · `now < expires_at` (else `approval_expired`) · `decided_by` holds `approver_role` **as a grant** (else `approval_role_not_permitted`) · `decided_by != requested_by` when `reversibility == irreversible` (else `approval_self_approved`) · reason present on a rejection (else `ValueError` — a rejection with no reason is not reviewable). And the apply-side list: state is `approved` · caller holds the `executor` grant · `digest_action(...)` recomputed from the *arguments about to be run* equals the stored digest (else `approval_digest_mismatch`).
- [ ] Keep it offline, dependency-free, and deterministic: the only clock is the injected `clock` (H1–H9 run with a fake clock so expiry is a fact rather than a sleep), no network, no model call anywhere in the module, and the record's fields chosen so that **argument values live in the state store but never in the audit entry** — enforced by scanning the audit file in H7, as Day 26's C7 did.
- [ ] Add the four refusals that are *design statements* rather than error handling, and give each a docstring explaining what would be lost without it: `approval_digest_mismatch` (the TOCTOU hole) · `approval_self_approved` (separation of duties) · `approval_reversal_impossible` (an irreversible action has no undo, and a pretend-undo is how a customer is told their refund was reversed) · `approval_duplicate` (a decision is final; otherwise a re-approval silently replaces a rejection and the audit shows only the survivor).

### 9. Test: The H-Fixtures (H1–H9) and the Control (1 hour)

## Deliverable

The **human approval mechanism** — one workflow, over one durable record, opened by the layer and never by the model, deciding about a value rather than a description, with every transition in the audit chain the permission layer already writes:

```text
   THE MODEL              agent.py  (REASONING_PROMPT byte-identical — 27 days running)
      │  proposes a call … the ONLY thing it can do here
      ▼
   THE CHOKE POINT        tools.py: ToolRegistry.execute  (unchanged seam from Day 26)
      │  grant resolution → reversibility irreversible ⇒ confirm: human
      ▼
   THE GATE               permissions.py → approval.py: submit(...)
      │  ONE record, written by the LAYER: digest, canonical subject, signals, expires_at
      │  the model never writes it, never reads it, never re-opens it
      ▼
   THE REFUSAL            ToolResult.failure(error_kind=approval_required, class=policy)
      │  ⇒ no retry · no sibling substitution · run stops
      ▼
   THE STOP               agent.py, two lines: step_approval ⇒ termination "awaiting_approval"
      │  the run does NOT block: execute_bounded has no cancellation, tool_timeout_s=30
      ▼
   THE RECORD             state.py: kind=approval, author="approver" ∈ AUTHORED_SOURCES
      │  durable · ttl-bounded (default 900s) · append-only (no update method exists)
      ▼
   THE HUMAN              tools/approvals.py  (a CLI, deliberately not an HTTP route)
      │  approve / reject, attributed, or say nothing ⇒ expired (never "assumed")
      │  requested_by ≠ decided_by for anything irreversible
      ▼
   THE EXECUTOR           a SEPARATE, separately-granted principal; the agent may not apply
      │  digest recomputed from the args about to run ⇒ mismatch refused
      ▼
   THE REVERSAL           reversible ⇒ a COMPENSATING record (append, never edit)
      │  irreversible ⇒ approval_reversal_impossible, loudly
      ▼
   THE RECORD             audit.py: one chain, six event codes, in order
      │  requested · approved · rejected · expired · applied · compensated
      │  digest yes · argument values no · row values no · model prose no

   THE CONTROL            H9 — on vs off: identical answers, tools, SQL, rows, tokens, cents
                         0 chats · 0 embeds · 0 SQL · 0 rows · 0 approvals on the default path
   THE COST               machine: one store write + one sha256 per transition
                         human:   queue latency — unmeasured, and the report says so
   THE HONEST LIMITS      no authenticated operator surface (Day 29) · no queue, no rate limit
                         (Day 28) · no external chain anchor, so truncation is invisible
                         (Day 29) · the `email` decision is still unmade and today's export
                         client reads exactly those rows · there is still NO WRITE PATH, so
                         nothing in this repository can refund anybody, and the day does not
```

Twenty-six days gave the machine authority and yesterday gave it a way to say no. Today hands the last decision to a person — and finds out, halfway through, that the interesting part is not the handoff at all. It is that **the step a human is supposed to be guarding is the one step this system has never had**, so the day had to decide what "executes" means, and every honest answer forced the same conclusion: the security-relevant event is the *decision*, not the mutation, and a decision can be made, recorded, expired, reversed, and refused without a single row changing. The finding is that **the human is the only component in this system that cannot be a confused deputy — and the only way to make that true rather than flattering is to make the human's decision a value, not a description, attributed to a principal that is not the requester, expiring on a clock, recorded in the same chain as the model's ask, and impossible for the model to obtain on its own.**
