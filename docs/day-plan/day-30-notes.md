# Day 30 Notes — Integration, Evaluation and Defense

> Notes answering `docs/day-plan/day-30.md`.
> Twenty-nine days built a machine that reads (Days 6–10), acts (11–12), fails honestly (13), computes (14–15), plans (16), remembers (17–18), splits into specialists (19), learns how it will be judged (20–22), explains one request from the inside (23) and across a process boundary (24), learned to be attacked (25), learned who may open a door (26), learned to stop and wait for a person (27), drew a map of what breaks first (28), and yesterday learned to package itself and refuse a second writer (29). The curriculum now hands the series its last day and its only non-mechanism: **bring the entire system together, run end-to-end scenarios**, with seven scenarios written as literal questions — *How does Saleor handle checkout?* · *Where is this behavior implemented?* · *Which products generated the most revenue?* · *Why did this customer fail to complete checkout?* · *Why is this test failing?* · *Why did latency increase?* · *Perform an approved operation* — **ten columns** to record per scenario (input, reasoning/workflow, retrieval, tools, evidence, output, latency, cost, evaluation score, failure cases), and the deliverable **a complete technical demonstration of the AI Engineering OS**. The inventory for this day is unlike every previous day's, because the missing thing is not a feature: the repository has **43 files under `ai_os/`** (40 `.py` plus three YAML datasets), **29 harnesses under `tools/`**, a regression gate that names **17 suites** (`tools/regress_all.py:59–77`), an **18-row** golden set (doc nine + code six + the adversarial F/G/H), and a per-day fixture family for every day since Day 7 — and **not one artifact that runs the whole system through one request path in one process under one clock.**
>
> The finding that reorganizes the day is not "there is no demo." It is that **the fixture-per-day discipline built seventeen worlds, and the demonstration is the first artifact that has to live in one.** Every day suite constructs its own: `tools/trace_smoke.py` builds its own trace store, `tools/data_smoke.py` its own seeded `sqlite3.connect(":memory:")` (`data.py:455–458`), `tools/state_smoke.py` its own store file, `tools/bench_agent.py` its own scripted `BenchGateway`. "Green" has only ever meant *green in that day's world*, and assembly is where **state stops being private.** The trace store is a per-process `OrderedDict` capped at 256 (`observability.py:706–716`, the cap at `:714`), so a seven-scenario run can evict scenario 1's trace before scenario 6 asks for it. The gateway's `last_provider`/`last_latency_ms`/`last_attempts` are module-level fields on a shared global (`gateway.py:80–82`) read *after* the call (`server.py:124–126`), so a latency column read in a shared process reads whatever ran last. The store cache is identity-keyed and holds **one store per corpus** (Day 28), so a third is refused by name. The state store's `get()` calls `_maybe_save()` (`state.py:607`), so a read rewrites the file; the ledger is a per-process list (`ledger.py:65`). None of these is a bug; every one is a **context assumption a per-day fixture never had to state**, and the demonstration is the first artifact that states them.
>
> The second finding is that **two of the seven scenarios cannot be demonstrated today, and a demo that scripts around them is a brochure.** Scenario 5 — *Why is this test failing?* — names a capability never designed: there is **no test-runner tool, no CI artifact, no log-ingest tool, and no test outcome in either corpus**; the honest answer is "here is the code that could fail," which is scenario 2 in disguise. And the real finding is categorical, not additive: a `run_tests` tool would be the first request in thirty days to ask the system to **execute something**, which is a different authority from every read tool built so far and would need a sandbox this repository has never had. Scenario 7 — *Perform an approved operation* — runs into Day 27's finding: **there is no write path at all**, so the demonstration ends with `Saleor rows changed: 0` and the decision (the request, the digest, the principal, the refusal) is the entire security event. Both are findings, and the day's rule is that **the ten columns are filled for a scenario the system must decline exactly as carefully as for one it answers**, because a demonstration whose negative cells are blank measured only the code it just read.
>
> The single idea: **a demonstration is not a claim that the system works — it is a set of pre-registered scenarios whose refusals are as load-bearing as its answers, and the defense is the register that says, per cell, what is mechanized, what is a scripted stand-in, and what is `PENDING` with an owner.** The day therefore treats the demonstration the way Day 28 treated the diagram and Day 29 treated the image: as a **falsifiable document** with a ratchet over it, where every cell is a fixture id or a named absence and a cell that is neither is refused.
>
> **The one line the day would die defending: an integration test is not the sum of the day suites — it is the discovery of the state each day suite kept private, so the honest demonstration is the one that measures the trace cap, the store cache, the state file, and the shared global as *integration findings* rather than inheriting them as assumptions, and that records the scenarios it must decline as checked absences rather than scripting a stand-in that would make the register look fuller than the system is.**

## 1. The Loaded Question — "A Complete Technical Demonstration"

The deliverable is one sentence and a ten-column table, and the table is the day's real content:

```text
for every scenario record:  input · reasoning/workflow · retrieval · tools · evidence ·
                            output · latency · cost · evaluation score · failure cases
```

Read as a report template, those ten columns are a checklist filled in afterwards. Read as a fixture format, they are **ten expectations written before the run**, and that is the whole design. The series has known this since Day 7 — *write the expectation first, or you are describing what happened* — and a demonstration is precisely the artifact where the temptation to describe backwards is strongest, because the run is the impressive part and the expectation is the boring one. So the day's first move is to treat the curriculum's columns as the **schema of a pre-registered row**, exactly as Day 20 treated the golden set's five fields: `input` is the hashed question, `reasoning/workflow` is a path (a plan with step ids, or a single call), `retrieval` is the evidence set with ids and scores, `tools` is the ordered sequence, `evidence` is the *invariant*, `output` is the answer with citations, `latency` is a measured number with its caveat, `cost` is the ledger delta with its units, `evaluation score` is a layer-1 verdict with every `PENDING` semantic cell owned, and `failure cases` is the **negative twin** and the refusal it must produce.

A demonstration is also the first artifact in the series with a reader who **was not there**. Twenty-nine days wrote for the person who can re-run the fixture; a demonstration writes for someone who cannot. That changes what it must contain and it changes what it must refuse. It must contain the same thing the `Exit Check` of every plan has contained for twenty-nine days — an answer to *"how do you know?"* — but citable, so a reviewer can follow a cell to a fixture rather than to a paragraph. And it must refuse the one thing a demo is built to do: **make the system look better than it is.** The curriculum supplies seven scenarios, and five of them the system can address today; the day's honesty is entirely in what it does with the other two.

Two do not, and the two are the day's most useful rows, because they are the only places where the demonstration can be *wrong* — a green S1 is a green S1, but a *claimed* S5 or S7 is a lie with a scenario number on it, and the register exists to make that impossible.

Why the same demonstration is not simply the seventeen day suites run in sequence — and this is the architectural question the day turns on — is that the suites were written to verify a *world*, and the demonstration has **one** of every shared thing. The day names the four shared resources precisely, and each one is a file:line rather than a worry. **The trace store** is one `OrderedDict` capped at 256 (`observability.py:706–716`, cap `:714`); seven scenarios fit, and a rerun loop does not, so the honest cell is `held | evicted` and never "retained." **The store cache** is keyed on `sha256(file) + embedding_model + dimension` and holds one store per corpus (Day 28), so the demo holds docs and code and a **third is refused by name** — an LRU here would make "which store answered" a question about timing, and Day 28 refused it for exactly that reason. **The state store** is one file whose `get()` rewrites it (`state.py:607`) and whose `put` rewrites the whole file from memory (`state.py:838–845`, tmp at `:843`, `os.replace` at `:845`) with no lock, so S4's checkpoints and S4's episodic index are two consumers that must be **serialized** — safe for exactly one writer, which is the assumption Day 29's `SingleWriter` lock makes true rather than lucky. **The gateway and its ledger** are one shared global with mutable `last_*` fields (`gateway.py:80–82`) and one per-process list (`ledger.py:65`), so the latency column reads *inside its own call window* and the cost column is the ledger's **delta**, never its total.

The scope boundary is where the honesty has to live, and it is the sharpest of the series because a demonstration is read as a claim about the *whole*. **The demonstration proves paths, never quality.** The semantic cells (citation support in meaning, groundedness beyond membership, answer relevance) stay `PENDING` exactly where Days 20–22 left them, and a scenario whose only failing cell is semantic is `pending` with an owner, never `pass`. **The stub scripts what the fixture says**, so a green scenario proves the plumbing carried the request, not that a model would answer it; the real-model column is a handoff, not a result. **Two scenarios are absences**, asserted by enumeration rather than admitted in prose. And **no scenario touches a write path**, so `Wrote? = no` survives its sixteenth day unchanged, and the word "refund" appears nowhere in the deliverable. Identity, authentication, the decision route, the trace sink, retention, and a metric baseline are `PENDING` with owners, and the report says so in the same table as its passes — because a demonstration that reported only what it proved would be the first document in thirty days to be *shorter* than the truth.

## 2. Integration Is the Discovery of Shared State

An integration test asks a question a unit fixture structurally cannot: *when two modules that each passed alone are placed in one address space under one clock, which of their assumptions about the world stop being true?* The answer in this repository is unusually legible, because twenty-nine days built modules that are each **carefully bounded and each bounded by a different world**, and the boundaries are visible in the harnesses rather than hidden in the modules. `tools/trace_smoke.py` builds a trace store and never fills it. `tools/state_smoke.py` builds a store file and never shares it. `tools/bench_agent.py` builds a `BenchGateway` that answers by script and never touches the real gateway's `last_*` fields. `server.py` builds **one** gateway at import (`server.py:35`) and every route reads the same global. So "do the pieces work" has been answered seventeen times and "does the system work" has never been asked, because nobody had written the artifact that has to hold all seventeen in one hand.

The four shared resources, and what each one does to the demonstration:

**The trace store** is the clearest example of a bound that is invisible until it is a consumer's problem. It is an in-process `OrderedDict` capped at 256 traces (`observability.py:706–716`, the cap at `:714`), and the cap is a *storage* decision made on Day 23 for a store that had no reader yet. A seven-scenario run opens a root per scenario (`server.py:103` for `/chat`, `:145` for `/chat/stream`, `:224` for `/rag`, plus the library scenarios' own roots), so the cap does not bind in a single demo and *will* bind in the rerun loop a demonstration is written to encourage. The honest handling is to report `traces_held` and `evicted_count` and the specific question — **is scenario 1's trace still fetchable after scenario 6 ran?** — and to state the boundary (`retention = process lifetime`) rather than imply that a demo is an observability tool. The general lesson is the day's: **a demonstration is a consumer of every bounded resource it touches, and a bound written on Day 23 becomes a finding on Day 30.**

**The store cache** is the integration's clearest win and its clearest trap, and both come from the same line. `_rag_store()` (`server.py:192–197`) calls `RagStore.load(path)` on every call, and Day 28's cached `load_store_cached` (keyed on `sha256(file) + embedding_model + dimension`) turns a per-request parse into a per-process one. So scenario 1 and scenario 2 both call `_rag_store()`, and the demo's cache read is `docs: miss→hit` then `code: miss→hit`. The trap is that **scenario 2's latency is then lower than scenario 1's for a reason that is not the question's difficulty** — a warm store, not an easy question — and a reader who is not told that reads the number as a quality signal, which is precisely the category error Day 28 built the identity-keyed cache to prevent. The day's rule is that the *reason travels with the number*: every latency cell in the record carries whether the store was cold or warm. And the safe default is asserted rather than assumed: a **third corpus is refused by name**, because an LRU would make "which store answered this" a question about timing.

**The state store** is the resource that makes the demonstration's single-process assumption explicit. One file backs scenario 4's plan checkpoints (`executor.run_plan` flushes task state, Day 17) and scenario 4's run-end memory index (`episodicize`/`remember_episode`, Day 18), and both go through a `put` that rewrites the entire file from memory (`state.py:838–845`) — while a `get()` also rewrites it (`state.py:607` calls `_maybe_save()`). So the demo must **serialize** S4's writes and record `state_writes`, and it must state the boundary the correctness depends on: the file is safe for exactly one writer, Day 29's `SingleWriter` lock is what makes the demonstration's assumption true rather than lucky, and the day the assumption breaks is the day a second replica appears — which Day 29 already refuses at boot. This is the integration finding that is *not* a bug and *not* a discovery, and it is the most valuable kind: a per-day fixture never had to write, read, and write the same file in one process, and the demonstration is where that sequence is first performed in order.

**The gateway and its ledger** are the shared resources a demonstration most easily flatters. The gateway is a module-level global (`server.py:35`) with mutable `last_provider`/`last_latency_ms`/`last_attempts` fields (`gateway.py:80–82`) that the routes read *after* the call returns (`server.py:124–126`); the ledger is a per-process list (`ledger.py:65`). So a latency column that reads `gateway.last_latency_ms` after the next scenario has started is reading the wrong call, and a cost column that reads `ledger.summary()` is reading the whole process. The discipline the day adopts is small and testable: **the latency cell is read inside the scenario's own call window, and the cost cell is the ledger's *delta* across the scenario.** The context enforces it — a read after the next scenario begins is a refusal, not a silently wrong number — which is Day 28's shared-global trap turned into an assertion rather than a comment. The honesty note the report carries: **the demo's latency column measures one call in a shared process and is not a benchmark**, and the day reports the *median of the scenario's own calls* rather than a single post-hoc read, because one sample in a shared process is a coincidence with a unit attached.

Why "it ran end-to-end" is not a control is now a specific claim and not a slogan. A runner that executes seven scenarios and prints seven answers has proven that seven code paths did not raise; it has proven nothing about the *system* and nothing about any specific answer. The repository already knows the shape of the missing control, because every day since Day 20 has shipped one: V9 (Day 20), R9 (Day 21), AB9 (Day 22), O9 (Day 23), D9 (Day 24), and every day's off-switch exist because **a feature that changes a legitimate answer is a bug wearing a feature's clothes.** So the demonstration's control is not "the demo ran." It is **Z9: with the runner off, every prior fixture is byte-identical; with the runner on, every prior fixture is still byte-identical** — because the demo is a **reader** of the system and not a modifier of it. The concrete claim is small enough to check: the runner adds no tool, no route, no span kind, no store, and no model call; offline it is 0 billed calls; and the only resource it *changes* is the trace store's contents, which is the one resource whose **consumption** is the thing under test.

The five integration findings the repository lets the day **predict from the code before it runs** — which is the whole point of writing the notes first — are these. (a) **The trace cap is invisible until it isn't** (above): it does not bind in a small demo and will bind in a rerun, so the cell is `held | evicted`. (b) **The store cache turns a per-request parse into a per-process cost**, so S2 is faster than S1 for a reason that is not the question (above). (c) **The recall pre-step becomes measurable end-to-end for the first time** (Day 18): S4 over a store S4 already indexed is the one place in thirty days where `recall()` (0 chats, 0 embeds) competes with a fresh investigation (≥1 chat) *inside one request path* rather than between two day suites, which is the "only if useful" meter arriving at its first honest consumer — and the honest finding is modest, because the answer to "is it useful" is still a real-model question. (d) **The data seam substitutes silently** (`data.py:798–806`): S3 with `SALEOR_READONLY_DB_URL` unset answers from `SEED_SQL` (`data.py:455–458`), so the demo must print *which backend answered* or its most confident number is its least trustworthy — the same discipline as Day 29's readiness probe naming the database. (e) **The two unanswerable scenarios are unanswerable in a way a fixture can assert**: S5's missing tool is enumerable (`registry.names()` has seven entries and none runs tests) and S7's missing write path is enumerable (`policy.yaml`'s `statement_allow` is `[select, with]` and no grant declares `effect: write`), so "we cannot demonstrate this" becomes a **checked** claim rather than an apology — and both run the demonstration's rule that **a fixture that asserted a scripted stand-in for either would be a `FAIL`.**

## 3. A Scenario Is a Fixture — the Ten Columns

The curriculum's ten columns are a fixture format, and the difference is *when they are filled*. Filled in afterwards they are a description; filled in first they are an expectation, and every one of them then has a failure mode that a fixture can catch. The day writes them down as the schema of a pre-registered row, in the same register Day 20 used for the golden set's five fields:

- **input** — the question, hashed (`obs.sha256_text`, `server.py:226`), so a scenario cannot quietly become a different question between the registry and the run.
- **reasoning/workflow** — the *path*: for S1/S2/S3/S6 a single call, for S4 a **plan** with step ids (Day 16's `Plan`, a list of `Step`s), so "workflow" means a structure and not a paragraph.
- **retrieval** — the evidence set, with ids and scores, and — this is the cell the day is most careful about — **the same set the invariant is checked against**, so `evidence` and `output` cannot disagree about what was retrieved.
- **tools** — the ordered sequence, compared to the registry's `expected_tools`, so a scenario that used the wrong tool is caught even when its answer happens to look right.
- **evidence** — the *invariant*, and there is exactly one per scenario, drawn from the series' five translations of one sentence.
- **output** — the answer with citations, and the fabricated twin's answer beside it.
- **latency** — a measured number, stamped with cold/warm, read inside the call window (§2).
- **cost** — the ledger **delta**, in the ledger's own units (`ledger.py:99`), never the process total.
- **evaluation score** — Day 20's **layer-1 deterministic** verdict, joined to the golden row where one exists and `n/a` where it does not (§0.5).
- **failure cases** — the negative twin and the refusal code it must produce; a scenario with no negative twin is not in the registry.

The **one invariant** deserves its own paragraph, because it is what makes the seven scenarios *one system* rather than seven demos. Days 6, 14, 16, 17, and 19 each translated the same sentence — *the answer may assert only what the evidence supports* — into their own vocabulary: `cited ⊆ retrieved` (Day 6 retrieval), `asserted ⊆ returned` (Day 14 data), `conclusion ⊆ evidence` (Day 16 planning), `recalled ⊆ authored` (Day 17 state and Day 18 memory), `delegated ⊆ returned` (Day 19 hand-off). The demonstration's contribution to the series is to **run them on one artifact and show they are the same check.** S1 and S2 assert `cited ⊆ retrieved`; S3 asserts `asserted ⊆ returned`; S4 asserts `conclusion ⊆ evidence` over the transcript **and** `recalled ⊆ authored` over the memory it recalled; S7 (when built) asserts the answer names the request id and asserts `applied: false`. And the proof that the demonstration is grading the system rather than congratulating it is that the **fabricated twins** — the rows the day suites built specifically to fail — still fail: `tools/plan_smoke.py`'s fabricating answer (P8), `tools/data_smoke.py`'s fabricated twin (Q8), `tools/tool_smoke.py`'s ghost symbol (T6). A demonstration whose twins pass is a demonstration whose check was re-typed and got it wrong, which is why the day calls the invariant from `ai_os/trace.py`'s existing functions (`grounding_over_transcript`, `recalled_subset_authored`) rather than re-implementing it.

Mapping a scenario to a route, a library call, or a refusal is the honest answer to *"can a user do this?"* and the repository's answer is uncomfortable and specific. **S1 and S2 are HTTP** — `POST /rag` with `corpus="docs"`/`"code"` (`server.py:200`, `:193`), the only two scenarios reachable by curl. **S3, S4, and S7 are library calls** — `server.py` exposes exactly `/health`, `/chat`, `/chat/stream`, `/traces/{id}`, `/traces`, `/ledger`, `/rag`, `/metrics`, `/logs`, `/ingest/span` (plus Day 29's additive `/healthz` and `/readyz`), and there is **no `/agent`, no `/sql`, no `/approvals` route**. The absence is not an oversight to be fixed in a demonstration: it is the standing consequence of Day 26's finding that there is **no authentication**, so a `/agent` route would place the most powerful capability in the system behind the least protected surface, and the day records the route gap per scenario rather than adding seven unprotected endpoints to make the demo easier. **S6 is an HTTP read of an already-built record** — `GET /traces/{id}` (`server.py:171`) for a curl, `obs.default_store().get()` for the library run (§0.4).

What "evaluation score" means is the column most likely to be flattered, so the day pins it. It is Day 20's **layer-1 deterministic verdict** — membership and arithmetic checks, each naming one owner: `expected ⊆ retrieved`, `cited ⊆ retrieved`, `conclusion ⊆ evidence`, `tool == expected_tools`, `must_not`, `refusal == expected`, `failure == category`, cost, latency. It is **not** a quality number, and the day refuses to invent one: layer 2 (the semantic slot, `ai_os/semantic_judge.py`) and layer 3 (the LLM-as-judge lane, off by default) stay exactly where Days 20–22 left them, and a scenario whose only failing cell is semantic is `pending` with an owner, never `pass`. The pipeline is the point — **the demo reports the same verdicts the gate reports**, joined by scenario id — which is what makes the scorecard a *join* rather than a second opinion, and what makes a disagreement a **gate bug to fix, never a demo to adjust** (Day 19's rule, `the fixture is never weakened`, arriving at the demonstration).

The cost column has two currencies, and reporting one is reporting the half the day controls. **Machine cost** is the ledger delta: S1/S2 are 1 embed + 1 chat each live and **0 billed** offline; S3 is **0 embeds + 2 chats** (generate, explain; +1 on a repair); S4 is the plan's chats plus its steps' chats and embeds; S6 is **0 chats, 0 embeds** (it reads a trace); S7 is **0 chats** and one state-store write per transition. **Human cost** — the only one Day 27 introduced — is unbounded and unmeasured: S7's decision waits on a person, the series has no instrument for it, and the report says so rather than reporting a latency it cannot have measured. And one number the day is proudest of is not a cost at all: the **offline demonstration is 0 billed calls for all seven scenarios and all ten columns**, which is what makes the artifact reproducible by anyone with the repository and no key — and is the reason thirty days of this were affordable in the first place.

## 4. The Seven Scenarios, One by One

**S1 — Knowledge: *How does Saleor handle checkout?*** The real request path: `POST /rag` (`server.py:200`), `corpus="docs"`, which embeds the question, retrieves from `data/store.json` (Day 21's 11,061 real chunks, dim 768, `@cf/baai/bge-base-en-v1.5`), builds context through Day 9's `build_context`, and answers from the gateway. The invariant is `cited ⊆ retrieved`, and the interesting cell is the one Day 21 found: **the invariant holds while the retrieval misses.** On the real store only 3 of 7 answerable rows surface ≥50% of their expected docs at k=9 and **4 surface none**, so a green `cited ⊆ retrieved` on S1 is compatible with a genuinely unhelpful answer — which is exactly the distinction the whole evaluation layer exists to keep, and the demonstration's first honest row. S1 is also the scenario that shows the store cache at work (§2), so its latency cell carries cold/warm. The failure case is a **refusal**: an out-of-corpus question must return the honest "not covered" path, not the nearest neighbours.

**S2 — Code: *Where is this behavior implemented?*** The same endpoint with `corpus="code"` (`server.py:193`), retrieving Saleor *source* ingested by `ai_os/ingest_code.py`'s AST extractor and cited as `module#Symbol:line` (`rag.citation()`). On the stub this is green (code six 6/6); the real `data/code_store.json` is **quota-blocked** (Day 10: Cloudflare's free 10k neurons/day covers ~16k of 29,156 symbols), so the honest cell is `stub` and the real column is `PENDING` with Day 10 as owner. The invariant is `cited ⊆ retrieved` over symbol ids, and the failure case is the fabricated `module#Symbol` (Day 11's T6 ghost), which the day suite already catches and the demonstration re-runs rather than re-implements.

**S3 — Data: *Which products generated the most revenue?*** The pipeline *is* the loop (Day 14): the model generates SQL as a **tool argument** through `run_saleor_sql`, the statement passes Day 15's choke point (`normalize → parse → policy → cost → rewrite → execute`), and the answer's numbers must satisfy `asserted ⊆ returned`. The definition guard is real: the glossary's `revenue` excludes `DRAFT` orders, and the policy enforces it. Two honest cells: the **backend label** (`stub (SEED_SQL)` offline vs `postgres`), because the seam at `data.py:798–806` substitutes silently and the day will not let its most confident number be its least attributable; and `Wrote? = no`, unchanged for the sixteenth day, asserted by the attack twin that re-runs a `DELETE`-shaped request and shows the run **stops** (`policy_violations: 1`, zero DB execution). S3 is the scenario with **no golden row** (§0.5) — its scorecard column is `n/a` on the golden set and green on `data_smoke`/`sql_attack_smoke`.

**S4 — Customer investigation: *Why did this customer fail to complete checkout?*** The demonstration's composed scenario and its least trustworthy: a **stored plan** (Day 16's `D16_PLAN_GOOD` shape — the curriculum's own five-step DAG with a `payment ← order_state` edge) executed by `executor.run_plan` through the same atoms as the loop, over **three** corpora (data, code, docs), with Day 18's memory pre-step on. The invariants are `conclusion ⊆ evidence` over the transcript (the P8 fabricated-cause twin must fail) and `recalled ⊆ authored` over the memory it recalled. The cost shape is the plan's chats plus its steps' — and the correction from §0.3: the run writes **k+1** state records (k checkpoints + one episodic index), not two. What S4 demonstrates is that **the executor composes steps across corpora and the answer stays grounded**; what it does **not** demonstrate is that a real model would choose those steps, which is Day 21/22's benchmark on a stored plan, and the day says so in the `pending` cell rather than letting a green S4 imply plan quality.

**S5 — Engineering investigation: *Why is this test failing?*** The day's first genuine gap, and the one a demo is most tempted to fake — a stubbed "test failure explanation" would be the Day-7 padding mistake wearing a demo's clothes. *Why is this test failing?* is a question about a **failing artifact** (a test run, a stack trace, a CI log, a commit), and the repository has none of those as inputs: `corpus/` is 233 documentation pages and `corpus_code/` is Saleor *source*, so the closest honest answer is "here is the symbol a checkout test would exercise," which is S2 with a different question shape — and the day **does not rename S5 into S2.** It records the missing capability precisely: no test-runner tool, no tool returns a test result, neither corpus holds a test outcome. And the real finding is categorical, not additive: a `run_tests` tool would be the first request in thirty days to ask the system to **execute something**, so it needs a sandbox and a *different authority* from every read tool built so far — which the permission model that would gate it does not have (Day 26 is designed, not built). S5's fixture is therefore an **absence fixture**: it enumerates `registry.names()` (seven tools, none runs a test), asserts no `ai_os/` module spawns a subprocess or a shell, and prints the enumeration — so the `PENDING` is proven rather than admitted.

**S6 — Operational investigation: *Why did latency increase?*** The question contains an aggregate the system cannot produce, and the honest split is the scenario's content. The **mechanism** is real and tested (Day 23/24): one request's causal span tree with a monotonic clock, parent paths, prompt refs, `model.<op>.attempt` spans, `ttft_ms`, the `client`/`server` distinction, and ledger-linked cost reconciled to the exact delta. So the demo **can** answer *"this request was slow, and here is where the time went"* — root duration, per-hop attribution, the retry that fell back, the store parse, the DB wait. It **cannot** answer *"latency increased"*, because that is a claim about a **window** and there is no window: the trace store is per-process and capped (`observability.py:714`), `/metrics` is a snapshot of counters and fixed-bucket histograms (`server.py:249`, Day 24), and there is no sink, no retention, and no baseline. The day answers the answerable half, states the unanswerable half as the reason S6 is `PARTIAL`, and notes the one thing a demonstration can still do: run S1 twice, cold and warm, and show the **store-cache delta** (Day 28) as the only "latency changed" fact the system can prove about itself.

**S7 — Controlled action: *Perform an approved operation.*** The scenario collides with the series' oldest clean claim. There is **no write path at all**: `SqliteDataStore` (`data.py:463`) and `PostgresDataStore` (`data.py:557`) each expose one query method and no mutation; `PostgresDataStore` sets `default_transaction_read_only`; `policy.yaml`'s `statement_allow` is `[select, with]`; and all seven registered tools are reads. So "perform an approved operation" demonstrates the **decision** — the request, the digest, the requested-by/decided-by, the refusal — and never a mutation, and the scenario's headline is **`Saleor rows changed: 0`**. While Day 27 is unbuilt, S7 is the second **absence fixture**: it asserts no grant declares `effect: write`, `statement_allow` is `[select, with]`, both stores expose exactly one query method and no mutation, and the Postgres session is read-only — so the `PENDING` is enumerated. The failure-cases column for S7 is **the whole scenario**, and the day treats that as correct: the most important thing about an approval system in this repository on this day is that nothing was approved, because nothing could be.

The seven as one sentence: **three scenarios run end-to-end through real seams (S1, S2, S3), one composes a stored plan over all three corpora (S4), one answers a mechanism and not a window (S6), one has no tool (S5), and one has no write path (S7)** — and the demonstration is honest exactly to the extent that it says which is which in the record and not in a preface.

## 5. Design: The Registry, the Record, the Refusal Register

The registry is the demonstration, and the runner is its rendering:

```yaml
# ai_os/scenarios.yaml — a SCENARIO is a question with ten pre-registered columns.
#   * `expect` is written before the run (the series' rule since Day 7).
#   * `pending` is a first-class cell: a demo that lists only what it proved is
#     a brochure; a demo that names what it could not prove is a defence.
#   * a column with no expectation is REFUSED, and a record cell that is neither
#     a fixture id nor a named `pending` is REFUSED — the register cannot acquire a blank.
version: 1
scenarios:
  - id: S1
    name: knowledge
    question: "How does Saleor handle checkout?"
    route: {kind: http, method: POST, path: /rag, body: {corpus: docs}}
    expect:
      tools: [search_saleor_docs]
      invariant: cited_subset_retrieved
      refusal_on: ["unrelated question", "empty corpus"]
    cost: {embeds: 1, chats: 1, sql: 0, rows: 0}
  - id: S3
    name: data
    question: "Which products generated the most revenue?"
    route: {kind: library, call: run_agent, tools: [run_saleor_sql]}
    expect:
      tools: [run_saleor_sql]
      invariant: asserted_subset_returned
      labels: {backend: "stub (SEED_SQL)"}
      refusal_on: ["DELETE-shaped request → policy stop, 0 DB execution"]
    cost: {embeds: 0, chats: 2, sql: 1, rows: 1, writes: 0}
  - id: S5
    name: engineering_investigation
    question: "Why is this test failing?"
    route: {kind: none}
    expect: {tools: [], invariant: null}
    finding: "no test-runner tool; registry.names() = 7 reads, 0 executors"
    pending: ["a run_tests tool (owner: a future ingestion+sandbox day)"]
  # S2 code · S4 customer · S6 operational · S7 controlled_action: same shape
```

**Decision 1 — the registry is a file, and the record is checked against it.** Day 28's ratchet was "every box is a file"; Day 29's was "an image is a subset with a manifest"; today's is the same idea at the demonstration level. `tools/demo_smoke.py` parses `ai_os/scenarios.yaml`, resolves every scenario's route against the code (an HTTP route exists in `server.py`; a library call exists in `ai_os/`, asserted by import, not by trust), and asserts **both directions** — every scenario in the registry ran, and every cell in every record is either a fixture id or a named `pending`. A registry with a phantom scenario and a record with an unaccounted cell are the same defect from opposite ends, and the second one is the brochure.

**Decision 2 — the runner is a reader, not a router.** In the register of `tools/eval_harness.py` (Day 20's "a router, not a grader"), `tools/demonstrate.py` presents each question to *production* exactly as a user would (offline stub by default, `--live` for the real gateway) and collects `{scenario, trace, ledger_delta, run}` **without touching answer-path code**. What it owns that a day suite does not is the **integration context**: one gateway, one state store, one trace store, one store cache for the whole run, with the four shared-resource events recorded as *findings* rather than as fixtures passing. Rejected: a fresh process per scenario — it would make every scenario look like its day suite and delete the integration question the day exists to ask.

**Decision 3 — the scorecard is a join, not a second opinion.** Each scenario maps to the harness that already grades it — S1/S2 → `tools/bench_rag.py --fixtures` (R1–R9) and the retrieval families (`retrieval_day10.py --stub`); S3 → `tools/data_smoke.py` (Q1–Q8) and `tools/sql_attack_smoke.py` (X1–X11); S4 → `tools/plan_smoke.py` (P1–P9) and `tools/bench_agent.py --fixtures` (AB1–AB9); S6 → `tools/trace_smoke.py` (O1–O9) and `tools/distributed_smoke.py` (D1–D9); S1/S2 (only) → `tools/eval_harness.py --stub`'s golden rows (§0.5) — and prints, per scenario, **the demo's verdict beside the existing harness's verdict.** A disagreement is a **gate bug to fix, not a demo to adjust** (Day 19's rule). Rejected: a new grader — the day adds no metric, no judge, and no semantic lane, because a demonstration that grades itself with a ruler it built is measuring its own consistency.

**Decision 4 — the two unanswerable scenarios are fixtures that assert absence.** This is the day's most careful design, because it converts *"we could not demo this"* from an apology into evidence. S5's fixture enumerates the registry (seven tools, none runs a test), asserts neither corpus holds a test outcome, and asserts **no `ai_os/` module spawns a subprocess or a shell** — and states why the gap is categorical (executing code is a new authority). S7's fixture asserts `statement_allow: [select, with]`, no `effect: write` grant, one query method per store and no mutation, and `default_transaction_read_only`. Both print their evidence, because a checked absence is the strongest cell in the register.

**Decision 5 — the demonstration runs twice: on the host and in Day 29's image.** Day 29's N9 asserted host/container parity for the offline N-set; Day 30 extends it to the seven scenarios, so the demonstration is a property of the **artifact** and not of the laptop. The image has no `.env` (Day 29), so on a fresh `docker run` the gateway is `None` (`server.py:38`) and S1–S4 are the **stub** scenarios — which is the correct and expected result, and the report says so verbatim in the same table as the pass, exactly as Day 29's N9 note did.

**Decision 6 — three documents, and the register is the deliverable.** `docs/demonstration.md` is the artifact a reader who did not build the system opens first: the seven scenario records, the scorecard, the integration findings, the defense transcript, and the residual register. `docs/evaluations/integration-day30.md` is the report: the Z1–Z9 table, the four shared-resource findings, the host/image parity, the cell accounting, and every `PENDING` line. `docs/concepts/integration.md` is the concept doc, joining the **18** already in `docs/concepts/` as its **nineteenth** (§0.2). All three keep the same three lines visible — **what exists, what does not, and who owns each absence** — which the series has been converging on since Day 26 and which gets its final form here.

## 6. Build: The Runner — `tools/demonstrate.py`

**Status: `PENDING` — not written, not run.** One file, one entry point, two modes, and the discipline is that the runner is a *reader* and never a modifier.

**The runner**, in the register of every harness in `tools/`: a decision, written down, with the reasons in comments, and deliberately not a framework. **Offline (the default)** builds the stub gateway (`tools/mock_gateway.py`) and the stub stores and runs all seven scenarios for **0 billed calls**; **`--live`** swaps only the *chat wire* for the real gateway from `.env` (retrieval stays on whatever store it is given, exactly as `tools/agent_smoke.py --live` does), labels the run `live`, and reports the real bill. A provider outage prints `[SKIP]` and exits non-zero rather than reporting a false `FAIL` — a demo that fails on a quota is a demo that lies about the system — the same contract `tools/agent_smoke.py --live` set on Day 12.

**The integration context** is the day's one genuinely new mechanism, and it adds no field to production code: `DemoContext` constructs one gateway, one `StateStore`, one `TraceStore`, and one store cache, and exposes `evicted(trace_id)`, `cache_stats()`, `state_writes()`, `ledger_delta(since)` — each a *reader* over an existing object (`obs.default_store()`, `gateway.ledger`, the store's own counters). The one addition is a **call-ordering discipline**: a scenario reads `gateway.last_*` inside its own call window, and the context rejects a read after the next scenario has started, which is Day 28's shared-global trap turned into an assertion rather than a comment.

**The ten-column record** is a dataclass with ten required fields and one optional (`pending: list[str]`), and an empty required field is a `ValueError` naming the scenario and the column. The rule is the whole point: **a scenario with an unfilled required cell does not render**, so the registry cannot quietly lose a column and the runner cannot print a partial record. The `pending` list is where every unprovable cell goes, with an owner string, and Z8 asserts it is non-empty *only* where the day claims a limitation — so a scenario that could be fully proven and is not is a `FAIL`.

**The seven scenario functions** are thin drivers over existing seams and nothing more: `s1_knowledge` → `POST /rag` `corpus=docs` (or `run_rag` in-process); `s2_code` → `corpus=code`; `s3_data` → `run_agent` with the data tool (the pipeline *is* the loop); `s4_customer` → `executor.run_plan` over a stored plan with the memory pre-step on; `s5_engineering` → the absence fixture; `s6_operational` → `obs.default_store().get(trace_id)` + the ledger reconciliation; `s7_controlled` → the Day-27 decision path *or* the absence fixture while Day 27 is unbuilt. **No scenario re-implements a check**: `cited ⊆ retrieved`, `asserted ⊆ returned`, `conclusion ⊆ evidence`, and `recalled ⊆ authored` are called from `ai_os/trace.py`'s existing functions (`grounding_over_transcript`, `recalled_subset_authored`, …), because a demonstration that disagrees with a day suite is a demonstration that re-typed the invariant and got it wrong.

**It stays offline, deterministic, and free**: the stub answers by script on `:8700`/`:8701`, the stub stores are embedded locally, the state store is a temp file, the trace store is the process's own, and the clock is injectable so latency is a *fact* and not a wait. There is **no `time.sleep` on the offline path** and **no real model call anywhere on it** — the same requirement as Days 27–29, and the reason the day's cost line is **0 billed calls** for the runner, the registry, the scorecard, and the checkers combined.

## 7. Build: The Integration Seam — What Only Breaks When All Seven Run at Once

**Status: `PENDING` — not written, not run.** Five measurements, each a reader over a shared resource, and the discipline is that a finding is reported as a finding and never dressed as a fixture passing.

**The trace store under seven scenarios.** Seven roots (`server.py:103`, `:145`, `:224`, plus the library scenarios' own roots) land in a store capped at 256 (`observability.py:706–716`, cap `:714`), so the demo reports `traces_held`, `evicted_count`, and the specific question — *is scenario 1's trace still fetchable after scenario 6 ran?* — and states the boundary (`retention = process lifetime`). The finding is not that the cap is wrong; it is that **a demonstration is a consumer of a bounded resource**, and the demo is the first artifact that has to say whether it can look backwards.

**The store cache.** `_rag_store()` (`server.py:192–197`) parses on every call; Day 28's cached `load_store_cached` (keyed on `sha256(file) + embedding_model + dimension`) makes it one parse per corpus per process. The demo records `cache: {docs: miss→hit, code: miss→hit}`, prints scenario 2's latency *with the reason* (warm store, not easy question), and asserts a **third corpus is refused by name** rather than evicting the first, because "which store answered" must never become a question about timing.

**The state store as one file with two consumers.** S4's checkpoints and S4's episodic index write the same file, whose `put` rewrites it from memory (`state.py:838–845`) and whose `get()` rewrites it too (`state.py:607`). The demo runs S4's writes **in one thread in one order** and records `state_writes` (the corrected `k+1`, §0.3), and states the finding Day 28 predicted and Day 29 enclosed: the file is safe for exactly one writer, **the lock from Day 29 is what makes the demo's single-process assumption true rather than lucky**, and the day the assumption breaks is the day a second replica appears — which Day 29 refuses at boot.

**The ledger and the shared global.** The cost cell is the ledger's **delta** across the scenario (`ledger_delta(since)`), never the total (`ledger.py:65`); the latency cell reads `gateway.last_latency_ms` (`gateway.py:80–82`) **inside the scenario's call window**, and the context rejects a read after the next scenario has begun. The honesty note the report carries: **the demo's latency column measures one call in a shared process and is not a benchmark**, which is why the day reports the *median of the scenario's own calls* rather than a single post-hoc read.

**The first honest end-to-end recall.** S4 over a store it has already indexed is the one place in thirty days where Day 18's "only if useful" meter is measurable at the system level: `recall()` is **0 chats, 0 embeds** (Day 8/9's scorer over stored signatures) and a fresh investigation is **≥1 chat**, so the demo prints the two and the delta. The finding is modest and stated as such — on a stub, recall *serves an episode*, which Day 18 proved; the demonstration adds that the comparison can be made **inside one request path** rather than between two day suites, and that "is it useful" is still a real-model question (`PENDING`, Day 21).

**The findings the run did not produce**, because a demonstration that reports only what it saw is hiding the half of the method that is prediction: (a) the **two-writer corruption** Day 28 predicted and Day 29 measured is *not* reachable in the demo — one process, and Day 29's lock refuses a second — so the demo records the prediction, the guard, and the fact that it cannot exercise it, and does **not** claim the corruption is gone; (b) the **`$0.00` failure cost** (`ledger.py:99` — `cost_usd=self.cost(model, usage) if ok else 0.0`) is invisible offline (no failures) and real live, so it is recorded as a Day-28 finding *confirmed by reading* rather than claimed by measuring; (c) the **database substitution** (`data.py:798–806`) is invisible on the stub *by construction*, so S3's backend label is the cell that matters and the demo asserts the **label**, not the backend choice — the same discipline as Day 29's readiness probe.

## 12. Daily Learning Record

### Problem

A capstone is normally a demo, and a demo cannot be wrong — it runs, it prints, and the audience claps. The problem the day actually solved is that this repository has seventeen verified worlds and has never been one system. Every day suite since Day 7 constructs its own store, its own stub gateway, its own fresh state file, its own clock, and verifies its module against *that* world; so "green" has always meant *green in that day's world*, and the assembly question — which assumptions stop being true when two modules share an address space — had never been asked, let alone measured. Concretely, and in the order the day found them: a trace store capped at 256 traces (`observability.py:714`) that a seven-scenario run consumes and a rerun loop exhausts; a store cache keyed on identity that holds one store per corpus (Day 28) and refuses a third by name; a state store whose `get()` rewrites the file (`state.py:607`) and whose `put` rewrites all of it (`state.py:838–845`), so S4's checkpoints and S4's memory index are two consumers of one unlocked file; a gateway whose `last_*` fields are a shared global read after the call (`gateway.py:80–82`, `server.py:124–126`) so a latency column can read the wrong scenario; a per-process ledger (`ledger.py:65`) so a cost column can read the whole process. And two of the curriculum's seven scenarios the system simply cannot do: *Why is this test failing?* has no test-runner tool, no test outcome in either corpus, and would require **executing untrusted code** — a new authority — and *Perform an approved operation* has no write path at all, so its honest headline is `Saleor rows changed: 0`. The problem is not that the pieces are missing. It is that **the state each world kept private was never placed in one room, and a demonstration is the first artifact that has to live in one.**

### Concept

**A demonstration is not a claim that the system works; it is a set of pre-registered scenarios whose refusals are as load-bearing as its answers, and a defense is the register that says, per cell, what is mechanized, what is a scripted stand-in, and what is `PENDING` with an owner.** Four ideas did the real work. **A scenario is a fixture** — the curriculum's ten columns read as ten *expectations written before the run*, exactly as Day 20 read the golden set's five fields, so each column has a failure mode and a scenario with an unfilled cell does not render. **Integration is the discovery of shared state** — the four resources the demonstration has one of (the trace store, the store cache, the state file, the shared gateway) are each a file:line, and the day's job is to measure them as *findings* rather than inherit them as assumptions; a bound written on Day 23 becomes a finding on Day 30. **The invariant is one sentence in five vocabularies** — `cited ⊆ retrieved` (Day 6), `asserted ⊆ returned` (Day 14), `conclusion ⊆ evidence` (Day 16), `recalled ⊆ authored` (Day 17/18), `delegated ⊆ returned` (Day 19) — and the demonstration runs them on one artifact, calling the existing functions rather than re-typing the check, so the fabricated twins still fail and prove it is grading the system and not congratulating it. And **absence is a finding, and it is asserted by enumeration** — S5 and S7 name what does not exist (`registry.names()`; `statement_allow: [select, with]`) with the evidence printed, because a limitation that is asserted can be closed and observed, and a limitation admitted in prose is inherited by whoever edits the file next. Three rules make the day specific to this repository. **The runner is a reader, not a router** — it presents each question to production exactly as a user would, adds no tool, route, span kind, or store, and its control is that every prior fixture is byte-identical with it on and off. **The scorecard is a join, not a second opinion** — each scenario maps to the harness that already grades it, so a disagreement is a gate bug to fix and never a demo to adjust. And **the demonstration runs on the host and in Day 29's image**, so it is a property of the artifact and not of the laptop.

### Understanding

The re-readings hit in order. **(1) Seventeen green suites are not one green system, and the gap is exactly the state each suite kept private.** The demonstration's most valuable output is not a green scenario; it is the four measured integration findings — the cap nobody filled, the cache nobody shared, the file nobody contended, the global nobody re-read — because those are the things a per-day fixture could not have seen and a production incident would have found. **(2) A demonstration is the first artifact with a reader who was not there, so it must be citable rather than persuasive.** Twenty-nine days wrote `Exit Check`s for the person who can re-run the fixture; the defense transcript is that same reflexive question — *how do you know?* — turned outward, and the answer must point at a fixture id rather than a paragraph. **(3) The honest negative is worth more than the honest positive.** A green S1 is a green S1; a *claimed* S5 or S7 is a lie with a scenario number on it, and the register makes the lie impossible by refusing a cell that is neither a fixture nor a named absence — which is why the absence fixtures are the day's most careful design and not its apology. **(4) The category error the day must keep avoiding is quality-as-path.** `cited ⊆ retrieved` holds while the retrieval *misses* (Day 21: 4 of 7 answerable rows surface none), and a warm store makes S2 faster than S1 for a reason that is not the difficulty. The demonstration's whole honesty rests on reporting the *distinction* — a path proven, a judgment withheld — which is why the semantic columns stay `PENDING` with owners and the latency cell carries cold/warm. **(5) The two scenarios the system cannot do point at a categorically new authority.** S5 needs to **execute** code and S7 needs to **write**; every tool built in thirty days is a read, so these are not two missing features but the first two requests to grant authority the system has spent its entire history not having — which is why the day names them, enumerates them, and does not build them on the last day of the series. **(6) The capstone's honest headline is a count of accounted-for cells.** On day thirty the measurement of a system is not what it can do but whether every claim it makes can be traced to the thing that would falsify it — and the number the day is proudest of is the **zero** in the unaccounted column.

### Debugging

- **A prior fixture moved with the runner on** → the demo is not passive. Check what it *wrote*: the trace store's contents, a state record, a ledger row. The runner must add no tool, route, span kind, or store; if it did, that is the bug and not the fixture.

- **A scenario's latency is the wrong call** → `gateway.last_*` (`gateway.py:80–82`) is whatever ran last. The read must be inside the scenario's call window; the context's rejection of a late read is the test. If the number improves for no reason, check for a warm store before checking the question.
- **A green `cited ⊆ retrieved` with a useless answer** → not a bug. That is Day 21's finding: the invariant holds while the retrieval misses. Do not "fix" it; report it, because the *distinction* is the demonstration's most important cell.
- **A scenario cannot find its trace** → the cap is 256 (`observability.py:714`) and the store is per-process. Check `evicted_count` before suspecting the span code; an `evicted` trace is a bounded-resource fact, not a missing span.
- **A third corpus silently replaced the first** → the cache must refuse, not evict (Day 28). If the demo answered a code question from the docs store, the identity key is wrong, and the key is `sha256(file) + embedding_model + dimension` or it is a guess.

- `cited ⊆ retrieved` holds while retrieval misses. Should the demonstration's *evaluation score* column be allowed to be green in that case, or does a demonstration owe its reader the retrieval-miss as a first-class failure even when the invariant passes?

- The register's headline is a count of accounted-for cells. Is that metric gameable in the same way a coverage number is — plenty of cells, all traced, none of them the ones that matter?
- Thirty days end with a system that reads well and cannot write at all. Is that the right place for an "AI Engineering OS" to stop, or is the absence of a write path the single largest thing the series chose not to learn — and who owns deciding that now?

### Tomorrow

There is no Day 31 in this curriculum, and the day has to end on the honest sentence rather than reach for one. What exists after today is a **demonstrated, accounted-for system**: seven scenarios recorded with ten columns each, a scorecard joined to the harnesses that grade them, four measured integration findings that no per-day fixture could have produced, two absences asserted by enumeration, and a register in which every claim is a fixture id or a named owner with **zero unaccounted cells**. What does **not** exist is a much shorter list than the series can flatter itself about, and the day names it in full: **no write path** (and therefore no refund, no order change, no action the curriculum's seventh scenario asks for); **no test-runner tool** (and therefore no answer to the fifth scenario, and a *sandbox* — a new authority — standing between the system and the first thing that would execute code); **no agent route, no authenticated surface, and no decision route** (so the most powerful capabilities are library calls and the decision surface is a CLI); **no trace sink, retention, or metric baseline** (so "why did latency increase" is answerable for one request and not across a window); **no semantic evaluation** (so every scenario's *quality* is `PENDING`, exactly as it has been since Day 20); **no real code store** (Day 10's quota, still the largest single missing artifact); and **no real-model observation for any scenario** (the `--live` bill is a handoff). The 30-day arc closes on the thing it has been building toward since Day 7 without ever naming: a system whose every claim has a falsifier, whose every absence has an owner, and whose most valuable artifact is not a mechanism at all but a **register** — because the series' final discovery is that the difference between a demo and a demonstration is not how much the system can do, it is whether the person watching can find out where you would be wrong. **The machine learned to read, act, fail, compute, plan, remember, specialize, judge itself, explain itself, defend itself, wait for a person, and package itself — and the last thing it learned is how to be honest about the half it did not build.**
