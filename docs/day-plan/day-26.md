# Day 26 — Agent Security

## Objective

Build permission boundaries.

Twenty-five days built a machine that reads (Days 6–10), acts (11–12), fails honestly (13), computes (14–15), plans (16), remembers (17–18), splits into specialists (19), learns how it will be judged (20–22), explains one request from the inside (23) and across its boundaries (24), and yesterday learned to be attacked (25). Every one of those days added **authority**, and yesterday's finding was that authority held by a component which reads untrusted text is a *confused deputy's* authority — so the defense has to live somewhere the model cannot edit. Today the curriculum answers yesterday with a mechanism: `Agent → Policy → Permission check → Tool`, with five rules — **read-only by default, explicit tool permissions, input validation, output validation, audit logs** — and the deliverable **basic agent security layer.** The repo's honest starting inventory: `policy.yaml` guards generated **statements** (`statement_allow`, `tables_allow`, `columns_deny`, `definitions`, `row_limit`, `max_cost`, server-side timeouts) and `SafeSql.inspect` runs it *before* a connection exists; `validate_args` in `ai_os/tools.py` types arguments against a hand-rolled JSON-Schema subset (`type`, `enum`, `minimum`, `maximum`, `required`, unknown-key rejection — **no `maxLength`, no `pattern`**); `ToolRegistry.scope()` (Day 19) already denies an out-of-role tool as a `policy` rejection; but `DataAgent.get_product` / `get_order` / `get_customer` call `self.store.query(...)` **directly**, bypassing `SafeSql.inspect` entirely, with `_literal()` doing manual quote-escaping on the `id`; `get_customer` returns `u.email`, a column `columns_deny` never names; **nothing anywhere validates what a tool returns**; `run_agent` already carries a `principal` string that authorizes nothing; and `server.py` exposes `/health`, `/chat`, `/chat/stream`, `/ledger`, `/rag` — no agent route, no identity, no audit surface. The one piece of good luck is structural: every path to a tool — `run_agent`'s loop, `run_tool_answer`, `executor.run_plan` (Day 16), the fallback ladder's sibling substitution, and Day 19's `RoleAgent.run` — goes through `registry.validate_args` + `registry.execute`, which means **one** seam can hold the whole boundary.

Day 26's first principle is that **a threat model is a list of worries and a permission system is a decision procedure.** Day 25 produced the list; today produces the procedure: a check that runs on **every** call and **every** result, resolves to `allow` or `deny` with a named code, defaults to deny, and leaves a record — including the records for the calls it allowed. The rule the whole day is built on: **a boundary in the caller is a boundary the next caller forgets.** Yesterday's L1 layer was four defenses assembled for four unrelated reasons — Day 15's SQL allow-list, Day 11's argument schema, Day 17's closed state write path, and the database's `saleor_read_only` role — plus Day 19's role scope. They all work, and none of them is *the* permission check, because none of them knows what a principal is, none of them can say "this caller may not," and a new tool added tomorrow inherits exactly the authority its author remembered to write down and nothing more. Day 26 makes the coherence **deliberate, uniform, and auditable** by moving the decision into the tool surface itself: `ToolRegistry` gains the check, `register()` gains a required grant, and a tool that arrives without one is a `ValueError` at import time rather than a code-review comment.

Second principle: **read-only is a declaration, a policy, and a privilege — and only the third is a fact about the world.** Day 15's guarantee came from a config file plus a database role, which is strong, and it is *invisible from the tool*: nothing in `run_saleor_sql`'s registration says what it does, so nothing in the registry, the trace, the audit log, or a reviewer's head can tell that this particular tool is the only one that reaches a database. Day 26 adds the first layer — every tool **declares** its effect (`read` / `write` / `none`) and its data class (`public` / `internal` / `pii`) — and the declaration is enforced three ways: no grant means no registration, no `write` effect may exist without an explicit human-confirmation grant (Day 27's approval seam), and the declaration is *asserted against* the layers below it, so the day can say which of the three layers is carrying the weight on any given call. Third: **validation belongs at both ends, and the far end is the half nobody has.** Input validation exists and is decent; **output validation does not exist at all**, and the gap is not academic: `columns_deny` is enforced on the *statement*, so a fixed resolver that selects `u.email` is inside policy, and a result set that came back with `password_hash` in it would be handed straight to the model. Day 26 adds `check_result` — declared column set, denied-column intersection, row cap, the retrieval contract (`doc_id`/`chunk_id` present so `cited ⊆ retrieved` stays decidable) — and fixes the failure mode that makes output validation pointless if you get it wrong: **a permission failure at the result boundary returns no rows at all**, because a partial answer is how a leak becomes untraceable, and Day 14's `_data_result` already showed the shape-preserving trick (keep `columns`, `sql`, `executed`; drop the values). Fourth: **a permission system that cannot be audited is a rumour.** `Ledger` records provider calls and money; the trace records a request; nothing records *who was allowed to do what*. Day 26 adds `ai_os/audit.py`: append-only JSONL, hash-chained (`prev_hash` → `hash`), one entry per decision, `principal`/`tool`/`effect`/`decision`/`code`/`args_hash`/`result_shape`/`run_id`/`latency_ms`, and **nothing sensitive** — no SQL text, no row values, no email, no prompt, no secret — because the metadata-safe default from Days 23–24 does not relax when the input is a decision, and a security feature that expands what gets recorded is a regression wearing a feature's clothes. And the day is honest about what a hash chain is: **tamper-*evident* for edits, reorders, and interior deletions; not tamper-proof against truncation of the tail**, because nothing inside the process can notice a file that simply ends. That anchor is Day 29's.

Fifth, and most uncomfortable: **this is authorization, not authentication.** The `principal` is a string the caller supplies — `run_agent(..., principal=...)` already accepts one, and `STATE_PRINCIPAL` already defaults it — so a caller who can pass `principal=admin` is an admin, and the audit log records a *decision*, not a *person*. Nothing today changes that, and the day must not let the word "security" in the title hide it: identity, secrets, transport, and rate limiting are Day 29, and the residual register has to say so in the same paragraph as the invariants. Sixth: **deny by default, including for the caller we do not recognise.** A principal with no entry in the grant file gets the `default` set, and `default` grants only the two read-only search tools — so an unknown caller is *less* privileged than a known one, and the seven-tool registry the model sees today must be re-derivable, or the control row below is not a control. Seventh: **exactly one check per argument.** A `sql` argument's check is semantic (`SafeSql.inspect`) with a byte cap as a resource bound; an `id` argument's check is a shape (`pattern`) because its semantic layer does not exist and cannot honestly be invented for a literal; a `table` argument's check is the closed set derived from the schema card, which today is *identical* to `tables_allow` — a coincidence the day converts into an asserted, load-time-checked invariant instead of a fact someone has to remember. Two checks on one argument is how a policy ends up disagreeing with itself; zero checks is how `maxLength` never gets added.

And the control returns: **C9.** With the permission layer on or off, every legitimate request must be bit-identical — same answer, same tool sequence, same SQL text hash, same row counts, same tokens, same cents — because the whole layer is deterministic, local, and offline: **0 chats, 0 embeds, 0 SQL, 0 rows.** The only behavioral differences may appear on traffic that is *supposed* to be denied, and that asymmetry is the entire point. Day 23 earned "traceable", Day 24 "end-to-end", Day 25 "attackable, and defended where it counts"; Day 26 earns **"governed"** — and hands Day 27 the one thing an allow-list can never decide by itself: which actions deserve a human, and Day 29 the isolation, identity, and secret management that a boundary inside the process cannot be. **The tree learned to cross doors, the system learned to be attacked, and today it learns who is allowed to open them — and it finds out that "who" is still a string the caller chose.**

## Duties Outline

### 1. Learn: The Loaded Objective — "Build Permission Boundaries" (45 min)

- [ ] Parse **"build permission boundaries"** as a claim about *where a decision is made*, not about how many rules exist: the question at every seam is not "is this allowed?" (a lookup answers that) but **"which code, if the model, the planner, the fallback ladder, the orchestrator, and the next engineer all conspire, still gets to say no?"** A boundary that only one caller honours is a preference with a config file.
- [ ] Inventory the boundaries this repo already has, named by file and function, and mark for each whether it is a **check** (it can say no), a **declaration** (it says what something is), or a **privilege** (the world says no regardless): `policy.yaml` + `SafeSql.inspect`/`Policy.check` (check, statements only) · `validate_args` (check, shape only) · `ToolRegistry.scope()`/`ERROR_ROLE` (check, role only, Day 19) · `StateStore._check_provenance` + `AUTHORED_SOURCES` (check, writes only, Day 17) · `execute_bounded` timeout wall, the step wall, the ledger ceiling, `detect_repeat`/`detect_oscillation` (resource walls, not permissions) · `saleor_read_only` + `default_transaction_read_only` (privilege) · and **nothing at all** that answers "may *this principal* call *this tool* with *these arguments*, and may it keep *these columns*?"
- [ ] Write the gap list honestly, because the gap list is the day: **no grant model** (a tool's authority is whatever its author remembered) · **no deny-by-default** (the registry *is* the allow-list; the model is shown every registered tool) · **no identity** (`principal` authorizes nothing) · **no output validation** (nothing inspects a `ToolResult`) · **no audit** (no record of a decision, allow or deny) · **no closed argument shapes** (`maxLength`/`pattern` are absent from the hand-rolled validator; `id` reaches SQL through `_literal`'s escaping alone; `max_chars` has a minimum and no maximum) · **no declaration** (nothing says `run_saleor_sql` is the only tool that touches a database).
- [ ] Pre-commit the day's split: **grant resolution, deny-by-default, the single choke point, the registration-time grant requirement, `maxLength`/`pattern` enforcement, the result contract (declared columns, denied-column intersection, row cap, retrieval contract), no-partial-rows on a result failure, the audit entry shape, the hash chain and its verification, and the on/off equivalence are `MECH`.** **The grants' correspondence to reality is not**: who actually needs `get_customer`, whether an operator would approve this grant set, and whether a real model ever attempts an escalation are questions with no fixture, and the day must not invent one.
- [ ] Pre-commit seven invariants before any build: **(a) one choke point** — every call and every result passes `ToolRegistry`, so the loop, `run_tool_answer`, `executor.run_plan`, the fallback ladder, and `RoleAgent.run` inherit the boundary for free; **(b) deny by default** — an unregistered tool, an ungranted tool, an unknown principal, and a missing decision are all *deny*, and `execute()` with no decision supplied denies; **(c) registration is a grant** — no grant, no tool; **(d) exactly one check per argument** — a shape check or a semantic check, never both and never neither; **(e) result failures return no rows** — shape is preserved, values are not; **(f) every decision is recorded, allows included** — in an append-only, hash-chained log that carries no values; **(g) C9** — the layer is passive: legitimate traffic is bit-identical on and off, at zero model and query cost.
- [ ] Name the negatives with owners: **authentication, transport security, secret management, egress policy, and rate limiting** are Day 29; **human approval for consequential actions** is Day 27; **a real threat model from an operator who owns this data** is `PENDING` and is why the grant file is a proposal, not a mandate; **an external anchor for the audit chain** (so truncation is detectable) is Day 29; **authentication of the `principal` string** is Day 29 and is the single largest honest limit the day carries.

### 2. Learn: Read-Only by Default — Three Layers, Only One of Which Is a File (45 min)

- [ ] Learn the three layers and say which is which, because the day's whole vocabulary depends on the distinction: **declaration** (the tool says what it is: effect `read`/`write`/`none`, data class `public`/`internal`/`pii` — a fact about *our* code, enforced by `register()`), **policy** (config says what is permitted: `statement_allow`, `tables_allow`, `columns_deny`, `row_limit`, `max_cost`, and now per-tool grants — a fact about *our* rules), and **privilege** (`saleor_read_only` has no write grant; `default_transaction_read_only` is set on the session — a fact about the *world*, which no config file can overrule). A reader who asks "is this system read-only?" deserves all three, and today only the third is unfalsifiable by us.
- [ ] Learn why **default** is the load-bearing word and why the common reading of it is the wrong one. "Read-only by default" is usually implemented as *start from the full capability set and subtract what is forbidden* — a **deny-list**, which is Day 15's `columns_deny` shape and which fails in the direction that matters: a new tool, a new table, or a new argument appears with **full** authority, and only gets weaker as someone remembers to subtract. Day 26's rule is the opposite: **a tool has no authority until a grant names it**, so the failure mode of forgetting becomes *denial*, which is safe, loud, and testable. The grant file is small on purpose — seven tools, three principals — because an allow-list that must be edited to add capability can be reviewed, and a deny-list that must be edited to remove capability is reviewed only after the incident.
- [ ] Learn what a *write* would even look like here, so the write path can be refused by construction rather than by vigilance: a refund, an order cancellation, an address change — none exists in this repo, and the day does not build one. That is not a gap in the day's work; it is the reason the day can claim read-only **without a single write to undo**: the strongest form of "read-only by default" is a registry in which no write-shaped tool has ever been registered. So the fixtures register one deliberately — a `create_refund`-shaped tool used *only* in the harness, never in `build_default_registry` — and assert that it is refused for every principal, and that granting it requires an explicit `effect: write` grant whose `confirm` field names a human-approval seam that **does not exist yet**, which is exactly how Day 26 hands Day 27 its first real client.
- [ ] Learn the fourth layer nobody counts: **the store.** Day 15 has three (`statement_allow`, `SafeSql.inspect`, the role), and Day 14's Q5 exists precisely to prove the *engine* refuses a write when layer 1 is bypassed via `DataAgent.run(validate=False)`. Today the same question has to be asked of a *result*: the statement was allowed and the rows still have to be checked, because the fixed resolvers never pass through `SafeSql` at all. And note the offline stub: `SqliteDataStore` has no read-only role, so the MECH fixtures are testing layer 1 and the new layer 4, and the privilege claim is `PENDING` until it runs against Postgres with `SALEOR_READONLY_DB_URL` set.

### 3. Learn: Explicit Tool Permissions — Grants, Effects, and Deny by Default (45 min)

- [ ] Learn a grant's anatomy, and keep it small enough to read in one screen: `tool` · `effect` (`read`/`write`/`none`) · `data` (`public`/`internal`/`pii`) · `args` (per-argument caps: `maxLength`, `pattern`, `enum`) · `result` (the **declared** column set, `max_rows`) · `confirm` (`none` or `human`, reserved for Day 27) — and a principal map `{"default": [...], "analyst": [...], "support": [...]}` whose union is still only the seven tools of `build_default_registry`. A permission file nobody can read is a permission file nobody can review, and a review that cannot happen is a review that does not occur.
- [ ] Learn **the choke-point argument**, which is the day's central architectural claim: there are exactly five ways this system reaches a tool, and they all go through `registry.validate_args` and `registry.execute`. That is not luck — it is the shape Days 11–16 built (`run_tool_answer` *is* `run_agent(max_steps=1, max_tool_calls_per_step=1)`; Day 16's executor walks a plan through the same atoms; Day 19's `RoleAgent.run` *is* `run_agent` with a narrower registry). So the check belongs in the registry, and it belongs in **both** `validate_args` and `execute`, because a decision made at validation time and not carried into execution is a decision a future call site can skip. The fixture that proves it is not "we added a call" but "we removed the possibility": `execute()` with `decision=None` denies, so a hypothetical fifth path is safe by default rather than dangerous by omission.
- [ ] Learn what **least privilege at the contract surface** means for a language model, and why it is better than a call-time refusal: `registry.schemas()` is what the gateway sends the model, so if `schemas()` returns only the principal's granted slice, an ungranted tool is not merely refused when called — it is *never named in the prompt*, so the model cannot spend turns discovering it. Day 19 already does this for roles via `scope()`; Day 26 generalizes the same idea from roles to principals and then makes `scope()` a *derived view* of the grant file rather than a second, parallel rule table. The constraint that keeps the control row honest: **the `default` grant set must be exactly today's tool set**, or C9 is not a control but a behavior change.
- [ ] Learn the **principal** honestly. `run_agent` already takes `principal`, and `StateStore` already keys every record by one, so the identity plumbing exists and is used — for *scoping memory*, not for authorizing anything. Today it is a caller-supplied string: it is **authorization with no authentication**, and the difference is not academic, because an unauthenticated `principal=admin` is not a weaker admin, it is an admin. So the day builds the decision procedure over a principal it does not trust, and writes the limitation into the deliverable rather than the changelog: **Day 26 decides *what may be done*; Day 29 decides *who is asking*.**
- [ ] Learn the difference between a **missing grant** and a **malformed grant**, because only one of them may be silent. A missing grant is a deny — normal, expected, auditable. A malformed grant (a grant for a tool nobody registered, a principal entry that is not a list, a `result.columns` that is not a list) is a **load-time error**, because a permission file that half-parses is a permission file that silently grants half of what it looks like it grants. `load_permissions()` fails closed and says which line and which principal, in the spirit of `Policy.from_dict`.

### 4. Learn: Validation at Both Ends — Input as a Gate, Output as the Half Nobody Has (45 min)

- [ ] Learn that the current input validator is a *ten-line subset* and that the two missing keys are the two that matter for security: `ai_os/tools.py`'s `validate_args` enforces `type`, `enum`, `minimum`/`maximum`, `required`, and unknown-key rejection — and **nothing else**. There is no `maxLength`, so a model may hand `search_saleor_docs` a 40 KB "query" and the only thing bounding the observation is Day 12's `budget_chars` clamp *after* the call; and there is no `pattern`, so `id` — which reaches SQL through `_literal()`'s hand-rolled quote-escaping — accepts any string at all. Day 26 adds exactly those two keys to the same hand-rolled validator (no new dependency, same error-message discipline: **name the field, name the bound**), and pins every cap against a **measured** legitimate maximum rather than a taste: the longest real query in the Day 14/15 fixtures, the longest real `doc_id` in `corpus/`, the largest `k` any fixture uses. A cap tuned to a guess breaks Q1–Q8 and I1–I9, and the fix is the cap's provenance, never the fixture.
- [ ] Learn the **class distinction that Day 12's retry rule makes load-bearing**: a *repairable* rejection invites "fix the argument and retry once" (rule 4), while a *policy* rejection is a STOP (rule 5). So an over-long query is `invalid_args`/`repairable` — the model may shorten it, which is correct and useful — while a permission denial, a denied column in a result, or a request for an ungranted tool is `rejection_class: policy` and must never arrive dressed as repairable, or the day hands out the retry it exists to prevent. The fixture asserts the class for each refusal, because a denial that arrives as `repairable` is functionally a bypass with better manners.
- [ ] Learn **output validation** from the specific hole rather than the general principle, because a general principle does not survive contact with a codebase. Three facts, all verifiable in this repo: (1) `columns_deny` is enforced on the **statement**, inside `SafeSql.inspect`, which only `DataAgent.run` calls; (2) `get_product` / `get_order` / `get_customer` do **not** call it — they call `self.store.query(...)` directly, so their result columns are governed by nothing at all; (3) `get_customer` selects `u.email`, and `email` is not on the deny list. The conclusion is not "PII is leaking" — it is the sharper, more useful one: **the deny list describes a class of statement, and the system also emits results, so half the policy has no subject.** Day 26 gives results a subject: every grant declares the columns its tool may return; a result carrying a column the grant did not declare is a contract violation; a result whose columns intersect `columns_deny` is refused; and a tool with no declared columns (the two search tools return *evidence records*, not columns) is held to the **retrieval contract** instead — `doc_id` and `chunk_id` present on every evidence row, text length within the grant's cap, so `cited ⊆ retrieved` and `conclusion ⊆ evidence` stay decidable after a security decision has run.
- [ ] Learn the failure mode that decides the whole design: **a permission failure at the result boundary returns no rows.** Not a truncated set, not the safe columns, not a masked value the model may paraphrase. Day 14's `_data_result` already showed the shape-preserving move for a rejected *query* (keep `sql`, `validation: rejected`, `executed: false`; the values never existed), and Day 26 reuses it one layer out: keep `columns`, `query_kind`, `executed`, and the redacted-column names; drop every value. The reason is not tidiness — **a partial answer is how a leak becomes untraceable.** A model handed three of five columns will narrate the three, the trace will show a successful call, and the audit log will show an `allow`, and the missing two columns will be nobody's decision.
- [ ] Learn what a **redaction** is and is not, and settle the `email` question in writing rather than in a config diff. Three available moves: deny `get_customer` outright (safe, and probably wrong — support is a real job); redact the `email` column at the result boundary and record the redaction (the value leaves the process, the shape stays, `redacted: [email]` is in the result record and in the audit entry's `result_shape`); or grant the column to one principal only. Today the honest answer is that **nobody has asked**, so the day implements all three mechanisms, ships the strictest as the default, and marks the *choice* `PENDING` with an owner — a security day that silently edits a deny list to make a fixture green has taught the wrong lesson, and one that silently grants a column to make a fixture pass has invented a mandate nobody gave it.

### 5. Design: The Permission Model, the Choke Point, and the Audit Record (30 min)

- [ ] Design the grant file before touching the registry — the whole file, because the file *is* the reviewable artifact:
  ```yaml
  # permissions.yaml — who may call what, and what may come back.
  #   * allow-lists, always: a tool has no authority until a grant names it.
  #   * declaration + policy + privilege: the tool says what it is, this file
  #     says what is permitted, the saleor_read_only role says what is possible.
  #   * fail closed: an unknown principal gets `default`; a malformed file is a
  #     load error, never a partial load.
  version: 1
  principals:
    default:    [search_saleor_docs, search_saleor_code]     # least privilege
    analyst:    [search_saleor_docs, search_saleor_code, run_saleor_sql, describe_saleor_schema]
    support:    [search_saleor_docs, get_order, get_product]
  tools:
    search_saleor_docs:   {effect: read, data: public,   args: {query: {maxLength: 512}}, result: {evidence: true, max_rows: 10}}
    search_saleor_code:   {effect: read, data: public,   args: {query: {maxLength: 512}}, result: {evidence: true, max_rows: 10}}
    run_saleor_sql:       {effect: read, data: internal, args: {sql:  {maxLength: 8000}}, result: {columns: "*", max_rows: 100}}
    describe_saleor_schema:{effect: read, data: internal,args: {table: {enum: "$tables"}},   result: {columns: "*", max_rows: 1}}
    get_product:          {effect: read, data: public,   args: {id: {pattern: "^[A-Za-z0-9_-]{1,64}$"}}, result: {columns: [id, slug, product_type, currency, price, variants], max_rows: 1}}
    get_order:            {effect: read, data: internal, args: {id: {pattern: "^[A-Za-z0-9_-]{1,64}$"}}, result: {columns: [id, number, status, currency, total, lines], max_rows: 1}}
    get_customer:         {effect: read, data: pii,     args: {id: {pattern: "^[A-Za-z0-9_-]{1,64}$"}}, result: {columns: [id, email, orders, currency], max_rows: 1, redact: [email]}}
  ```
  Note what is *not* in the file: any `write`. A `write` effect may only be added with an explicit grant carrying `confirm: human`, and no such grant exists, so today the file's maximum authority is a read.
- [ ] Design decision #1 — **one choke point, in the tool, carrying the decision from validation into execution.** `ToolRegistry.__init__(permissions=…)`; `validate_args` returns the `Decision` alongside the `ToolResult` (`ToolResult` gains a `permission` field, so the decision travels with the value); `execute` re-checks and **denies when it has no decision**, so a future call site is safe by omission. Every existing path (`run_agent`, `run_tool_answer`, `executor.run_plan`, the fallback ladder, `RoleAgent.run`) is unchanged code that inherits the boundary, and the fixture set proves it by calling all five with an ungranted tool.
- [ ] Design decision #2 — **registration requires a grant, and the grant's declaration is load-checked against the layers below it.** `register(name, schema, fn, grant=…)` raises when the grant is missing, and the smoke test proves it by attempting a registration with no grant. `run_saleor_sql`'s `effect: read` is then *asserted* against `policy.yaml` (`statement_allow: [select, with]`) and against the store's read-only role — so if someone edits the policy to allow `insert`, the day's own fixture fails and says which of the three layers stopped disagreeing. A declaration nobody cross-checks is a comment.
- [ ] Design decision #3 — **deny by default at four levels, each with its own code.** `no_grant` (tool is not in the principal's set) · `unknown_tool` (not registered — inherited from Day 11, still `repairable`, because a hallucinated name is the model's mistake to fix) · `unknown_principal` (a principal with no entry falls back to `default`, and the *fact that it fell back* is audited) · `missing_decision` (`execute` reached with no decision — an internal-invariant violation, `policy`, and loud). The codes are part of the contract because Day 25's `rejection_class` and Day 15's `error_kind` already are, and a security decision without a name is a decision nobody can grep for.
- [ ] Design decision #4 — **exactly one check per argument, declared in the grant.** `sql`: semantic (`SafeSql.inspect`) + a byte cap as a resource bound, never a second parse · `id`: shape (`pattern`), because its only semantic layer is `_literal`'s escaping and pretending otherwise would be a check that does not exist · `table`: the closed set derived from `SCHEMA_CARD`, which today is *exactly* `tables_allow` — a coincidence the load-time check converts into an invariant (a card table outside the allow-list is a boot error, and a policy table with no card entry is a warning) · `query`/`module`: shape with a measured cap · `k`: the existing `maximum`, plus the missing `maximum` on `max_chars` (bounded by the corpus budget, so a model cannot ask for an unbounded observation).
- [ ] Design decision #5 — **result contract, and no partial rows.** `check_result` runs on every `ToolResult` before it becomes a `tool` message: declared-column membership, `columns ∩ columns_deny = ∅`, `row_count ≤ grant.max_rows`, retrieval-contract conformance for evidence rows, redaction of `redact:` columns with the redaction *named in the result record*. A violation is `rejection_class: policy` with the shape preserved and every value dropped, so the model is told the call failed and the trace can still say which columns arrived.
- [ ] Design decision #6 — **every decision is audited, allows included, and the audit log is append-only and hash-chained.** `ai_os/audit.py`: `AuditEntry(seq, ts, run_id, trace_id, principal, tool, effect, decision, code, args_hash, result_shape, latency_ms, prev_hash, hash)`, one JSON object per line, `hash = sha256(canonical_json(entry − hash))` chained to `prev_hash`, `verify()` walking the file and naming the first broken link. A log of only denials tells you what failed and nothing about what a principal is doing, which is the question an incident review actually asks. Bounded per run by the turn wall — at most `max_steps × max_tool_calls_per_step` calls, so the *model* cannot flood it — and never rotated by the layer, because silent truncation is the one attack a self-verifying file cannot see.
- [ ] Design decision #7 — **the trace grows columns, the prompt does not change, and the refusal text names a class rather than a policy.** `ai_os/trace.py` gains `permission` (the decision), `permission_code`, `granted_tools`, and `redacted` per step row, with the metadata-safe default intact. `REASONING_PROMPT` is **unchanged** — rule 5 ("`rejection_class: policy` → STOP") already does exactly what a permission denial needs, and a prompt edit here would be a security change made in the one place Day 25 proved cannot carry one. `TERMINATION_NOTE["policy"]` is generalized from "the safe SQL layer refused a *policy* violation" to the policy *class* (`permission_denied`, `sql_policy`, `role_violation`, `result_violation`) so the note stays truthful when the refusal did not come from SQL — the alternative is a note that lies on every non-SQL denial, which is worse than no note.

### 6. Build: `ai_os/permissions.py` — Grants, Decisions, and a Fail-Closed Loader (1 hour 5 min)

- [ ] Add `ai_os/permissions.py` and keep it a *library of decisions*, not a framework: `EFFECT_READ`/`EFFECT_WRITE`/`EFFECT_NONE` and `DATA_PUBLIC`/`DATA_INTERNAL`/`DATA_PII` · `ArgRule(maxLength, pattern, enum, minimum, maximum, semantic)` · `ResultRule(columns, max_rows, evidence, redact)` · `Grant(tool, effect, data, args, result, confirm)` · `Principal(name, tools)` · `PermissionSet.from_dict/load(path)` and `PermissionSet.for_principal(name)` · `Decision(allow: bool, code: str, reason: str, grant: Grant | None)` · `check_call(principal, name, args, *, perms) -> Decision` · `check_result(name, result, *, perms, decision) -> Decision`.
- [ ] Make the loader **fail closed and specific**: a missing file is a `ValueError` naming the env var and the default path; a principal entry that is not a list of strings, a grant for a tool nobody registered, a `result.columns` that is not a list, an unknown `effect`/`data` value, or a `write` effect without `confirm: human` is a `ValueError` naming the key — never a silently ignored key. An unknown *principal* is not an error: it resolves to `default` and the resolution is itself auditable, because refusing a brand-new caller is correct and crashing on one is not.
- [ ] Keep the resolution order explicit and testable: **grant for the principal → `default` grant set → deny `no_grant`.** No inheritance chains, no wildcards, no "tool prefix" matching — a permission file with a pattern language in it is a permission file whose review is a proof, and this repository's rule has been "build before abstracting" for twenty-five days.
- [ ] Thread the existing config conventions rather than inventing new ones: `PERMISSIONS_PATH` (default `permissions.yaml` beside `policy.yaml`) and `PERMISSIONS=none` to restore the ungoverned path, matching `SALEOR_SQL_POLICY`'s shape, plus `AGENT_PRINCIPAL` beside the existing `STATE_PRINCIPAL`. Add the knobs to `.env.example` with the same explanatory comment style — the env file is documentation that cannot go stale.
- [ ] Add the two missing JSON-Schema keys (`maxLength`, `pattern`) to the hand-rolled `validate_args` in `ai_os/tools.py`, with the same failure-message discipline it already uses (**name the field, name the bound**) and the same refusal to coerce: a value that fails a bound is rejected, never truncated into compliance. A cap that silently shortens a query would make `Wrote?` and `columns` mean something other than what they say.
- [ ] Keep it dependency-free and offline: no policy engine, no OPA, no network, no clock dependence in the decision path (the `ts` is stamped by the audit writer, not by the check). Cost of the whole layer: **0 chats, 0 embeds, 0 SQL, 0 rows** — dictionary lookups, set membership, and one `sha256` per decision.

### 7. Build: The Choke Point — Registry, Loop, Result Path, and Trace (1 hour 5 min)

- [ ] Put the check in `ai_os/tools.py`'s `ToolRegistry` and nowhere else: `__init__(…, permissions: PermissionSet | None = None, principal: str | None = None)`, `register(name, schema, fn, grant=None)` refusing a grantless registration, `schemas()` returning the principal's granted slice (the least-privilege contract surface), `validate_args` returning the decision on the `ToolResult` (a new `permission` field: `{"decision", "code", "grant_tool"}`), and `execute(name, args, decision=None)` **denying when `decision is None`**. That last clause is the one to argue for in review: it converts "every caller remembered" into "every caller is safe by default," which is the difference between a boundary and a convention.
- [ ] Route the denial into the vocabulary that already exists: `ToolResult.failure(..., error_kind="permission_denied", rejection_class="policy")` — so Day 12's rule-5 STOP, Day 13's guard ring, Day 15's classification, the fallback ladder's policy exclusion, and the trace all handle it with tested code and **no new control plane**. Confirm by reading the loop, not by trusting the shape: the sibling substitution is already gated on `result.rejection_class != POLICY_CLASS`, so a denied call can neither retry nor substitute, and `step_policy` stops the run before `no_progress`/`oscillation` can claim the terminal.
- [ ] Make `executor.run_plan` (Day 16) and `RoleAgent.run` (Day 19) *inheritors* rather than participants: neither file gains a check, because both go through the registry. Then make `ToolRegistry.scope()` a **derived view** of the same grant file — a role's tool list becomes "the tools `default` grants, filtered by the role's declared interest" — so there is one rule table instead of two that can disagree, and a fixture asserts a role cannot reach a tool its grant set excludes even when the role map is wrong.
- [ ] Add `check_result` to the return path, in `registry.execute`, *after* the tool returns and *before* the result is stored on the `ToolResult` the loop will serialize: a violation becomes `ToolResult.failure(rejection_class="policy")` carrying the **shape** (`columns`, `query_kind`, `executed`, `redacted`) and **no values**; redaction drops the named columns and records `redacted: [email]` in the result and in the audit entry. Nothing in `_tool_message` changes, so the observation clamp, the `truncated` flag, and `cited ⊆ retrieved` keep working exactly as they did.
- [ ] Extend the trace, additively and safely: `ai_os/trace.py` gains `permission`, `permission_code`, `granted_tools`, `result_redacted`, and an `unknown_principal_fallback` flag, with the Day 23/24 metadata-safe default extended over the new fields (`data_columns` promotes them, values are never promoted) and C7 scanning them for values — **a security feature that expands what gets recorded is a regression wearing a feature's clothes**, and the audit entry is the most tempting place in the repo to leak a row of PII. `REASONING_PROMPT` stays byte-identical; only `TERMINATION_NOTE["policy"]` is generalized to name the refusal class.

### 8. Build: The Audit Log — Append-Only, Hash-Chained, Metadata-Safe (1 hour 5 min)

- [ ] Add `ai_os/audit.py`: `AuditEntry` (the shape in design decision #6), `AuditLog(path)` with `append(entry)`, `verify() -> {ok, entries, first_broken_seq}`, canonical JSON (`sort_keys`, `separators`, UTF-8, no floats) so the hash is reproducible, and a `NullAuditLog` for the control row and for every test that does not care. The log is **append-only**: no update, no delete, no rotation, and the writer opens in append mode with one `write()` per line so a crash truncates at a line rather than mid-record.
- [ ] Decide what an entry may contain, and write the exclusions down as rules, not as habits: **no SQL text, no row values, no column *values*, no `email`, no document text, no system prompt, no policy or permission file contents, no API key, no `ToolResult.error` string that could echo a payload.** Permitted: identifiers (`run_id`, `trace_id`, `seq`), the principal string, the tool name, the declared effect and data class, the decision and code, `args_hash` (a sha256 of the canonical args) plus `args_shape` (key names and value *lengths*), `result_shape` (row count, column names, `truncated`, `redacted`), and `latency_ms`. A reviewer can prove the call happened, prove which arguments were used without storing them, and reconstruct the decision — and cannot read a single row of customer data out of the log.
- [ ] State the tamper model precisely, because a security artifact whose guarantee is vague is a liability: **tamper-evident for edits, reorders, and interior deletions** (the chain breaks and `verify()` names the first bad `seq`), and **not tamper-proof against truncation of the tail** — nothing inside the process can notice a file that simply ends, so the day ships `verify()` reporting `entries: N` and `chain_ok: true` separately, and the residual register says the external anchor is Day 29's. Also state the second honest limit: **the log records a decision, not a person**, because the principal is a caller-supplied string; an audit log that cannot attribute is a log of events, and the deliverable says "audit" in the sense of *record*, not *forensics*.
- [ ] Expose the smallest useful inspection surface: `GET /audit?principal=…&tool=…&decision=deny` returning entries (no values to leak, since none are stored) and `GET /audit/verify` returning `{entries, chain_ok, first_broken_seq}` — deliberately tiny, deliberately read-only, and consistent with `server.py`'s existing `/ledger`. Note and record that **`server.py` has no agent route and no identity surface at all today**, so the audit endpoint is the first thing in this repo that is meaningfully per-caller; that is a Day 29 fact wearing today's clothes, and the day's own notes should say so where the endpoint is registered.
- [ ] Keep the volume argument in the design rather than in a footnote: entries per run are bounded by the turn wall (`max_steps × max_tool_calls_per_step`, default 6 × unbounded-within-step ⇒ the number of *calls the model actually emitted*, which Day 11 already caps per step), so **the model cannot flood the audit log**; a caller looping at the HTTP layer is a rate-limiting problem, and rate limiting is Day 29's.

## Deliverable

The **basic agent security layer** — one decision procedure that every tool call and every tool result passes through, that denies by default, and that records every decision it made:

```text
   THE LAYER            agent.py / executor.py / orchestrator.py
                          │  (all five paths, unchanged code)
                          ▼
   THE CHOKE POINT      tools.py: ToolRegistry.validate_args → Decision → execute(decision)
                          │            execute(decision=None) ⇒ DENY
                          ▼
   THE DECISION         permissions.py: check_call(principal, tool, args)
                          default grant set → deny "no_grant" · unknown principal → default + audited
                          │
                          ├─ INPUT   maxLength · pattern · enum · maximum · the existing type checks
                          │          exactly one check per argument: shape OR semantic, never both
                          ▼
   THE TOOL             seven tools, each with a declared effect + data class
                          │            registration without a grant ⇒ ValueError
                          ▼
   THE RESULT           permissions.py: check_result(name, result)
                          declared columns · ∩ columns_deny = ∅ · row cap · retrieval contract
                          violation ⇒ policy, SHAPE KEPT, VALUES DROPPED (no partial rows)

   READ-ONLY            declaration: effect: read, no `write` grant exists in the file
   BY DEFAULT           policy:      statement_allow [select, with] · tables_allow · row_limit
                       privilege:   saleor_read_only + default_transaction_read_only
                       any write ⇒  create_refund-shaped tool denied for every principal

   THE RECORD           audit.py: append-only JSONL, hash-chained
                       {seq, ts, run_id, principal, tool, effect, decision, code,
                        args_hash, result_shape, latency_ms, prev_hash, hash}
                       allows included · no SQL text · no row values · no email · no prompt
                       tamper-evident for edit/reorder/interior delete · NOT for tail truncation

   THE CONTROL          C9 — on vs off: identical answers, tools, SQL, rows, tokens, cents
   THE COST             0 chats · 0 embeds · 0 SQL · 0 rows — one sha256 + one line per decision
   THE HONEST LIMITS    the `principal` is a caller-supplied string: this is authorization,
                       not authentication (Day 29) · nobody has decided who may read `email` ·
                       the grant set is a proposal until an operator owns it (PENDING) ·
                       human approval for consequential actions is Day 27
```

Twenty-five days handed the machine authority, yesterday taught it to be attacked, and today gave it a way to say no. The finding is not that permissions are hard: it is that **the boundaries this repository had were real, scattered, and each attached to a different reason** — and a boundary whose existence depends on the author remembering to attach it is a boundary that a new tool, a new call site, or a new agent can walk straight through. What the day builds is the one thing that makes the rest coherent: a single decision procedure in the tool surface, defaulting to deny, checked on both the way in and the way out, refusing to hand back half an answer, and leaving a tamper-evident record of every call it allowed and every call it stopped — and it ends by naming the largest thing it does not do, which is to know **who** is asking. **The boundary is finally a thing in the system rather than a thing in four different files — and it still trusts a string the caller wrote.**
