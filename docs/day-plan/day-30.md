# Day 30 — Integration, Evaluation and Defense

## Objective

Bring the entire system together.

Run end-to-end scenarios. For every scenario record:

- input
- reasoning/workflow
- retrieval
- tools
- evidence
- output
- latency
- cost
- evaluation score
- failure cases

Twenty-nine days built a machine that reads (Days 6–10), acts (11–12), fails honestly (13), computes (14–15), plans (16), remembers (17–18), splits into specialists (19), learns how it will be judged (20–22), explains one request from the inside (23) and across a process boundary (24), learned to be attacked (25), learned who may open a door (26), learned to stop and wait for a person (27), drew a map of what breaks first (28), and yesterday learned to package itself — an image whose file list is a manifest, two probes with status codes, and one lock that refuses the second writer (29). The curriculum now asks for the first artifact in the series that is not a mechanism: **bring the entire system together, run end-to-end scenarios**, with seven scenarios supplied as literal questions — *How does Saleor handle checkout?* · *Where is this behavior implemented?* · *Which products generated the most revenue?* · *Why did this customer fail to complete checkout?* · *Why is this test failing?* · *Why did latency increase?* · *Perform an approved operation* — a ten-column record per scenario, and the deliverable **a complete technical demonstration of the AI Engineering OS**. The repo's inventory for this day is unlike every previous day's, because the thing that is missing is not a feature. The repository has **43 modules** under `ai_os/`, **29 harnesses** under `tools/`, a regression gate that names **17 suites** (`tools/regress_all.py:59–77`), an 18-row golden set (doc nine + code six + the adversarial F/G/H) and a per-day fixture family for every day since Day 7 — and **not one artifact that runs the whole system through a single request path in a single process in a single clock.** Every fixture builds its own world: `tools/trace_smoke.py` constructs its own trace store, `tools/data_smoke.py` its own seeded `sqlite3.connect(":memory:")` (`data.py:455–458`), `tools/state_smoke.py` its own store file, `tools/bench_agent.py` its own scripted gateway. "Green" has only ever meant *green in that day's world*, and the honest status of the integration question — *does the whole thing run as one thing?* — is that **no test in thirty days has ever asked it.**

Day 30's first principle is that **a demonstration is not a claim that the system works, it is a set of pre-registered scenarios whose refusals are as load-bearing as its answers** — and the finding that reorganizes the day is that **the fixture-per-day discipline built seventeen worlds, and the demonstration is the first artifact that has to live in one.** That is not a criticism of the discipline; it is the discovery of what the discipline measured and what it did not. Every day suite verified *its* module against *its* dependencies, which is exactly right for building one layer at a time and exactly wrong as evidence about the assembled system, because assembly is where **state stops being private.** The trace store is a per-process `OrderedDict` capped at 256 traces (`observability.py:706–716`, the cap at `:714`), so a seven-scenario run evicts scenario 1's trace by the time scenario 6 asks for it. The gateway's `last_provider` / `last_latency_ms` / `last_attempts` are module-level fields on a shared global (`gateway.py:80–82`) read *after* the call returns (`server.py:124–126`), so a latency column that reads them in a shared process is reading whatever ran last. The store cache is keyed on identity and holds **one store per corpus** (Day 28), so the demonstration holds two and a refusal is the correct behaviour for a third. The state store's `get()` calls `_maybe_save()` (`state.py:607`), so a read is a full-file rewrite; the ledger is a list in the process (`ledger.py:65`); and `run_rag` returns a `trace_id` for a record nobody can fetch after a restart. None of these is a bug. Every one of them is a **context assumption that a per-day fixture never had to state**, and the day's job is to state them, measure which of the seven scenarios each one touches, and print the register.

Day 30's second principle is that **two of the seven scenarios cannot be demonstrated today, and a demonstration that scripts around them is a brochure.** Scenario 5 — *Why is this test failing?* — names a capability this repository has never had: there is **no test-runner tool, no CI artifact, no log-ingest tool, and no failing-test input in either corpus**; `corpus/` holds 233 Saleor documentation pages and `corpus_code/` holds Saleor *source*, so the honest answer to "why is this test failing" is "here is the code that could fail," which is scenario 2 in disguise, and the day records the missing tool with an owner rather than pretending. Scenario 7 — *Perform an approved operation* — runs into the finding Day 27 spent a day establishing: **there is no write path at all.** `SqliteDataStore` (`data.py:463`) and `PostgresDataStore` (`data.py:557`) each expose one query method and no mutation method; the Postgres session is `default_transaction_read_only`; `policy.yaml`'s `statement_allow` is `[select, with]`; all seven registered tools are reads. So "perform an approved operation" demonstrates the **decision** — the request, the digest, the principal, the refusal — and never a mutation, and the scenario's headline number is `Saleor rows changed: 0`. Both scenarios are findings, and the day's third principle is the one that keeps the register honest: **the ten columns are filled for a scenario the system must decline exactly as carefully as for one it answers**, because a demonstration whose negative cells are blank is a demonstration that measured only the code it just read.

And the word in the title that is not *integration* or *evaluation* is **defense**, and it is the day's actual deliverable. A defense is the first artifact in the series whose reader did not build the system, so it cannot be a rerun of the fixtures — it is the register that says, per scenario and per column, **what is mechanically proven, what is a scripted stand-in, and what is `PENDING` with an owner.** The day therefore treats the demonstration the way Day 28 treated the diagram: as a **falsifiable document**, with the same ratchet. Every cell in the record is either a fixture id, or a `PENDING` with a name; a cell that is neither is refused by the harness, because the failure mode of a demonstration document is not being wrong — it is being *unchecked*, which is how a demo acquires its first lie.

## Duties Outline

### 1. Learn: The Loaded Objective — "A Complete Technical Demonstration" (45 min)

- [ ] Parse the deliverable as a claim about **evidence, not capability**, because "a complete technical demonstration" contains a hidden word: *demonstration*. A demonstration is a claim made to somebody who was not there, which makes it the first artifact in this series with a **reader who cannot re-run the fixtures in their head** — and that changes what it must contain. The useful reformulation, and the day's working definition: **for every scenario, name the input, the path it took, the evidence it produced, the number it cost, and the cells it cannot prove** — and if a cell cannot be traced to a fixture, that is a `PENDING` with an owner, not a blank. The curriculum's own ten columns are the register, and the day's only addition is the discipline of the last column: *failure cases* means the negative twin, not a caveat.
- [ ] Take the delivery honestly, because the curriculum's seven scenarios are **not seven features — they are seven request classes with three different dependency shapes**. Knowledge (scenario 1) and code (2) need a corpus and a store; data (3) needs the read-only seam and the policy; customer investigation (4) needs the planner over data *and* code *and* docs; engineering (5) needs a tool that does not exist; operational (6) needs the trace and a baseline; controlled action (7) needs an approval workflow and a write path. The day groups them by what has to be true, which is what makes the register possible: **three are answerable end-to-end today (1, 2, 3), one is answerable as a composed investigation on a stored plan (4), one is answerable only at the mechanism level (6), one has no tool (5), and one has no write path (7)** — and each status is a sentence a reader can check.
- [ ] Inventory the **integration surface as it actually stands**, item by item, because the honest statuses are the day: *the request path* — **real and complete for two of the seven scenarios**: `POST /rag` (`server.py:200`) serves `corpus="docs"` and `corpus="code"` from one endpoint (`:193`), and there is **no agent route, no data route, and no approval decision route** on `server.py` at all, so scenarios 3–7 are reachable as *library calls* (`run_agent`, `executor.run_plan`, `run_saleor_sql`) and not as HTTP. *the evaluation* — **present and layered**: Day 20's `tools/eval_harness.py --fixtures` (V1–V9), Day 21's `tools/bench_rag.py --fixtures` (R1–R9), Day 22's `tools/bench_agent.py --fixtures` (AB1–AB9), all `MECH`, all 0 chats. *the trace* — **present, per-process, capped**: `GET /traces/{trace_id}` (`server.py:171`) fetches a record from a store capped at 256 (`observability.py:714`), and `GET /traces` (`server.py:180`) counts them. *the ledger* — **present, per-process**: `GET /ledger` (`server.py:185`) summarizes a list in the process (`ledger.py:65`). *the approval workflow* — **designed, not built** (Day 27). *the deployment* — **built yesterday**: a 587 MB image, `/healthz` and `/readyz`, a single-writer lock (Day 29). That is the surface the demonstration has, and the day names it before it runs a single scenario.
- [ ] Answer the hard question first, before any file is written: **what is the deliverable, and what makes it worth a day?** Three candidates. (a) *Write a demo script that prints pretty answers.* Verdict: **rejected** — a demo that scripts around the two unanswerable scenarios is the brochure the series has refused since Day 7. (b) *Run the seven scenarios live and report the numbers.* Verdict: **necessary and insufficient** — a live run costs money, is unrepeatable, and produces a screenshot rather than an artifact a reader can check. (c) **Make the demonstration falsifiable**: a scenario registry with pre-registered expectations, a runner whose every cell is a fixture id or a named `PENDING`, a scorecard joining the seven scenarios to the existing harnesses, and a control proving the runner is passive. Verdict: **chosen** — and it is the only one of the three that survives contact with a reader who did not build the system, which is the test the whole day exists to meet.
- [ ] Pre-commit the day's split before any build. **`MECH`:** the scenario registry and its ten columns; the runner's offline path (0 chats); the trace eviction count under seven scenarios; the store-cache refusal for a third corpus; the per-scenario tool sequence and evidence set; the `cited ⊆ retrieved` / `asserted ⊆ returned` / `conclusion ⊆ evidence` / `recalled ⊆ authored` checks on each scenario that recalls; the two `PENDING` scenarios' *absence* asserted as a finding; the scorecard's joins to V/R/AB/O/D; the host/image parity; and the runner-off equivalence. **Not `MECH`:** whether the seven scenarios are the seven a real user would ask; whether the stub's answers would match a real model's; whether a demo is a substitute for a load test; whether the operational scenario's "why" is answerable without a metric baseline; and every claim about *quality* — the semantic cells stay `PENDING` with owners, exactly as they have since Day 20.
- [ ] Pre-commit nine invariants: **(a) a scenario is a fixture** — every scenario has pre-registered expectations, and a scenario with none is not in the registry; **(b) a cell is a fixture id or a named `PENDING`** — a cell that is neither is refused, so the register cannot acquire a blank; **(c) the runner is passive** — offline it is 0 chats, 0 embeds, 0 SQL, 0 rows, and every prior fixture is unchanged with it on and off; **(d) the negative twin is a column** — every scenario's *failure cases* names the refusal the system must produce, and the fixture asserts it; **(e) absence is a finding** — scenarios 5 and 7 assert what is *missing* (no test-runner tool; no write path) rather than scripting a stand-in; **(f) the demonstration is one process, and the process is a fact** — the trace cap, the store cache, the shared gateway, and the per-process ledger are measured as integration findings, not hidden; **(g) evidence is the same invariant in every scenario** — `cited ⊆ retrieved` for 1/2, `asserted ⊆ returned` for 3, `conclusion ⊆ evidence` for 4, `recalled ⊆ authored` for 4's memory, and the *same* check runs in the demo as in the day suite; **(h) the cost is a column and the offline cost is zero** — the demo's headline is that a complete demonstration costs nothing without a key; **(i) the control is the deliverable** — Z9 asserts host ≡ image and runner-off ≡ unchanged, the two things that make the artifact a property of the system rather than of the laptop.
- [ ] Name the negatives with owners, carried from Days 25–29 and closed or re-owned today: **the decision route** and **the authenticated surface** stay `PENDING` (Day 29's deployment never added auth, so scenario 7's decision is a CLI act — owner: the day identity lands); **the write path** stays `PENDING` with **no owner, deliberately** (Day 27's judgment, unchanged: the first write destroys `Wrote? = no`); **the test-runner tool** is a new `PENDING` with a genuine owner — it is the first capability the curriculum has asked for that the repository has never designed, and the day names it rather than folding it into scenario 2; **the trace sink, retention, and the metric baseline** stay `PENDING` (there is no sink, so "why did latency increase" is answerable for *one request* and not across a window — owner: the storage decision Day 28 refused to make for a sink that does not exist); **the semantic evaluation lanes** (citation support in meaning, groundedness beyond membership) stay `PENDING` from Day 20/21; and **the seven scenarios' real-model behavior** stays `PENDING` — the stub scripts what the fixture says, so a green scenario proves the *path*, not the model, and the day says so in every row.

### 2. Learn: Integration Is the Discovery of Shared State (45 min)

- [ ] Learn **what integration actually tests**, because the word is used to mean "run everything" and that is the least useful reading. An integration test asks a question a unit fixture structurally cannot: *when two modules that each passed alone are placed in one address space under one clock, which of their assumptions about the world stop being true?* This repository is a nearly perfect specimen of the problem, because twenty-nine days built modules that are each **carefully bounded and each bounded by a different world**: `tools/trace_smoke.py` builds a trace store and never fills it; `tools/state_smoke.py` builds a store file and never shares it; `tools/bench_agent.py` builds a `BenchGateway` that answers by script and never touches the real gateway's `last_*` fields; `server.py` builds **one** gateway at import (`server.py:35`) and every route reads the same global. So the integration question is not "do the pieces work" — thirty days of fixtures say yes — it is **"which of the seventeen worlds was each piece written for, and which of those worlds does the demonstration have only one of."**
- [ ] Learn the **four shared resources** the demonstration has exactly one of, and measure what each one does under seven scenarios, because the list is the day's §7 and each entry is a file:line rather than a worry. **(1) the trace store** — one `OrderedDict` capped at 256 (`observability.py:706–716`, cap `:714`), so seven scenarios with a handful of spans each fit, but the *retention* question arrives the moment a scenario wants to look at an earlier scenario's trace; the demo records `evicted_count` and refuses to claim a trace survives a run it did not. **(2) the store cache** — keyed on `sha256(file) + embedding_model + dimension`, holding one store per corpus (Day 28), so the demo holds the docs store and the code store and a **third is refused by name** rather than evicted, because an LRU would make "which store answered" a question about timing. **(3) the state store** — one file, whose `get()` rewrites it (`state.py:607`) and whose `put` rewrites the whole file from memory (`state.py:838–845`, tmp at `:843`, `os.replace` at `:845`) with no lock, so scenario 4's memory and scenario 3's checkpoint are two consumers of one file and the demo must serialize them, not interleave them. **(4) the gateway and its ledger** — one shared global with mutable `last_*` fields (`gateway.py:80–82`) and one per-process ledger list (`ledger.py:65`), so the demo's latency column reads `gateway.last_latency_ms` **immediately after its own call** and the cost column sums the ledger's *delta* across the scenario, never the total — Day 28's shared-global trap, arriving at its first real consumer.
- [ ] Learn **why "it ran end-to-end" is not a control**, and state the failure it prevents. A runner that executes seven scenarios and prints seven answers has proven that seven code paths did not raise; it has not proven that the *system* is the same system it was before, and it has not proven that any specific answer is correct. The repository already knows this: Day 20's V9, Day 21's R9, Day 22's AB9, Day 23's O9, and every day's off-switch exist because *a feature that changes a legitimate answer is a bug wearing a feature's clothes.* So the demonstration's control is not "the demo ran" — it is **Z9: with the runner off, every prior fixture is byte-identical, and with the runner on, every prior fixture is still byte-identical**, because the demo is a *reader* of the system and not a modifier of it. The concrete claim: the runner is 0 chats, 0 embeds, 0 SQL, 0 rows offline; it adds no tool, no route, no span kind, and no store; and the only thing it changes is the trace store's contents, which is the one resource whose *consumption* is the thing under test.
- [ ] Learn **the five integration findings this repository can already predict from the code**, because a demonstration that only discovers them by running is a demonstration nobody can check, and the day's whole method is that the prediction is written *before* the run. (a) **The trace cap is invisible until it isn't**: seven scenarios each open a root (`server.py:103`, `:145`, `:224`) and the store holds 256, so the cap does not bind in a small demo and *will* bind in a rerun loop — the honest report prints the count and states the boundary rather than implying retention. (b) **The store cache turns a per-request parse into a per-process cost** (Day 28): scenario 1 and scenario 2 both call `_rag_store()` (`server.py:192–197`), which is exactly one parse per corpus per process and zero thereafter, so the demo's latency column shows scenario 2 *faster* than scenario 1 for a reason that is not the question's difficulty — and a reader who is not told that reads the number as a quality signal. (c) **The recall pre-step is measurable for the first time end-to-end** (Day 18): scenario 4 over a store that scenario 4 already indexed is the demonstration's one place where `recall()` (0 chats) competes with a fresh investigation (≥1 chat), which is the "only if useful" meter arriving at its first honest consumer. (d) **The data seam substitutes silently** (`data.py:798–806`): scenario 3 with `SALEOR_READONLY_DB_URL` unset answers from `SEED_SQL` (`data.py:455–458`), so the demo must *print which backend answered* or its most confident number is its least trustworthy. (e) **The two unanswerable scenarios are unanswerable in a way a fixture can assert**: scenario 5's missing tool is enumerable (`registry.names()` has seven entries and none runs tests) and scenario 7's missing write path is enumerable (`policy.yaml`'s `statement_allow` is `[select, with]` and no grant declares `effect: write`), so "we cannot demonstrate this" becomes a *checked* claim rather than an apology.
- [ ] Learn **what the demonstration must not do**, with the same seriousness as Day 27's list of what an approval must not be. It must not **script an answer the system cannot produce** — a stubbed "test failure explanation" for scenario 5 is the Day-7 padding mistake wearing a demo's clothes. It must not **read the shared global after another scenario ran** — `gateway.last_provider` is the last call in the process, not this scenario's call (`gateway.py:80–82`). It must not **claim retention the store does not have** — a trace shown in a demo is not a trace kept (`observability.py:714`). It must not **aggregate across scenarios as if they were one run** — the ledger is per-process (`ledger.py:65`) and the scenarios are separate questions; and it must not **call a live model to make the demo impressive**, because the demonstration's cost claim is that the whole thing is reproducible at **0 chats, 0 embeds, 0 SQL, 0 rows** and `--live` is a labelled add-on, not the mode.

### 3. Learn: A Scenario Is a Fixture — the Ten Columns, Pre-Registered (45 min)

- [ ] Learn **why the curriculum's ten columns are a fixture format and not a report template**, because that is the day's central design move. Read as a report, the columns are a checklist a demo fills in afterwards — and a checklist filled in afterwards is a description of what happened, which is exactly the artifact Day 20 replaced with a pre-registered one. Read as a fixture, the columns are **ten expectations written before the run**, and each one has a failure mode: *input* (the question, hashed), *reasoning/workflow* (the path — a plan with step ids, or a single call), *retrieval* (the evidence set with ids and scores), *tools* (the sequence, in order), *evidence* (the invariant — `cited ⊆ retrieved` and its three translations), *output* (the answer, with citations), *latency* (a measured number, with the shared-global caveat), *cost* (the ledger delta, with the units), *evaluation score* (the layer-1 deterministic verdict, with the owner of every `PENDING` semantic cell), and *failure cases* (the negative twin and the refusal it produces). A column with no expectation is a column the harness refuses, which is the same ratchet as Day 28's claim↔fixture bijection: **an unfalsifiable cell cannot enter the record, and an unclaimed fixture cannot hide in the harness.**
- [ ] Learn **the one invariant that every scenario shares**, because it is the thread that makes the seven scenarios one system rather than seven demos. Days 6, 14, 16, 17, 18, and 19 each translated the same sentence — *the answer may assert only what the evidence supports* — into their own vocabulary: `cited ⊆ retrieved` (retrieval), `asserted ⊆ returned` (data), `conclusion ⊆ evidence` (planning), `recalled ⊆ authored` (state/memory), `delegated ⊆ returned` (hand-off). The demonstration's contribution to the series is to **run all five on one artifact and show they are the same check**: scenario 1 and 2 assert `cited ⊆ retrieved` over the store; scenario 3 asserts `asserted ⊆ returned` over the result set; scenario 4 asserts `conclusion ⊆ evidence` over the transcript *and* `recalled ⊆ authored` over the memory it recalled; scenario 7 asserts that the answer names the request id and asserts `applied: false`. A scenario whose output fails its invariant is `FAIL`, and the demo's headline is that the *fabricated twins* — the ones the day suites built specifically to fail — still fail, which is the proof that the demonstration is grading the system and not congratulating it.
- [ ] Learn **how a scenario maps to an HTTP route, a library call, or a refusal**, because the mapping is the honest answer to "can a user do this?" and the repository's answer is uncomfortable and specific. Scenario 1 and 2 are **HTTP**: `POST /rag` with `corpus="docs"`/`"code"` (`server.py:200`, `:193`). Scenario 3, 4, and 7 are **library calls**: there is no `/agent`, no `/sql`, no `/approvals` route — `server.py` exposes exactly `/health`, `/chat`, `/chat/stream`, `/traces/{id}`, `/traces`, `/ledger`, `/rag`, `/metrics`, `/logs`, `/ingest/span` (Day 29's `/healthz` and `/readyz` are additive), and **the absence of an agent route is not an oversight** — it is the standing consequence of Day 26's finding that there is no authentication, so the day records the route gap per scenario rather than adding seven unprotected endpoints to make a demo easier. Scenario 6 is **an HTTP read of an already-built record**: `GET /traces/{id}` (`server.py:171`).
- [ ] Learn **what "evaluation score" means here and what it does not**, because the column is the one most likely to be flattered. The score is Day 20's **layer-1 deterministic verdict** — a set of membership and arithmetic checks, each naming one owner: `expected ⊆ retrieved`, `cited ⊆ retrieved`, `conclusion ⊆ evidence`, `tool == expected_tools`, `must_not`, `refusal == expected`, `failure == category`, cost, latency. It is **not** a quality number, and the day refuses to invent one: layer 2 (semantic) and layer 3 (LLM-as-judge, off by default) stay exactly where Days 20–22 left them, and a scenario whose only failing cell is semantic is `pending` with an owner, never `pass`. The pipeline is the point: **the demo reports the same verdicts the gate reports**, joined by scenario id, which is what makes the scorecard a *join* rather than a second opinion.
- [ ] Learn **the cost column's two currencies**, because a demonstration that reports only one is reporting the half it controls. **Machine cost** is the ledger delta: scenario 1 and 2 are 1 embed + 1 chat each on a real run and **0 chats, 0 embeds** offline; scenario 3 is **0 embeds + 2 chats** (generate, explain; +1 on a repair); scenario 4 is the plan's chats plus its steps' chats and embeds; scenario 6 is **0 chats, 0 embeds** (it reads a trace); scenario 7 is **0 chats** and one state-store write per transition. **Human cost** — the only one Day 27 introduced — is unbounded and unmeasured: scenario 7's decision waits on a person, the series has no instrument for it, and the report says so rather than reporting a latency it cannot have measured.

- [ ] Learn **what scenario 5 actually exposes**, because it is the day's most useful negative and the one a demo is most tempted to fake. *Why is this test failing?* is a question about a **failing artifact** — a test run, a stack trace, a CI log, a commit — and the repository has none of those as inputs. What it has is `corpus_code/` (Saleor source, ingested as symbols by `ai_os/ingest_code.py`), so the *closest honest answer* is "here is the symbol that a checkout test would exercise," which is scenario 2 with a different question shape. The day therefore does not rename scenario 5 into scenario 2; it records the missing capability precisely — **a `run_tests` / `read_ci_log` tool does not exist, no tool returns a test result, and neither corpus contains a test outcome** — and gives it an owner (a future day's ingestion seam, plus a *sandboxing* decision the series has never had to make, because running tests means executing untrusted code, which is a categorically different authority from every tool built so far). That last clause is the real finding: scenario 5 is not a missing tool, it is the first request in thirty days to ask the system to **execute something**, and the permission model that would gate it does not exist.
- [ ] Learn **what scenario 6 can and cannot answer**, because "why did latency increase" contains an aggregate the system cannot produce. The mechanism is real and tested: Day 23 built one request's causal span tree and Day 24 propagated it across a boundary, with `model.<op>.attempt` spans, `ttft_ms`, ledger-linked cost, and the `client`/`server` distinction. So the demo **can** answer *"this request was slow, and here is where the time went"* — the root duration, the per-hop attribution, the retry that fell back, the store parse, the DB wait. It **cannot** answer *"latency increased"*, because that is a claim about a **window** and this system has no window: the trace store is per-process and capped (`observability.py:714`), `/metrics` is a snapshot of counters and fixed-bucket histograms (`server.py:249`, Day 24), there is no sink, no retention, and no baseline. The day's honest handling is to answer the answerable half, and to state the unanswerable half as the *reason* the operational scenario is `PARTIAL` — and to note the one thing a demo can still do: run scenario 1 twice, once cold and once warm, and show the store-cache delta (Day 28) as the only "latency changed" fact the system can prove about itself.
- [ ] Learn **why scenarios 1, 2, and 3 are the demonstration's floor and not its ceiling**, because the temptation is to demo the impressive one (scenario 4) and treat the simple ones as warm-up. The opposite is true. Scenarios 1–3 are the three that run through **real request paths** (`POST /rag`) or a **real seam** (`run_saleor_sql`) and satisfy the series' oldest invariant in three vocabularies, so they are the three whose green cells are cheapest to trust and whose `PENDING` cells are sharpest (`cited ⊆ retrieved` holds while the *retrieval* misses — Day 21's finding — which is exactly the distinction the demo must keep). Scenario 4 is the impressive one and the *least* trustworthy, because it is a stored plan driven by a scripted gateway: it demonstrates that the executor composes steps and that `conclusion ⊆ evidence` holds, and it demonstrates nothing about whether a real model would choose those steps — which is Day 21/22's benchmark, not Day 30's demo.
- [ ] Learn **the demonstration's single headline, and get it right**: not *"the system answers seven questions"* but **"seven scenarios, ten columns each, N cells traced to a fixture, M cells `PENDING` with owners, and 0 cells unaccounted for."** The number the day is proudest of is the **last** one, because it is the one a demonstration normally hides: a demo that reports 70 filled cells and no names is a demo whose blanks are invisible, and the ratchet's whole purpose is that an empty cell is louder than a wrong one.

### 5. Design: The Scenario Registry, the Ten-Column Record, and the Refusal Register (30 min)

- [ ] Design the record before touching the harness, because the registry *is* the demonstration and the runner is its rendering:
    ```yaml
    # ai_os/scenarios.yaml — Day 30's addition. A SCENARIO is a question with
    #   ten pre-registered columns. A column with no expectation is refused:
    #   * `expect` is written before the run (the series' rule since Day 7).
    #   * `pending` is a first-class cell. A demo that lists only what it proved
    #     is a brochure; a demo that names what it could not prove is a defence.
    version: 1
    scenarios:
      - id: S1
        name: knowledge
        question: "How does Saleor handle checkout?"
        route: {kind: http, method: POST, path: /rag, body: {corpus: docs}}
        expect:
          tools: [search_saleor_docs]
          invariant: cited_subset_retrieved
          refusal_on: ["unrelated question", "empty corpus"]
        cost: {embeds: 1, chats: 1, sql: 0, rows: 0}
      - id: S4
        name: customer_investigation
        question: "Why did this customer fail to complete checkout?"
        route: {kind: library, call: run_agent, plan: stored}
        expect:
          tools: [search_saleor_code, run_saleor_sql, search_saleor_docs]
          invariant: [conclusion_subset_evidence, recalled_subset_authored]
          refusal_on: ["fabricated cause"]
        cost: {embeds: "per_step", chats: "per_step + 1", sql: 1, rows: 1, writes: 2}
        pending: ["real-model plan quality (day21)", "semantic answer quality (day20 L2)"]
      - id: S5
        name: engineering_investigation
        question: "Why is this test failing?"
        route: {kind: none}
        expect: {tools: [], invariant: null}
        finding: "no test-runner tool exists; registry.names() has 7 reads, 0 executors"
        pending: ["a run_tests tool (owner: a future ingestion+sandbox day)"]
      # S2 code · S3 data · S6 operational · S7 controlled_action: same shape
    ```
  - [ ] Design decision #1 — **the registry is a file, and the record is checked against it**, because Day 28's ratchet was "every box is a file" and Day 29's was "an image is a subset with a manifest," and today's is the same idea at the demonstration level: `tools/demo_smoke.py` parses `ai_os/scenarios.yaml`, resolves every scenario's route against the code (an HTTP route exists in `server.py`; a library call exists in `ai_os/`), and asserts **both directions** — every scenario in the registry ran, and every cell in every scenario's record is either a fixture id or a `pending` entry. A registry with a phantom scenario and a record with an unaccounted cell are the same defect from opposite ends, and the second one is the brochure.
- [ ] Design decision #2 — **the runner is a reader, not a router**, in the same register as `tools/eval_harness.py` (Day 20's "a router, not a grader"). `tools/demonstrate.py` presents each scenario's question to *production* exactly as a user would (offline stub by default, `--live` for the real gateway) and collects `{scenario, trace, ledger_delta, run}` **without touching answer-path code**. The one thing it owns that a day suite does not is the **integration context**: it creates *one* gateway, *one* state store, *one* trace store, and *one* store cache for the whole run, and records the four shared-resource events (trace eviction, cache hit/miss, state write, ledger delta) as *findings* rather than as fixtures passing. Rejected: a per-scenario fresh process — it would make every scenario look like its day suite and would delete the integration question the day exists to ask.
- [ ] Design decision #3 — **the scorecard is a join, not a second opinion**. `tools/demo_smoke.py` maps each scenario to the harness that already grades it — S1/S2 → `tools/bench_rag.py` (R1–R9) and the retrieval families (`retrieval_day10.py --stub`); S3 → `tools/data_smoke.py` (Q1–Q8) and `tools/sql_attack_smoke.py` (X1–X11); S4 → `tools/plan_smoke.py` (P1–P9) and `tools/bench_agent.py` (AB1–AB9); S6 → `tools/trace_smoke.py` (O1–O9) and `tools/distributed_smoke.py` (D1–D9); S1–S4 → `tools/eval_harness.py --stub` (the 18 golden rows) — and prints, per scenario, *the demo's verdict* beside *the existing harness's verdict*. A disagreement is a **gate bug to fix, not a demo to adjust**, which is Day 19's rule (`the fixture is never weakened`) arriving at the demonstration. Rejected: a new grader — the day adds no metric, no judge, and no semantic lane, because a demonstration that grades itself with a ruler it built is measuring its own consistency.
- [ ] Design decision #4 — **the two unanswerable scenarios are fixtures that assert absence**, and this is the day's most careful design. S5's fixture enumerates the registry (`registry.names()` → seven tools, none of which runs a test), asserts that neither corpus contains a test outcome, and asserts that **no code path in `ai_os/` executes a shell command or a subprocess** — a *checked* absence, so the `PENDING` is a finding rather than an apology. S7's fixture asserts the same shape against the write path: `policy.yaml`'s `statement_allow` is `[select, with]`, no grant in the permission file declares `effect: write`, both stores expose one query method and no mutation, and the Postgres session is `default_transaction_read_only`. Both fixtures print their evidence, because "we cannot demonstrate this, and here is the enumeration that proves it" is the strongest possible cell in the register.
- [ ] Design decision #5 — **the demonstration runs twice: on the host and in Day 29's image**, and this is the day's inheritance from yesterday rather than a new invention. Day 29's N9 asserted host/container parity for the offline N-set; Day 30 extends it to the seven scenarios, so the demonstration is a property of the **artifact** and not of the laptop. The image has no `.env` (`Day 29`), so on a fresh `docker run` the `gateway` is `None` (`server.py:38`) and S1–S4 are the **stub** scenarios — which is the correct and expected result, not a failure, and the report says so verbatim in the same table as the pass.
- [ ] Design decision #6 — **the documents are three, and the register is the deliverable**. `docs/demonstration.md` is the artifact a reader who did not build the system opens first: the seven scenario records with ten columns each, the scorecard, the integration findings, the defense transcript, and the residual register with owners. `docs/evaluations/integration-day30.md` is the report: the Z1–Z9 table, the four shared-resource findings, the host/image parity, the cost shape, and every `PENDING` line. `docs/concepts/integration.md` is the concept doc, joining the **eighteen** already in `docs/concepts/`. All three keep the same three lines visible — **what exists, what does not, and who owns each absence** — because that is the sentence the whole series has been converging on and Day 30 is where it gets its final form.

### 6. Build: The Scenario Runner — `tools/demonstrate.py` (1 hour 5 min)

- [ ] Add `tools/demonstrate.py`, in the same register as every harness in `tools/` — a decision, written down, with the reasons in comments — and deliberately *not* a framework. One file, one entry point, two modes: **offline (the default)** builds the stub gateway (`tools/mock_gateway.py`) and the stub stores and runs all seven scenarios for **0 chats, 0 embeds, 0 SQL, 0 rows**; **`--live`** swaps only the *chat wire* for the real gateway from `.env` (retrieval stays on whatever store it is given, exactly as `tools/agent_smoke.py --live` does), labels the run `live`, and reports the real bill. A provider outage prints `[SKIP]` and exits non-zero rather than reporting a false `FAIL`, because a demo that fails on a quota is a demo that lies about the system.
- [ ] Build the **integration context** and make it visible, because it is the day's one genuinely new mechanism: `DemoContext` constructs **one** gateway, **one** `StateStore`, **one** `TraceStore`, and **one** store cache, and exposes `evicted(trace_id)`, `cache_stats()`, `state_writes()`, `ledger_delta(since)`. Each is a *reader* over an existing object (`obs.default_store()`, `gateway.ledger`, the store's own counters) and adds no field to production code — the demo measures the shared resources from the outside, so the system it measures is unmodified. The one addition is a **call-ordering discipline**: a scenario reads `gateway.last_*` *inside its own call window* and the context rejects a read that happens after the next scenario has started, which is Day 28's shared-global trap turned into an assertion rather than a comment.
- [ ] Implement the **ten-column record** as a dataclass with ten required fields and one optional (`pending: list[str]`), and make an empty required field a `ValueError` naming the scenario and the column. The rule is the whole point: **a scenario with an unfilled required cell does not render**, so the registry cannot quietly lose a column and the runner cannot print a partial record. The `pending` list is where every unprovable cell goes, with an owner string, and `Z8` asserts that every scenario's `pending` entries are non-empty *only* where the day claims a limitation — so a scenario that could be fully proven and is not fails the fixture.
- [ ] Implement the seven scenario functions, each of which is a **thin driver over an existing seam and nothing more**: `s1_knowledge` → `POST /rag` `corpus=docs` (or `run_rag` in-process); `s2_code` → `corpus=code`; `s3_data` → `run_agent` with the data tool (the pipeline *is* the loop, Day 14); `s4_customer` → `executor.run_plan` over a stored plan (Day 16) with the memory pre-step on (Day 18); `s5_engineering` → the absence fixture; `s6_operational` → `obs.default_store().get(trace_id)` + the ledger reconciliation (Day 23/24); `s7_controlled` → the Day 27 decision path *or* the absence fixture while Day 27 is unbuilt. No scenario re-implements a check: `cited ⊆ retrieved`, `asserted ⊆ returned`, `conclusion ⊆ evidence`, and `recalled ⊆ authored` are called from `ai_os/trace.py`'s existing functions (`grounding_over_transcript`, `recalled_subset_authored`, …), so a demonstration that disagrees with a day suite is a demonstration that re-typed the invariant and got it wrong.
- [ ] Keep it offline, deterministic, and free: the stub gateway (`tools/mock_gateway.py`) answers by script on `:8700`/`:8701`, the stub stores are embedded offline, the state store is a temp file, the trace store is the process's own, and the clock is injectable so latency is a *fact* and not a wait. There is **no `time.sleep` on the offline path** and **no model call anywhere on it** — the same requirement as Days 27–29, and the reason the day's cost line is **0 chats, 0 embeds, 0 SQL, 0 rows** for the runner, the registry, the scorecard, and the checkers combined.

### 7. Build: The Integration Seam — What Only Breaks When All Seven Run at Once (1 hour 5 min)

- [ ] Measure the **trace store under seven scenarios**, and print the number rather than implying retention: seven roots (`server.py:103`, `:145`, `:224`, plus the library-call scenarios' own roots) land in a store capped at 256 (`observability.py:706–716`, cap `:714`), so the demo reports `traces_held`, `evicted_count`, and — the honest row — **whether scenario 1's trace is still fetchable after scenario 6 ran**. The finding is not that the cap is wrong; it is that **a demonstration is a *consumer* of a bounded resource**, and the demo is the first artifact that has to say whether it can look backwards. The day records the boundary (`retention = process lifetime`) and refuses to claim the demo is an observability tool.
- [ ] Measure the **store cache** as the integration's clearest win and its clearest trap. `_rag_store()` (`server.py:192–197`) calls `RagStore.load(path)` on every call, and Day 28's cached `load_store_cached` (keyed on `sha256(file) + embedding_model + dimension`) turns it into one parse per corpus per process. The demo records `cache: {docs: miss→hit, code: miss→hit}` and prints scenario 2's latency *with the reason* — a warm store, not an easy question — and asserts that a **third corpus is refused by name** rather than evicting the first, because "which store answered" must never become a question about timing.
- [ ] Measure the **state store as one file with two consumers**, and make the demonstration serialize them. Scenario 4's checkpoints (`executor.run_plan` flushes task state, Day 17) and scenario 4's memory index (`episodicize` at run-end, Day 18) write the *same* file, whose `put` rewrites it from memory (`state.py:838–845`) and whose `get()` rewrites it too (`state.py:607`). The demo therefore runs scenario 4's writes **in one thread in one order** and records `state_writes` — and states the finding Day 28 predicted and Day 29 enclosed: **the file is safe for exactly one writer, the lock from Day 29 is what makes the demo's single-process assumption true rather than lucky, and the demo names the day the assumption would break.**
- [ ] Measure the **ledger and the shared global** as the columns a demonstration most easily flatters. The cost column is the ledger's **delta** across the scenario (`ledger_delta(since)`), never the total (`ledger.py:65` is a per-process list), and the latency column reads `gateway.last_latency_ms` (`gateway.py:80–82`) **inside the scenario's call window** — the context rejects a read after the next scenario begins. The honesty note goes in the report: **the demo's latency column measures one call in a shared process and is not a benchmark**, and the shared `last_*` fields are the reason (Day 28's trap), which is why the day reports the *median of the scenario's own calls* rather than a single post-hoc read.
- [ ] Measure the **first honest end-to-end recall**, because scenario 4 over a store it has already indexed is the one place in thirty days where Day 18's "only if useful" meter is measurable at the system level: `recall()` costs **0 chats, 0 embeds** (Day 8/9's scorer over stored signatures) and a fresh investigation costs **≥1 chat**, so the demo prints the two and the delta. The finding is modest and stated as such: on a stub, recall *serves an episode*, which is what Day 18 proved; what the demonstration adds is that the **comparison can now be made inside one request path** rather than between two day suites, and that the answer to "is it useful" is still a real-model question (`PENDING`, Day 21).
- [ ] Name the **integration findings the run did not produce** — the ones the day predicted from the code and did not observe, because a demonstration that reports only what it saw is hiding the half of the method that is prediction. Three: (a) the **two-writer corruption** Day 28 predicted and Day 29 measured is *not* reachable in the demo, because the demo is one process and Day 29's lock refuses a second — so the demo records the prediction, the guard, and the fact that the demo cannot exercise it, and does not claim the corruption is gone. (b) The **`$0.00` failure cost** (`ledger.py:99` — `cost_usd=self.cost(...) if ok else 0.0`) is invisible offline (no failures) and real live, so the demo records it as a Day 28 finding *confirmed by reading* rather than claimed by measuring. (c) The **database substitution** (`data.py:798–806`) is invisible on the stub *by construction*, so scenario 3's backend label (`stub (SEED_SQL)` vs `postgres`) is the cell that matters, and the demo asserts the **label**, not the backend choice — the same discipline as Day 29's readiness probe.
