# Day 26 Notes — Agent Security

> Notes answering `docs/day-plan/day-26.md`.
> Twenty-five days built a machine that reads (Days 6–10), acts (11–12), fails honestly (13), computes (14–15), plans (16), remembers (17–18), splits into specialists (19), learns how it will be judged (20–22), explains one request from the inside (23) and across its boundaries (24), and yesterday learned to be attacked (25). Every one of those days added **authority**, and yesterday's finding was that authority held by a component which reads untrusted text belongs to a confused deputy — so a defense must live somewhere the model cannot edit. The curriculum now supplies the mechanism: `Agent → Policy → Permission check → Tool`, with **read-only by default, explicit tool permissions, input validation, output validation, audit logs**, and the deliverable **basic agent security layer.** The starting surface is not hypothetical and it is not flattering: `policy.yaml` governs generated *statements*; `validate_args` enforces a ten-line JSON-Schema subset with **no `maxLength` and no `pattern`**; `ToolRegistry.scope()` denies out-of-role tools but knows nothing about principals; `DataAgent.get_product` / `get_order` / `get_customer` call `self.store.query(...)` **directly**, so `SafeSql.inspect` never sees them and `_literal()`'s hand-rolled quote-escaping is the only thing between an `id` argument and SQL text; `get_customer` returns `u.email`, a column `columns_deny` never names; **nothing anywhere validates what a tool returns**; `run_agent` already accepts a `principal` that authorizes nothing; and `server.py` has no agent route, no identity, and no audit surface. The one piece of structural luck: all five paths to a tool — the loop, `run_tool_answer`, `executor.run_plan`, the fallback ladder, and Day 19's `RoleAgent.run` — pass through `registry.validate_args` + `registry.execute`, so **one** seam can hold the entire boundary. Today's finding is not that permissions are hard. It is that **the boundaries this repo had were real, scattered, and each attached to a different reason** — and a boundary that exists only because its author remembered to write it is a boundary that a new tool, a new call site, or a new agent walks straight through.
> The single idea: **a threat model is a list of worries and a permission system is a decision procedure** — one that runs on every call and every result, defaults to deny, names its refusal, and leaves a record of the decisions it made *including the ones that said yes*. Mechanism stays `MECH`: grant resolution, deny-by-default, the single choke point, the registration-time grant requirement, `maxLength`/`pattern` enforcement, the result contract (declared columns, denied-column intersection, row cap, retrieval contract), no-partial-rows on a result failure, the audit entry shape, the hash chain and its verification, the entry-volume bound, and the on/off equivalence. Correspondence to reality does not: nobody has told us who may read a customer's email, the `principal` is a string the caller supplies, and whether a real model ever attempts an escalation is a question no fixture can answer. The day's architecture is four moves, and the order is the security argument — **declaration** (every tool says what it is: effect `read`/`write`/`none`, data class `public`/`internal`/`pii`; no grant, no registration) → **deny by default** (an unknown principal gets the strictest set, a missing grant is a denial, and `execute()` with no decision supplied denies, so a *future* call site is safe by omission) → **one choke point** in the tool surface, carrying the decision from validation into execution so no caller can skip it → **validation at both ends**, because input validation exists and output validation does not, and `columns_deny` is currently a description of a class of *statement* in a system that also emits *results*. Three rules make the day specific to this repo: **exactly one check per argument** — a shape check or a semantic check, never both (two checks on one argument is how a policy ends up disagreeing with itself) and never neither; **no partial rows** — a permission failure at the result boundary keeps the shape and drops every value, because a partial answer is how a leak becomes untraceable; and **the audit log records a decision, not a person** — it is tamper-evident for edits, reorders, and interior deletions, and explicitly *not* tamper-proof against truncation of the tail, because nothing inside the process can notice a file that simply ends. And C9 keeps the control: the layer is passive. On or off, a legitimate request is byte-identical, at **0 chats, 0 embeds, 0 SQL, 0 rows**, and the only behavioral differences appear on traffic that should have been denied — which is the entire point.
>
> **The one line the day would die defending: a boundary in the caller is a boundary the next caller forgets, so the boundary belongs in the tool, the default is deny, and a permission system that leaves no record is a rumour — which is also why "read-only" is not a claim this repo gets to make until somebody says who is asking.**

## 1. The Loaded Question — "Build Permission Boundaries"

The objective is four words and a diagram, and the diagram is the day's real content:

```text
Agent  →  Policy  →  Permission check  →  Tool
```

A check now sits between the wanting and the doing. That is the whole curriculum sentence, and the easy version of the day is to read it as "add an allow-list of tool names and call it done" — which is Day 19's `ToolRegistry.scope()` with the role names replaced by config keys. It is worth being precise about why that version is not the day, because the reason generalizes to everything after today.

**A threat model is a list of worries. A permission system is a decision procedure.** Day 25 produced a good list: actors, entry points, authority, the controlling layer, the residual risk. It is genuinely the most useful document in the repository. And nobody consults it at three in the morning when somebody registers a new tool, when a planner emits a step the loop did not anticipate, or when a result comes back with a column nobody expected. A list is read once by the people who wrote it. A decision procedure is consulted on **every** call, by code, and it returns a verdict with a name attached — `no_grant`, `unknown_principal`, `result_violation` — that a human can later grep for. The difference between the two artifacts is not thoroughness. It is *when it is consulted*.

So the day is not "add rules." It is **"add the one place a rule must be true, and make everything else inherit it."**

This repository is unusually well placed for that, and it took twenty-five days to become well placed without anyone planning it. Here is the honest inventory, with the distinction the day actually turns on — a **check** can say no, a **declaration** says what something is, a **privilege** is the world saying no regardless of our config:

| What exists | File / function | Kind | What it does not do |
|---|---|---|---|
| `statement_allow`, `tables_allow`, `columns_deny`, `definitions`, `row_limit`, `max_cost`, timeouts | `policy.yaml` → `sql_safety.Policy` | policy | applies to **statements only**; the fixed resolvers never call `SafeSql.inspect` |
| `normalize → parse → policy → cost` | `sql_safety.SafeSql.inspect` | check | knows nothing about who is calling |
| type / enum / minimum / maximum / required | `tools.validate_args` | check (input, shape) | no `maxLength`, no `pattern`, no output side at all |
| out-of-role denial, `role_violation` | `tools.ToolRegistry.scope`, `ERROR_ROLE` | check (role only) | roles are not principals; three names, not a grant model |
| `AUTHORED_SOURCES` + `_check_provenance` | `state.StateStore` | check (writes only) | nothing about reads, tools, or results |
| `tool_timeout_s`, `max_steps`, `budget_usd`, `detect_repeat`/`detect_oscillation` | `agent.execute_bounded`, `run_agent` | resource wall | bounds blast radius; decides nothing about authority |
| `saleor_read_only` role, `default_transaction_read_only` | `data.PostgresDataStore`, `replica_user.sql` | privilege | unavailable offline — `SqliteDataStore` has no such role |
| the tool's own effect, data class, declared columns, caps | — | declaration | **does not exist** |
| who may call what, with what arguments, keeping what columns | — | decision procedure | **does not exist** |
| a record of a decision, allow or deny | `ledger.Ledger` records *provider calls* and money; `trace` records a *request* | neither | no decision is ever recorded, so no incident review has anything to read |

The load-bearing row is the second-to-last. Everything above it works; none of it is *the* permission check, because none of it can say "this caller may not." And the reason that matters is not elegance. It is that **a boundary is only as strong as the number of places you have to remember to put it.** This repository has four. A new tool added on Day 31 will be governed by exactly as many of them as its author happened to think about, and the failure is silent, because nothing in the code says "you forgot."

Seven invariants keep the day honest:

1. **One choke point.** Every call and every result passes `ToolRegistry`. The loop, `run_tool_answer`, `executor.run_plan`, the fallback ladder, and `RoleAgent.run` are unchanged code that inherits the boundary.
2. **Deny by default.** Unregistered tool, ungranted tool, unknown principal, malformed grant, missing decision — all deny. The failure mode of forgetting is *denial*, which is loud and safe, rather than *capability*, which is quiet and catastrophic.
3. **Registration is a grant.** `register()` without a grant raises. A new tool cannot arrive with authority nobody declared.
4. **Exactly one check per argument.** A shape check or a semantic check. Two checks is how a policy starts disagreeing with itself; zero checks is how `maxLength` never gets written.
5. **No partial rows.** A result-boundary permission failure keeps the shape and drops every value.
6. **Every decision is recorded, allows included.** Append-only, hash-chained, and carrying no values — because a log of only denials tells you what failed and nothing about what a principal is doing.
7. **C9: the layer is passive.** Legitimate traffic is byte-identical on and off, at zero model and query cost.

The scope boundary is where the honesty has to live, and it is sharper than yesterday's. **This is authorization, not authentication.** The `principal` is a string the caller supplies — `run_agent(..., principal=...)` already takes one and `STATE_PRINCIPAL` already defaults it — so an unauthenticated `principal=admin` is not a weaker admin, it is an admin, and the audit log records a *decision* rather than a *person*. Identity, transport, secrets, egress, and rate limiting are Day 29. **The grant set itself is a proposal, not a mandate**: nobody who owns this data has been asked who may read `account_user.email`, and a security day that invents the answer to make its own fixture green has produced a policy with no author. Human approval for consequential actions is Day 27. And one limit belongs in the deliverable rather than the changelog: a hash-chained local file is tamper-evident for edits, reorders, and interior deletions, and **cannot detect truncation of its own tail** — the external anchor is Day 29's.

## 2. Read-Only by Default — Three Layers, Only One of Which Is a File

"Read-only by default" is the rule everyone nods at and nobody defines, so the day's first job is to make it three specific claims, because the three fail differently and only one of them is a fact about the world.

**Layer 1 — declaration.** The tool says what it is. `run_saleor_sql` declares `effect: read`; `get_customer` declares `data: pii`; a tool that declares nothing cannot be registered. This layer is a fact about *our code*, and it is enforced by `ToolRegistry.register()` refusing a grantless registration.

**Layer 2 — policy.** Config says what is permitted: `statement_allow: [select, with]`, `tables_allow` (seven tables, verbatim Day 14's schema card), `columns_deny` for `account_user`, `definitions.revenue` requiring the `draft` exclusion, `row_limit: 100`, `max_cost`, three server-side timeouts — and, from today, the per-tool grants. This layer is a fact about *our rules*, and it is the only layer a reviewer can change without a deploy.

**Layer 3 — privilege.** `saleor_read_only` holds no write grant, and `PostgresDataStore` sets `default_transaction_read_only` on the session. This layer is a fact about the *world*, which is exactly why it is the strongest: no config file, no prompt, and no hallucinated function call can overrule a missing grant. Day 14 built Q5 precisely to prove it — `DataAgent.run(sql, validate=False)` bypasses layer 1 and the **engine** still refuses — and that fixture is the reason the privilege claim is a claim at all.

A reader who asks "is this system read-only?" deserves all three, and the honest answer names the weak one. It is not the parser — the parser is the layer most likely to have a bug and the least consequential, because it is backed by a privilege. It is layer 1, the declaration, because layer 1 is the layer a **new tool** arrives on. A tool registered on Day 31 is read-only because of what it declares and because of what it happens to call, and nothing in the registry notices if it opens a socket, writes a file, or posts to an HTTP endpoint. Today that is invisible. After today it is a `ValueError` at import.

Now the part of the rule that is usually implemented backwards. **"Default" has two possible meanings and the difference is the whole bug class:**

```text
  deny-list   (start from everything, subtract the forbidden)     ← how "read-only" is usually built
     new tool      arrives with FULL authority
     new table     arrives VISIBLE
     new argument  arrives UNBOUNDED
     forgetting    ⇒ capability you did not mean to grant          (silent)

  allow-list  (start from nothing, grant what is needed)           ← what today builds
     new tool      arrives DENIED until a grant names it
     new table     arrives INVISIBLE
     new argument  arrives UNCAPPED
     forgetting    ⇒ a denial you will notice in the first fixture that fails
```

The failure *direction* decides the class of bug, and this repository learned the lesson the expensive way on Day 15: `columns_deny` is a deny-list, and it is fine, because Day 15's list was complete for a seven-table schema card. The mistake would have been to add a table to `tables_allow` and forget the columns. Allow-lists invert that: adding a table is a deliberate act, and forgetting the grant produces a denial you discover in a test rather than a grant you discover in an incident.

Which brings the most satisfying fixture in the day. A "write" in this domain is a refund, an order cancellation, an address change — **and none of them exists in this repository.** That is not a gap in the day's work; it is the reason the day can make a clean read-only claim: the strongest form of read-only is a registry in which no write-shaped tool has ever been registered. So the harness registers one deliberately — a `create_refund`-shaped tool, fixtures only, never in `build_default_registry` — and C3 asserts that every real principal is refused it, and that granting it would require an explicit `effect: write` grant carrying `confirm: human`, a field whose implementation does not exist yet. That is precisely how Day 26 hands Day 27 its first real client: **the first time this repository considers a write, the permission model has already insisted that a write carries a human in its grant.**

One more layer worth naming, because it is the one this day adds and it is easy to miss: **the store.** Layer 2 checks the statement; the statement is allowed; the rows still have to be checked. `get_product`, `get_order`, and `get_customer` never call `SafeSql` at all — they build a fixed query and hand it to `self.store.query(...)`. So for those three tools, the policy's table and column rules are *not enforced*, not weakly enforced, **not enforced**. The fourth layer is the result check, and it is the subject of §4. And one honest footnote while we are counting layers: offline, `SqliteDataStore` has no read-only role, so the MECH fixtures are exercising layers 1, 2, and 4, and the privilege claim is `PENDING` until the suite runs against Postgres with `SALEOR_READONLY_DB_URL` set. A security day that reports its offline run as proof of a database privilege would be making Day 7's mistake in a new costume.

## 3. Explicit Tool Permissions — Grants, Effects, and Deny by Default

A grant is the day's central noun, so it should be small enough to read in one screen, and every field should earn its place by answering a question that would otherwise be answered by whoever remembers to ask it:

| Field | Question it answers | Example |
|---|---|---|
| `tool` | which surface | `run_saleor_sql` |
| `effect` | what does it *do* — `read` / `write` / `none` | `read` |
| `data` | how sensitive is what it *touches* — `public` / `internal` / `pii` | `pii` for `get_customer` |
| `args` | what may this argument look like — `maxLength`, `pattern`, `enum`, `semantic` | `id: {pattern: "^[A-Za-z0-9_-]{1,64}$"}` |
| `result` | what may come *back* — declared `columns`, `max_rows`, `evidence`, `redact` | `columns: [id, email, orders, currency], redact: [email]` |
| `confirm` | does a human have to approve — `none` or `human` | `human` (only legal with `effect: write`) |

Six fields, and the two that will be argued about are `data` and `result`, because they are the ones that make §4 possible.

### The choke-point argument

This is the day's central architectural claim, and it is worth stating in the form a reviewer can check:

> There are exactly five ways this system reaches a tool, and all five go through `registry.validate_args` and `registry.execute`.

`run_agent`'s loop validates then calls `execute_bounded` → `registry.execute`. `run_tool_answer` *is* `run_agent(max_steps=1, max_tool_calls_per_step=1)`. Day 16's `executor.run_plan` walks a plan through the same atoms. The fallback ladder's sibling substitution re-validates and re-executes. Day 19's `RoleAgent.run` is `run_agent` with a narrower registry. So the check belongs in the registry, and — this is the clause worth arguing for in review — it belongs in **both** halves: `validate_args` produces the `Decision` and `execute` receives it, and **`execute` denies when it is handed `decision=None`**.

That last clause is the difference between a boundary and a convention. A check in `validate_args` alone is a check every caller must remember to route through; a check that refuses to run without a decision is a check where **a future call site is safe by omission**. Day 16 already taught the lesson in a different costume — `DataAgent.run(validate=False)` is an escape hatch that exists precisely so Q5 can prove the engine beneath it, and it is marked "nothing else should call it," which is a comment, not a mechanism. A comment is a request. A `decision=None` denial is a fact.

### Least privilege at the contract surface

`registry.schemas()` is what the gateway sends the model. So if `schemas()` returns only the principal's granted slice, an ungranted tool is not merely refused when called — it is **never named in the prompt**, and the model cannot spend five turns and three cents discovering that it exists. Day 19 already does this for roles via `scope()`, and it is the most underrated line in that module: privilege containment is a property of the loop's own contract surface, not a check bolted on outside it. Day 26 generalizes the same idea from roles to principals and then makes `scope()` a *derived view* of the grant file, so the repository ends up with one rule table instead of two that can disagree.

The constraint that keeps the control row honest is easy to state and easy to violate: **the `default` grant set must be exactly today's seven tools**, or C9 is not a control but an unannounced behavior change. The temptation will be to ship the "better" default — no `get_customer`, no `run_saleor_sql` for the anonymous principal — and that temptation is precisely what a security day must refuse, because a permission layer that ships tighter than the evidence in front of it is a policy decision made by a fixture instead of by an owner. Ship the layer, prove the equivalence, and leave the tightening as a one-line config change that a human makes on purpose.

### The principal

`run_agent` already accepts a `principal`, and `StateStore` already keys **every record** by one — the memory system has been doing per-principal isolation since Day 17 without ever asking what a principal *is*. That is a gift and a warning. The gift: the identity plumbing exists, the parameter is already threaded through the loop, and a grant file can key on it today. The warning: it is a **caller-supplied string**. `STATE_PRINCIPAL=default` in `.env.example` is a default, not an identity. There is no authentication anywhere in this repository — no session, no token, no signature, and `server.py` does not even expose an agent route to authenticate against.

So the honest description of the entire day is **authorization without authentication**, and it belongs in the deliverable, not in a footnote:

> Day 26 decides *what may be done*. Day 29 decides *who is asking.*

This is not a weakness of the day's design; it is the correct decomposition. Authentication without authorization is a system that knows who you are and does not care what you may do — which is the shape of most of the breaches that are embarrassing. Authorization without authentication is a system that knows exactly what each kind of caller may do and is trusting a label — which is useless against an attacker and *precisely correct* against a confused deputy, a mis-scoped specialist, a plan that emitted the wrong step, or a future engineer adding a tool. The confused deputy is the threat this system actually has, and for that threat a grant model is the whole defense. The human who is not the deputy is Day 29's.

### Missing versus malformed

A **missing** grant is a denial: normal, expected, audited, and the reason `unknown principal` resolves to `default` rather than raising. A **malformed** grant — a principal entry that is not a list, a grant for a tool nobody registered, a `result.columns` that is not a list, an unknown `effect`, a `write` without `confirm: human` — is a **load-time error** naming the key. The distinction is not pedantry. A permission file that half-parses is a permission file that silently grants half of what it looks like it grants, and the failure surfaces as an incident rather than as a stack trace. `Policy.from_dict` already established the discipline on Day 15; today inherits it.

And the resolution order stays deliberately primitive: **grant for the principal → the `default` set → deny.** No inheritance, no wildcards, no prefix matching. A permission file with a pattern language in it is a permission file whose review becomes a proof obligation, and this repository's rule has been *build before abstracting* for twenty-five days. The first caller who asks for role hierarchies should get the day's answer — which is that the grant file will grow a second, uglier mechanism unless it stays a list.

## 4. Validation at Both Ends — Input as a Gate, Output as the Half Nobody Has

### The input side: ten lines, and the two missing keys

`ai_os/tools.py`'s `validate_args` is a hand-rolled JSON-Schema subset — and it is a *good* one, in the sense that it earned its keep on Days 11–12: it checks `type` (with JSON's one-number-type problem handled and no coercion), `enum`, `minimum`/`maximum`, `required`, and it rejects unknown keys outright. It fails with a message that names the field, because that message is the interface Day 12's loop self-corrects against. What it does not do is enforce two keys:

- **no `maxLength`** — so a model may hand `search_saleor_docs` a 40 KB "query" today, and the only thing bounding the resulting observation is Day 12's `budget_chars` clamp *after* the call has already been made. The clamp is a good instrument; it measures the wrong thing. It bounds what the model sees, not what the model made us do.
- **no `pattern`** — so `id`, the argument that reaches SQL through `_literal()`'s hand-rolled quote-doubling, accepts any string at all. The escaping is a real guarantee and it stays; a `pattern` is not a replacement for it, it is a class of values the escaping never has to be correct about. Defense in depth with a *measurable* property: `id ∉ ^[A-Za-z0-9_-]{1,64}$` means `_literal` is never the thing standing between the request and the query.

Two keys, added to the same hand-rolled validator, with the same message discipline (**name the field, name the bound**) and the same refusal to coerce: a value that fails a bound is *rejected*, never truncated into compliance. That refusal is not fussiness. A silently shortened query would make `columns`, `row_count`, and `asserted ⊆ returned` mean something other than what they say, and this repository has spent four days building evaluations whose entire value is that they mean what they say.

Which raises the question every cap invites: **where does the number come from?** Not taste. `sql: {maxLength: 8000}` is pinned to the longest legitimate query in the Day 14/15 fixtures; `query: {maxLength: 512}` to the longest legitimate retrieval query in `corpus/`; `id` to the longest real identifier in the corpus. A cap tuned to a guess breaks Q1–Q8 and I1–I9, and the fix is always the cap's *provenance*, never the fixture — Day 7's rule, arrived at from a completely different direction. One more bound worth adding for the same reason: `max_chars` currently has `minimum: 1` and **no maximum**, so a model can request an unbounded observation and rely on the post-hoc clamp. A `maximum` equal to the corpus budget makes the request itself bounded.

### The class distinction, which Day 12's retry rule makes load-bearing

Day 12's `REASONING_PROMPT` grants exactly one retry: rule 4 says a *repairable* rejection invites "fix the argument and retry once," and rule 5 says a `policy` rejection is a STOP. So the class attached to a refusal is not metadata — it is the difference between "you may try again with a different argument" and "you may not."

- An over-long query is `invalid_args` / **repairable**. The model may shorten it, and that is correct and useful: nothing about length is a policy question.
- A permission denial, a denied column in a result, an ungranted tool, a write attempt is **policy**. It must never arrive dressed as repairable.

The second bullet is worth stating as a general rule, because getting it wrong produces a bypass with better manners: **a denial that arrives as `repairable` hands the model the retry the denial exists to prevent.** The loop will faithfully re-issue the call with a "corrected" argument, and the correction will be the model helping itself past a boundary. The fixture asserts the class on every refusal, and it asserts it on the *result* path too, because the result path is where a new check is most likely to be introduced with the wrong class out of convenience.

### The output side: half the policy has no subject

Output validation does not exist in this repository. Not weakly; not partially — it does not exist, and the reason is structural rather than accidental, which makes it a much better lesson than a missing feature usually is.

Three verifiable facts:

1. `columns_deny` is enforced **on the statement**, inside `SafeSql.inspect`, which is called by exactly one function: `DataAgent.run`.
2. `get_product`, `get_order`, and `get_customer` do **not** call it. They build a fixed, parameterized query and hand it straight to `self.store.query(sql, row_limit=1)`. The comment above them says "safe by construction: one fixed query, one validated `id`, zero generation," and for *generation* that is true — but "safe by construction" is a statement about how the query was written, not a statement about what it returns, and a fixed query can return anything its SELECT list names.
3. `get_customer`'s SELECT list is `u.id, u.email, u.number_of_orders, (SELECT o.currency …)`, and `email` is not on `columns_deny`. The deny list names `password`, `password_hash`, `last_login`, `auth_token`, `token`, `session_key`, `api_key`, `secret` — the credential-shaped columns. `email` is PII without being a secret, and the policy has no vocabulary for that distinction. It has `columns_deny`, which is a list of *names someone remembered*.

The conclusion is not "PII is leaking." It is sharper and more useful, and it generalizes to every system with this shape:

> **The deny list describes a class of statement, and the system also emits results — so half of the policy has no subject.**

Day 26 gives results a subject. Every grant declares the columns its tool may return. A result carrying a column the grant did not declare is a **contract violation**, not a curiosity. A result whose columns intersect `columns_deny` is refused. A tool with no declared columns — the two search tools return *evidence records*, not columns — is held to the **retrieval contract** instead: `doc_id` and `chunk_id` present on every evidence row, text length within the grant's cap, so `cited ⊆ retrieved` and `conclusion ⊆ evidence` remain decidable *after* a security decision has run. And `describe_saleor_schema` is held to `table ∈ tables_allow` plus `columns ∩ columns_deny = ∅` — which is true today by construction, because the card's seven tables are exactly `tables_allow`'s seven tables, and which becomes an asserted, load-time-checked invariant rather than a coincidence a future edit can break silently. That coincidence is the best kind of finding in this day: the invariant was already true, it was just undefended.

### No partial rows

If a result violates its contract, three designs are available, and the choice is the day's most consequential one:

```text
  (a) return the safe columns      "redact and continue"
  (b) return a truncated page      "row cap as a silent trim"
  (c) return nothing, keep the shape, record the violation            ← this
```

The reason is not tidiness. **A partial answer is how a leak becomes untraceable.** Hand the model three of five columns and it will narrate the three; the trace will show a successful call; the audit log will show an `allow`; and the two missing columns will be nobody's decision, in a system whose entire claim is that every decision is recorded. Option (a) has a second failure too — redaction that the model does not know about is redaction that the model will happily contradict from its own priors.

So (c): `ToolResult.failure(..., rejection_class="policy")` carrying `columns`, `query_kind`, `executed`, and `redacted` — and zero values. Day 14's `_data_result` already established the move one layer out, where a *rejected query* keeps `gen_sql`, `validation: "rejected"`, and `executed: false` precisely so the §8 table can tell "the validator refused it" from "the database refused it." Day 26 reuses that instinct: **keep the shape, drop the values**, so the trace can still say which columns arrived and the model is told only that the call failed.

### Redaction, and the `email` question

Three moves are available for `get_customer`: deny the tool outright; redact `email` at the result boundary and record the redaction; or grant the column to one principal only. All three are implementable in a day, and the day implements all three *mechanisms* while shipping the strictest as the default.

The choice itself is `PENDING`, and the reason is not indecision — it is that **nobody has been asked.** Support is a real job; a security day that silently edits a deny list to make a fixture green has taught the wrong lesson, and one that silently grants a column to make a fixture pass has invented a mandate nobody gave it. So the deliverable ships the mechanism, ships the strict default, names the decision as `PENDING` with an owner, and puts the three options on the table with their costs: denying the tool is safe and probably wrong; redacting keeps the shape and makes the redaction visible in the result record and the audit entry; a per-principal grant is the most flexible and the most likely to be forgotten by the next person who reads the file. Whichever is chosen, the requirement is that it be *written down* — because the alternative is the situation today, where the deny list is a list of names somebody remembered and the fixed resolvers are outside it entirely.

## 5. Design: The Permission Model, the Choke Point, and the Audit Record

The design is seven decisions, and it is worth writing down what was *rejected* alongside what was chosen, because in a security design the discarded options are where the reasoning shows.

**Decision 1 — one choke point, in the tool, carrying the decision from validation into execution.** Rejected: a decorator on each tool (`@requires("read")`), because a decorator is opt-out and the next tool author forgets it — that is a convention, and conventions are what this day exists to replace. Rejected: a middleware in `run_agent`, because three more paths (`run_tool_answer`, `run_plan`, `RoleAgent.run`) exist and none of them would be covered. Chosen: `ToolRegistry.__init__(permissions=…, principal=…)`, `validate_args` returning the `Decision` **on the `ToolResult`** (a new `permission` field, so the decision travels with the value and cannot be separated from it), and `execute(name, args, decision=None)` denying when no decision is supplied. The decision travels *inside* the result object rather than beside it on purpose: a side-channel return value is something a future call site can drop, and a field on the value cannot be.

**Decision 2 — registration requires a grant, and the declaration is cross-checked against the layers beneath it.** `register(name, schema, fn, grant=None)` raises when the grant is missing. But the stronger half is the cross-check: `run_saleor_sql` declaring `effect: read` is worth nothing if `policy.yaml` can be edited to `statement_allow: [select, with, insert]` and nothing notices. So the day's own fixture asserts **all three layers agree** — declared effect ⊆ `statement_allow` ⊆ the store's read-only privilege — and fails, naming the layer that stopped disagreeing, if someone edits the policy. A declaration nobody cross-checks is a comment; a declaration a test cross-checks is an invariant.

**Decision 3 — deny by default at four levels, each with its own code.** `no_grant` (registered, not granted to this principal) · `unknown_tool` (not registered — inherited from Day 11, and still *repairable*, because a hallucinated name is the model's mistake to fix) · `unknown_principal` (resolves to `default`, and **the fallback itself is audited**) · `missing_decision` (`execute` reached with no decision — an internal-invariant violation, `policy`, and loud). The codes matter because `error_kind` and `rejection_class` already are a contract in this repository, and a security decision without a name is a decision nobody can grep for at 3 a.m.

**Decision 4 — exactly one check per argument, declared in the grant.** This is the decision that most looks like a limitation and is most load-bearing. Two checks on one argument is how a policy starts disagreeing with itself: the schema says `sql` is a string, `SafeSql` says it is a query, and a future reader has to work out which one binds. So each argument gets a `semantic: true|false` flag and exactly one enforcement path:

| Argument | Check | Why that one and not the other |
|---|---|---|
| `run_saleor_sql.sql` | **semantic** — `SafeSql.inspect` (Day 15) + a byte cap as a resource bound | it *is* a query; a shape check cannot know a `SELECT` from a `SELECT` with a write head, and re-parsing it in the validator is Day 15's problem arriving twice |
| `get_*.id` | **shape** — `pattern: ^[A-Za-z0-9_-]{1,64}$` | it is a *literal*, not a query; its only semantic layer is `_literal()`'s quote-doubling, and pretending a pattern is a substitute for escaping (or vice versa) misdescribes what is standing where |
| `describe_saleor_schema.table` | **shape** — the closed set derived from `SCHEMA_CARD` | the card's seven tables *are* `tables_allow`'s seven tables, so the enum **is** the allow-list; a load-time check makes that an invariant instead of a coincidence |
| `search_*.query`, `module` | **shape** — `maxLength`, measured | free text with no semantics; the cap bounds the exfiltration channel and the observation size |
| `k`, `max_chars` | **shape** — existing `minimum`, new `maximum` | already ranges; they just needed the other end |

**Decision 5 — the result contract, and no partial rows.** `check_result` runs on every `ToolResult` *after* the tool returns and *before* the result becomes a `tool` message: declared-column membership, `columns ∩ columns_deny = ∅`, `row_count ≤ grant.max_rows`, retrieval-contract conformance for evidence rows, and redaction of `redact:` columns with the redaction **named** in the result record. A violation is `rejection_class: policy` with the shape kept and every value dropped. Rejected: returning a masked value (the model will contradict it) and truncating to the cap silently (a truncation that is not reported is Day 6's bug in a new place).

**Decision 6 — every decision is audited, allows included, and the log is append-only and hash-chained.** Rejected: reusing `Ledger`. The ledger records *provider calls* — model, tokens, cents, latency — and it is the right instrument for money. A permission decision is a different fact about a different subject, and merging them would mean the audit trail dies with the gateway process, which is exactly when you do not want it to. Rejected: logging denials only. A log of failures tells you what did not happen and nothing about what a principal is doing, which is the question an incident review actually opens with. Chosen: one entry per decision, chained, values excluded.

**Decision 7 — the trace grows columns; the prompt does not change; the refusal names a class, not a policy.** This is the decision that carries yesterday's lesson forward. It is deeply tempting to add a line to `REASONING_PROMPT` — *"if a tool call is denied for permission reasons, do not ask for it again"* — and Day 25 spent an entire day proving that a permission encoded in prose is a permission the model can be argued out of. The prompt is already correct: rule 5 says a `policy` rejection is a STOP, and a permission denial *is* a policy rejection. So `REASONING_PROMPT` stays byte-identical, the refusal needs no new vocabulary, and the only prompt-adjacent change is generalizing `TERMINATION_NOTE["policy"]`, which today reads "the safe SQL layer refused a *policy* violation (a write, a denied/sensitive table or column…)" — and would therefore **lie** on every non-SQL denial. The note becomes "the run stopped because a policy check refused this call: <class>" where class ∈ `permission_denied`, `sql_policy`, `role_violation`, `result_violation`. Naming the class is not disclosure: the model needs to know it may not proceed, and the operator needs to know which layer refused, while `policy.yaml` itself never enters the transcript.

Two more rejections worth one line each. **No policy engine** — no OPA, no Cedar, no Rego, no network, no new dependency: twenty-five days of hand-rolled validators is the house style, and a policy language would move the review from "read this file" to "verify this proof." **No redaction-as-silencing** — a redaction that is not recorded is Day 24's "a missing span is a gap" arriving through the back door, and an audit entry that omits the redaction it performed is a false record, not a short one.

## 6. Build: `ai_os/permissions.py` — Grants, Decisions, and a Fail-Closed Loader

The new module is a **library of decisions**, not a framework, and the discipline is that it contains no I/O beyond loading its own file: `EFFECT_READ` / `EFFECT_WRITE` / `EFFECT_NONE` and `DATA_PUBLIC` / `DATA_INTERNAL` / `DATA_PII`; `ArgRule(maxLength, pattern, enum, minimum, maximum, semantic)`; `ResultRule(columns, max_rows, evidence, redact)`; `Grant(tool, effect, data, args, result, confirm)`; `Principal(name, tools)`; `PermissionSet.from_dict` / `.load(path)` / `.for_principal(name)`; `Decision(allow, code, reason, grant)`; and the two functions the rest of the repository will call, `check_call(principal, name, args, *, perms)` and `check_result(name, result, *, perms, decision)`.

The naming of those two functions is not cosmetic. `check_call` and `check_result` say *check*, not *authorize* and not *enforce*, because a check reports a fact about the arguments and the result; the authority that *refuses* is the registry, and the record that *explains* is the audit log. Keeping the verbs separate is what stops the file from quietly growing into the thing the whole day argues against — a god object that decides, blocks, logs, and reports, and therefore has to be trusted on all four counts at once.

The loader is **fail closed and specific**, in the exact register `Policy.from_dict` set on Day 15: a missing file raises a `ValueError` naming the env var and the default path; a principal entry that is not a list of strings, a grant for a tool nobody registered, a `result.columns` that is not a list, an unknown `effect` or `data` value, and a `write` effect without `confirm: human` each raise a `ValueError` naming the key. An unknown *principal* is deliberately **not** an error — it resolves to `default` and the resolution is audited, because refusing a brand-new caller outright is a policy decision nobody asked for, while crashing on one turns a config typo into an outage and trains people to avoid the feature.

The resolution order is one line and is a test: **grant for the principal → the `default` set → deny `no_grant`.** No chains, no wildcards, no prefix matching.

Config follows the existing conventions rather than inventing new ones, because consistency is what lets a reader of `.env.example` predict the file's contents: `PERMISSIONS_PATH` (default `permissions.yaml`, beside `policy.yaml`) and `PERMISSIONS=none` to restore the ungoverned path for the control row, matching `SALEOR_SQL_POLICY`'s shape; and `AGENT_PRINCIPAL` beside the existing `STATE_PRINCIPAL`, since the two names the same thing for different subsystems and having them agree is cheaper than having them differ. All of it is added to `.env.example` with the same explanatory comment style, because in this repository the env file is documentation that cannot go stale.

The two missing JSON-Schema keys go into the hand-rolled `validate_args` in `ai_os/tools.py` — `maxLength` and `pattern`, each with the failure message naming the field *and* the bound, each rejecting rather than truncating — and the grant's per-argument rules are enforced through the same path, so an argument is validated once, by one function, with one error vocabulary. Two validators would be a second thing to regress and a second thing to disagree.

The whole layer is dependency-free and offline, and the decision path takes no clock: the `ts` is stamped by the audit writer, not by the check, so a decision is a pure function of `(principal, tool, args, perms)`. That is what makes C1–C9 deterministic and what makes the cost line honest: dictionary lookups, set membership, comparisons the validator already made, and one `sha256` per decision. **0 chats, 0 embeds, 0 SQL, 0 rows.**

## 7. Build: The Choke Point — Registry, Loop, Result Path, and Trace

The wiring in `ai_os/tools.py` is small and the smallness is the point, because a security layer that rewrites the call path is a security layer that has to be re-verified end to end:

- `ToolRegistry.__init__(…, permissions: PermissionSet | None = None, principal: str | None = None)`.
- `register(name, schema, fn, grant=None)` **raises** without a grant — the boot-time refusal C2 proves by attempting it.
- `schemas()` returns the principal's granted slice, so least privilege is a property of the contract surface and an ungranted tool is never named in the prompt.
- `validate_args` returns the `ToolResult` with a new `permission` field: `{"decision": "allow"|"deny", "code": …, "effect": …, "data": …}`.
- `execute(name, args, decision=None)` **denies when `decision is None`.**
- `run(name, args_raw)` is unchanged: validate, then execute, carrying the decision across.

The denial routes into vocabulary that already exists and is already tested: `ToolResult.failure(..., error_kind="permission_denied", rejection_class="policy")`. That single choice means Day 12's rule-5 STOP, Day 13's guard ring, Day 15's classification, the fallback ladder's policy exclusion, the trace, and the failure ledger all handle it with code that has a fixture history — **no new control plane**. And the claim is verified by reading the loop rather than by trusting the shape: the sibling substitution is already gated on `result.rejection_class != POLICY_CLASS`, so a denied call can neither retry nor substitute into a sibling tool, and `step_policy` is checked *before* `no_progress`/`oscillation`/`tool_failure`, so a policy hit owns the terminal.

Then the three files that gain **no** permission code, which is the day's architectural result rather than an omission:

- **`executor.py`** (Day 16) walks a plan through `validate_args` + `execute_bounded` + `registry.execute`. A plan step is therefore governed by exactly what a loop step is, and a planner cannot emit a step the loop could not have taken.
- **`RoleAgent`** (Day 19, in `agent.py`, built by `make_agent(role)` and imported by `orchestrator.py`) is `run_agent` with a narrower registry, so a specialist is governed identically — and `ToolRegistry.scope()` becomes a **derived view** of the grant file, so `ROLE_TOOLS` and the grants can no longer disagree. A fixture asserts that even a deliberately wrong `ROLE_TOOLS` entry cannot reach a tool the principal's grants exclude.
- **`agent.py`'s loop** gains one field, `policy_hits`, already there, and nothing else in the control flow. Day 16's `max_steps=1` identity case still holds; the fallback ladder still substitutes only for `tool_error`, never for a denial.

`check_result` is added to the return path *after* the tool returns and *before* the result is stored, so the value that becomes a `tool` message is the value that was checked — not a copy of it, and not a value reconstructed afterwards. A violation becomes a `policy` failure carrying `columns`, `query_kind`, `executed`, and `redacted`, with no values; a redaction drops the named columns and records them in the result and in the audit entry's `result_shape`. Nothing in `_tool_message` changes, so the observation clamp, the `truncated` flag, and `cited ⊆ retrieved` keep working exactly as they did, and `data_columns()` and `asserted ⊆ returned` (Day 14) see the same shape they have always seen.

The trace grows additively and safely: `ai_os/trace.py` gains `permission`, `permission_code`, `granted_tools`, `result_redacted`, and an `unknown_principal_fallback` flag, with the Day 23/24 metadata-safe default and its redaction scan extended over the new fields. This is the recurring requirement of the last three days, stated once more because the audit entry is the most tempting place in the entire repository to leak a row of PII: **a security feature that expands what gets recorded is a regression wearing a feature's clothes.** `REASONING_PROMPT` stays byte-identical. Only `TERMINATION_NOTE["policy"]` is generalized so that it names the refusal *class* instead of assuming the refusal came from the SQL layer — because a note that lies on every non-SQL denial is worse than no note at all, and the loop's last message is the one place where a lie becomes the system's final word on what happened.

## 8. Build: The Audit Log — Append-Only, Hash-Chained, Metadata-Safe

`ai_os/audit.py` is the day's evidence layer, and the design question is never "how much do we log" — it is "what may a security record contain." The answer is decided by the rule from Day 25, so the entry is narrow on purpose:

```json
{"seq": 41, "ts": "…", "run_id": "…", "trace_id": "…", "principal": "analyst",
 "tool": "run_saleor_sql", "effect": "read", "data": "internal",
 "decision": "deny", "code": "no_grant", "args_hash": "sha256:…",
 "args_shape": {"sql": {"chars": 412}}, "result_shape": null,
 "latency_ms": 0.21, "prev_hash": "sha256:…", "hash": "sha256:…"}
```

Permitted: identifiers, the principal string, the tool name, the declared effect and data class, the decision and its code, `args_hash` plus `args_shape` (key names and value *lengths*), `result_shape` (row count, column names, `truncated`, `redacted`), and latency. Forbidden, as rules rather than habits: **no SQL text, no row values, no `email`, no document text, no system prompt, no policy or permission file contents, no API key, and no `ToolResult.error` string that might echo a payload back out of a tool.** A reviewer can prove the call happened, prove which arguments were used without storing them, and reconstruct the decision — and cannot read a single row of customer data out of the file. The chain is `hash = sha256(canonical_json(entry − hash))` with `prev_hash` carried in, canonical meaning `sort_keys`, fixed separators, UTF-8, and no floats, so the hash is reproducible by anyone with the file and a shell.

`verify()` walks the file and returns `{ok, entries, chain_ok, first_broken_seq}` with `chain_ok` reported **separately** from `entries`, and that separation is the honest part of the design. The tamper model is exact:

| Attack | Detected | How |
|---|---|---|
| a value edited in place | **yes** | the entry's `hash` no longer matches its content |
| an interior entry deleted | **yes** | every subsequent `prev_hash` mismatches |
| two entries reordered | **yes** | same |
| the tail truncated | **no** | nothing inside the process can notice a file that simply ends — the chain is shorter and still valid |

So the claim the day may make is **tamper-evident for edits, reorders, and interior deletions**, never "tamper-proof." The fix for the fourth row is an external anchor — a remote sink, an immutable store, a periodic head published somewhere the process cannot reach — and that is Day 29's, and the residual register says so in the same sentence as the guarantee. The second honest limit sits right next to it: **the log records a decision, not a person.** The principal is a caller-supplied string, so this is an audit log in the sense of *record*, not in the sense of *forensics*, and a system that used the word "audit" without that distinction would be promising something Day 29 has to deliver.

The writer is append-only in the literal sense: append mode, one `write()` per line, no update and no delete method on the class, and **no rotation** — because silent truncation is the one attack a self-verifying file cannot see, so rotation is a storage decision made by an operator (Day 29), not a housekeeping behavior of a library. The volume argument belongs in the design and not in a footnote: entries per run are bounded by the turn wall, since the number of calls is `≤ max_steps × max_tool_calls_per_step` and Day 11 already caps calls per step — so **the model cannot flood the log**. A caller looping at the HTTP layer is a rate-limiting problem, and rate limiting is Day 29's.

The inspection surface stays as small and as boring as Day 25's `GET /attacks`: `GET /audit?principal=…&tool=…&decision=deny` and `GET /audit/verify`, read-only, no values to leak because none are stored. And one fact about `server.py` belongs in the day's notes at the point the endpoints are registered rather than six months later: **this repository has no agent route and no identity surface at all** — `/health`, `/chat`, `/chat/stream`, `/ledger`, `/rag`, no `principal` header, no session, no authentication. So the audit endpoint is the first thing in the system that is meaningfully per-caller, and it is per-caller only because someone put a string in a request. That is a Day 29 fact wearing today's clothes, and writing it here is cheaper than discovering it during an incident review.

| ID | What it proves | Attack / case | Expected |

| C8 | **no bypass** | the five call paths — loop, `run_tool_answer`, `run_plan`, the sibling substitution, `RoleAgent.run` — plus a deliberately wrong `ROLE_TOOLS` | all five deny an ungranted tool; `execute` with no decision denies; a wrong role map still cannot exceed the principal's grants; Day 19's out-of-role call is still `role_violation`/`policy` — Day 26 **adds** a check, it does not replace one |

Six of the nine fixtures assert a *negative* — a grant that was not given, a write that did not happen, a column that did not reach the model, a decision that was not recorded, a chain that broke, a path that could not bypass. That is the right shape for a security suite: the interesting claims are about what did **not** occur, and a suite that only asserts successful denials measures nothing beyond the code it just read.

The control row protects everything else, and it is stricter than it looks. The temptation in a security day is to ship a tighter default — no `get_customer`, no `run_saleor_sql` for the anonymous principal — and the temptation must be refused for a specific reason: **a permission layer that ships tighter than the evidence in front of it has made a policy decision on behalf of the people who own the data.** Ship the layer, prove the equivalence, print the grant-hit rates, and leave the tightening as a one-line config change a human makes on purpose. The same discipline governs the caps: a `maxLength` tuned to a guess breaks Q1–Q8 and I1–I9, and when it does the fix is the cap's provenance, never the fixture.

The `MECH` / `PENDING` split stays honest. **Grant resolution, deny-by-default, the single choke point, the registration-time requirement, `maxLength`/`pattern` enforcement, the result contract, no-partial-rows, the audit entry shape, the chain and its verification, the tamper-evidence claim, the entry-volume bound, and the on/off equivalence are `MECH`** — each has a deterministic assertion, none of which needs a model. **The grants' correspondence to reality is not**, and this day will not write a line claiming otherwise: nobody has told us who may read `account_user.email`; there is no authentication behind the `principal` string; there is no external anchor, so tail truncation is invisible; there is no rate limiting, so a caller can loop; and there is no observation of a real model attempting an escalation, because the stub is scripted to do what the fixture says and cannot surprise us. A green C-set proves the **decision procedure**. It does not prove the **policy**, and the two are different claims with different owners.

## 10. Measure: The Permission Report and the Price of a Decision

The report is one table over every fixture and every real tool:

| tool | principal | granted | decision | code | declared | check | result contract | audit seq | chain_ok | effect that did **not** happen |
|---|---|---|---|---|---|---|---|---|---|---|
| `search_saleor_docs` | `default` | ✓ | allow | — | read/public | shape | evidence, ≤10 rows | 12 | ✓ | — |
| `run_saleor_sql` | `support` | ✗ | deny | `no_grant` | read/internal | semantic | `*`, ≤100 rows | 13 | ✓ | no query ran, no row returned |
| `get_customer` | `analyst` | ✗ | deny | `no_grant` | read/pii | shape | `[id, email, orders, currency]`, redact `email` | 14 | ✓ | no `email` read at all |
| `get_customer` | `support` (granted, hostile store) | ✓ | deny | `result_violation` | read/pii | shape | undeclared column `password_hash` | 15 | ✓ | **no rows reached the model** |
| `create_refund` | any | ✗ | deny | `no_grant` | write/pii, `confirm: human` | semantic | — | 16 | ✓ | no write, no side effect, no ledger entry |
| `run_saleor_sql` | `analyst` | ✓ | deny | `sql_policy` | read/internal | semantic | `Wrote? = no` | 17 | ✓ | the write head never reached the connection |

Plus three worked narratives, because a table says what happened and a narrative says why.

**The escalation.** A `support` question asks why an order failed, the model proposes `run_saleor_sql` with a perfectly valid aggregation, and the call is denied with `no_grant` — no SQL parsed, no connection opened, no cost incurred. The loop stops on rule 5 with `TERMINATION_NOTE["policy"]` naming the class, the answer says plainly that the request was refused because the tool is not granted to this caller, and the audit entry records the decision with the args hashed. The interesting part is not the denial; it is that **the model never saw the tool in the first place**, because `schemas()` returned `support`'s granted slice, so the whole episode cost one turn instead of a discovery loop.

**The contract violation.** A granted `get_customer` call comes back from a hostile (or merely changed) store with a `password_hash` column the grant never declared. `check_result` refuses it, the result becomes a `policy` failure keeping `columns`/`query_kind`/`executed`/`redacted` and **zero values**, and the model is told the call failed. What the trace can still answer — which columns arrived — is exactly what the model cannot be told. That asymmetry is the design: the operator gets the forensic detail and the model gets a refusal, and neither gets a half-record.

**The write that does not exist.** The `create_refund`-shaped tool is registered in the harness only, and every real principal is refused it. Nothing about the refusal is clever; the whole point is that the *decision procedure* is the same one that granted the seven read tools, so there was never a special path for the dangerous case — and the grant file contains no `write` effect at all, so a reviewer can confirm the read-only claim by reading one file. This is what "read-only by default" looks like when it is enforced rather than asserted: not a rule that writes are banned, but a system in which granting one requires typing something that does not exist yet.

The questions the day exists to answer, answered from the record:

- Which code can say no, and is it the only code that needs to?
- What happens to a tool added tomorrow that nobody granted?
- What can a principal do that it was not granted, and how would we find out it happened?
- What is in the audit log, and what is provably *not* in it?
- If someone edits one byte of the log, do we find out, and where?
- What does the layer cost a legitimate request?

The cost answer is the cleanest number in the series: **0 chats, 0 embeds, 0 SQL, 0 rows**, by construction, because grant resolution is a dictionary lookup, the argument checks are comparisons the validator already made, and the result check is set membership over columns the result already carries. The measured overheads are one `sha256` per decision and one appended line per decision. Legitimate requests show a **zero delta** in tokens, cost, tool sequence, SQL text hash, and row counts against the `PERMISSIONS=none` control, and the grant-hit rates per tool are printed so that a grant nobody uses and a tool every question needs are both visible as numbers rather than as opinions.

And the day does not claim more than it built. What exists after today is a system in which **every** tool call and **every** tool result passes one decision procedure that defaults to deny, that the model cannot argue with, that cannot be skipped by a call site that forgot it, and that leaves a tamper-evident record of every decision it made. What does **not** exist is any assurance that the policy is the right policy, any assurance of who is asking, any assurance the log has not been truncated, and any assurance that a real model's escalation attempts look anything like the ones in the corpus. Those lines are `PENDING`, and they have owners: **Day 27** owns the human in the loop for the actions an allow-list cannot decide — the `confirm: human` field in every write grant is its first client; **Day 28** owns production rate limits, queues, and caching, which is where "a caller looping" stops being a note and becomes a mechanism; **Day 29** owns identity, transport, secrets, egress, and the external anchor that makes truncation detectable. None of them is served by a cleverer prompt, and all of them is served by what today established: **the boundary lives in the tool, the default is deny, and every decision is written down.**

## 12. Daily Learning Record

### Problem

Twenty-five days gave the system authority, and yesterday gave it a map of its own boundaries. Nobody had yet built the mechanism those two days implied. The failure mode was never that the boundaries were weak — Day 15's allow-list, Day 11's argument schema, Day 17's closed write path, Day 19's role scope, and the `saleor_read_only` role are all real, all tested, and all fail closed. The failure mode was that they were **scattered, and each one existed for a different reason**, so nothing in the code could answer the only question that matters at a new tool's registration: *what is this thing allowed to do, and who is allowed to ask?* Nothing knows what a principal is. Nothing validates a result. Nothing records a decision. A new tool inherits exactly the authority its author remembered to write down, and the forgetting is silent. Meanwhile two concrete holes sat in plain sight: `columns_deny` is enforced on the **statement**, while `get_product` / `get_order` / `get_customer` never call `SafeSql` at all and query the store directly — so `get_customer`'s `u.email` is outside a policy that names `password_hash` and never mentions email; and `id` reaches SQL through `_literal()`'s hand-rolled quote-doubling with no `pattern` in the schema, because the validator implements `type` and `enum` and never learned `maxLength`. And the trap the day had to avoid is the obvious one: ship a "secure" default that is tighter than the system it replaces, and turn a security layer into an unannounced behavior change that every existing fixture fails for reasons nobody wrote down. The problem is not that permissions are hard to express. It is that **the boundaries were four files each defending one thing, and a boundary is only as strong as the number of places you have to remember to put it.**

### Concept

**A threat model is a list of worries; a permission system is a decision procedure — and the difference is when each one is consulted.** A list is read once by the people who wrote it; a decision procedure is consulted on every call and returns a verdict with a name. So Day 26 builds four things in a deliberate order. **Declaration:** every tool states its `effect` (`read`/`write`/`none`) and `data` (`public`/`internal`/`pii`), and registration without a grant raises — so a new tool's authority is a fact in a config file rather than an assumption in a reviewer's head. **Deny by default:** an ungranted tool, an unknown principal (which resolves to the strictest `default` set, and whose fallback is audited), a malformed grant, and a missing decision are all denials, so *forgetting* produces a failure you notice in a test instead of a capability you discover in an incident; and the reason is directional, because a deny-list fails toward capability and an allow-list fails toward denial. **One choke point:** the check lives in `ToolRegistry`, travels *on* the `ToolResult` (a field on the value, not a side-channel return a caller can drop), and `execute` **denies when handed `decision=None`** — so all five existing paths inherit the boundary as unchanged code and a hypothetical sixth is safe by omission. **Validation at both ends:** input bounds are pinned to *measured* legitimate maxima, and output validation is the half that did not exist — declared columns, `columns ∩ columns_deny = ∅`, row cap, and the retrieval contract, with a violation keeping the shape and dropping every value, because **a partial answer is how a leak becomes untraceable.** Three rules make the day specific to this repo: **exactly one check per argument** — `sql` is semantic (`SafeSql`), `id` is a shape (`pattern`, because its only semantic layer is `_literal`'s escaping and misdescribing it helps nobody), `table` is the closed set derived from the card that turns out to *be* `tables_allow` — and a denial must never arrive as `repairable`, or Day 12's rule 4 hands out the retry rule 5 exists to prevent; **read-only is three claims** — declaration, policy, privilege — and only the third is a fact about the world, with the weakest link being the *next* tool rather than the parser; and **every decision is recorded, allows included**, append-only and hash-chained, with no SQL text, no row values, no email, and the tamper model stated exactly: edits, reorders, and interior deletions are caught; **truncating the tail is not**, and the external anchor is Day 29's. And the frame the day refuses to drop: this is **authorization without authentication** — the `principal` is a caller-supplied string, so the audit log records a decision rather than a person, and the grant set is a proposal until an owner says otherwise.

### Understanding

The re-readings hit in order: **(1) the choke point is the whole day.** Five paths, one seam, and the discovery that `DataAgent.run(validate=False)` already exists as a *deliberate* escape hatch with a comment saying "nothing else should call it" — which is a request, not a mechanism, and is exactly the shape `execute(decision=None) → deny` replaces. **(2) Least privilege at the contract surface beats least privilege at the call.** `schemas()` returning the granted slice means an ungranted tool is never named in the prompt, so the denial costs zero turns instead of a discovery loop — Day 19's `scope()` was the best line in that module and today generalizes it from roles to principals. **(3) The failure direction of an allow-list is the bug class.** "Default" is ambiguous in exactly one dangerous way, and the whole deny-list/allow-list argument follows from noticing which way forgetting pushes. **(4) Output validation is missing for a structural reason, not an accidental one.** The policy is written about *statements* because statements are where generation happens — and the moment a system emits results, half the policy has no subject. The fixed resolvers are the proof: they are safe by construction *as queries* and ungoverned as *results*, and `email` is a PII column the deny list has no vocabulary for. **(5) No partial rows.** Three columns of five with the trace showing a success and the audit showing an `allow` is how a leak becomes nobody's decision; Day 14's `validation: rejected, executed: false` already showed that shape preservation and value removal are different acts. **(6) A declaration nobody cross-checks is a comment** — so the day asserts effect ⊆ `statement_allow` ⊆ the read-only role, which converts "we were careful" into a test that fails and names the layer that stopped agreeing. **(7) The prompt must not change.** The temptation to add "if a call is denied for permission, do not retry" is precisely the move Day 25 spent a day refuting, and rule 5 already covers it; the only prompt-adjacent change is generalizing `TERMINATION_NOTE["policy"]`, because a note that says "the safe SQL layer refused" would lie on every non-SQL denial, and the loop's last message is the system's final word on what happened. **(8) Tamper-evident is not tamper-proof.** A hash chain catches edits, reorders, and interior deletions and is structurally blind to its own tail, so `chain_ok` and `entries` are reported separately — an audit artifact whose guarantee is vague is a liability. **(9) Authorization without authentication is the correct decomposition, not an excuse.** The confused deputy is the threat this system has; a grant model is the complete answer to *that*, and the human who is not the deputy is Day 29's problem. Shipping the tighter default would have been the day's real failure mode, not the missing authentication.

### Failure

1. **The check in the loop instead of the registry.** `run_plan`, `run_tool_answer`, and `RoleAgent.run` then bypass it, and the fixture that covers only the loop passes. Anti-fix: the choke point, plus `execute(decision=None)` denying.
2. **The check in `validate_args` only.** Every caller must remember to carry the decision across; the first one that does not is silent. Anti-fix: the decision travels on the `ToolResult`, and `execute` refuses without it.
3. **A decorator (`@requires("read")`) on each tool.** Opt-out, therefore a convention, therefore the thing this day replaced. Anti-fix: registration requires a grant.
4. **Shipping a tighter default.** No `get_customer` for the anonymous principal "because it is safer" — an unannounced behavior change justified by nobody, which breaks C9 and every honest fixture at once. Anti-fix: the `default` set *is* today's tool set; tightening is a one-line human decision.
5. **Caps tuned to a guess.** `maxLength: 256` chosen because it looks reasonable, breaking a legitimate long query in Q1–Q8. Anti-fix: pin every cap to a measured legitimate maximum; when it breaks, fix the cap's provenance, never the fixture.
6. **Truncating instead of rejecting.** Silently shortening an over-long query makes `columns`, `row_count`, and `asserted ⊆ returned` mean something else. Anti-fix: reject, name the field, name the bound.
7. **A denial arriving as `repairable`.** The model is handed the retry the denial exists to prevent, and "corrects" its way past the boundary. Anti-fix: assert the class on every refusal, input *and* result.
8. **Two checks on one argument.** The schema calls `sql` a string, `SafeSql` calls it a query, and the next reader has to decide which binds. Anti-fix: `semantic: true|false` per argument, exactly one path.
9. **Checking only the statement.** The half the policy has no subject: `columns_deny` binds generated SQL, and the fixed resolvers return whatever their SELECT list names. Anti-fix: `check_result` on every result, with a declared column set per grant.
10. **Returning the safe columns.** Three of five reach the model; the trace shows success; the audit shows `allow`; the missing two are nobody's decision. Anti-fix: no partial rows — shape kept, values dropped.
11. **Silent redaction.** A redaction that is not in the result record and not in the audit entry is Day 24's missing span arriving through the back door. Anti-fix: `redacted` is a first-class field in both.
12. **Editing `columns_deny` to make a fixture green.** A security day that quietly adds `email` to a deny list has answered a question nobody asked, in a config diff nobody reviews. Anti-fix: the choice is `PENDING` with an owner; ship the mechanism, ship the strict default, write down the open decision.
13. **Logging the values.** "For forensics," the SQL text and the row land in the audit file, and Day 23's metadata-safe default is bypassed by a security feature. Anti-fix: `args_hash` + `args_shape`; scan the log in C7 and fail if a value appears.
14. **A log of denials only.** It answers "what failed" and never "what is this principal doing". Anti-fix: every decision, allows included, one entry each.
15. **Claiming tamper-proof.** A hash chain cannot see its own tail being cut. Anti-fix: state the model exactly; `chain_ok` and `entries` separate; the anchor is Day 29's.
16. **Adding a line to `REASONING_PROMPT`.** A permission encoded in prose is a permission the model can be argued out of — the exact move Day 25 refuted. Anti-fix: rule 5 already covers it; the prompt stays byte-identical and the fixture proves it.
17. **A "security" rollup line.** "The agent is secure" is the sentence that undoes the day. Anti-fix: the residual register names every limit with an owner, and green fixtures never promote to a security claim.

### Debugging

- **A legitimate fixture broke after the layer** → check the grant for that tool first, then the cap, then the result contract, in that order. A change in a legitimate answer almost always means a grant, a bound, or a contract that is *wrong*, not a test that is wrong — and the fix is whichever of those it is, written down.
- **Something reached a tool and should not have** → grep the call path, not the decision. `registry.execute(` has exactly one entry point per caller; if the `decision` argument is missing at a call site, that is the bug, and `execute(decision=None)` is what made it visible instead of silent.
- **The loop retried a denied call** → check the `rejection_class` on the way out of `check_call`. A denial that reached the loop as `repairable` puts it back on rule 4's path, and the sibling substitution is gated on the same field.
- **The answer contains a column the grant did not declare** → check whether `check_result` ran *before* the result was stored rather than after, and whether the violating `ToolResult` was reconstructed downstream from the tool's own return value. A check that runs on a copy is not a check.
- **The audit file will not verify** → read `first_broken_seq`. If it is the last entry, you truncated; if it is in the middle, something edited or reordered. Check whether a test wrote a line by hand, which is the most common cause of a chain that breaks in a suite and never in production.
- **A test passes with the layer off** → that test is not a control, and C9 is not proven. The layer's contribution has to be *observable* in the report or it is not being tested.
- **The `email` decision keeps being deferred** → put it in the residual register with an owner and a date, because an unowned security decision does not get made; it gets inherited by whoever edits the file next, silently.
- **A principal fell back to `default` and nobody noticed** → the fallback is audited, so check `unknown_principal_fallback` in the trace. A fallback storm is a caller sending a name the system has never heard, which is either a typo or an authentication problem wearing a typo's clothes.

The trace and the audit log should answer, without anybody reasoning about intent: which tools this principal was granted, what it asked for, what was allowed, what was refused and by which code, what the results looked like by shape, what was redacted, and whether the record has been altered. A debugging session that still requires an opinion about whether the model "meant" to escalate has not finished — because the model's intent was never the input to any of these decisions, and the system is better for it.

The `PENDING` line is plain. **No claim is made that the grant set is correct** — nobody has decided who may read `account_user.email`, and the mechanism ships with the strictest default while the decision stays open with an owner. **No authentication exists**: the `principal` is a caller-supplied string, so the audit log records decisions and not people. **Tail truncation of the log is undetectable** without the external anchor Day 29 owns. **There is no rate limiting**, so a caller can loop, and the per-run entry bound protects against the model rather than against the caller. **No real model has been observed attempting an escalation**, because the stub does what the fixture says. And nothing in the day constrains what the model can *say* — only what it can *do*, which is Day 25's claim arriving again one layer down. None of them is served by a cleverer prompt, and all of them is served by what today established: **a boundary in the caller is a boundary the next caller forgets, so the boundary belongs in the tool, the default is deny, and a decision nobody can read is a decision nobody can trust.**

### Architecture

The claim of the day is the series' claim made explicit: **authority in this system is now a config file plus one choke point, not a property each contributor has to remember.** The architecture is deliberately *inherited* — `sql_safety.py` is untouched and still the thing that stops a generated write; `validate_args` is the same hand-rolled ten lines with two keys added; Day 19's `scope()` becomes a derived view rather than a replacement; Day 16's executor and Day 12's loop gain no permission code at all; and the one new module in the request path (`permissions.py`) is pure, offline, and decides nothing about the *world* — it resolves a grant and reports. The genuinely new logic is small: a decision, a result check, and an audit record. What makes it architectural rather than additive is the **placement** — the check is in the tool, the decision travels on the value, and `execute` refuses without it, so the five existing call paths are unchanged code and a future sixth is safe by default. This is "build before abstracting" applied to security one more time: learn the declaration/policy/privilege distinction, the failure-direction argument, the one-check-per-argument rule, and the no-partial-rows rule from this codebase's own holes, *before* reaching for a policy engine, a capability token, a WASM sandbox, or a sidecar proxy — and keep the fixtures sharp enough that the answer stays testable rather than fashionable. The most architectural decision of the day is the refusal to ship a tighter default: the layer goes in at exactly today's authority, with the tightening left as a one-line, human, reviewable change. That is the same instinct as Day 15's `Wrote? = no`, Day 21's `cited ⊆ retrieved`, and Day 25's label-don't-launder — **a system that tightens itself to look secure has made a decision nobody made, and a system that hides a fact to look safe is not safe, it is just unauditable.** And the limit the day states about itself is architectural too: the boundary is real, and it is inside a process that does not know who is talking to it.

### Questions

- The choke point makes a future call site safe by omission. Is there a second kind of omission this repository should also make safe by default — a new *result* shape, a new *plan step kind*, a new *state kind*?
- `execute(decision=None)` denies. Should the same clause exist for the *result* path — a `ToolResult` that arrives without having been checked is ungoverned, and today nothing distinguishes it from a checked one?
- Read-only is a declaration, a policy, and a privilege. Which of the three do we *cross-check* automatically (today: effect ⊆ `statement_allow` ⊆ role), and is there a fourth layer — a new tool's side effects — that no layer can see?
- The `email` decision is genuinely open. Deny, redact, or grant per principal — and does the answer change if the honest answer is "support needs it, analysts do not," which is a fact about a team this repository has never met?
- The audit chain is tamper-evident and not tamper-proof. What is the smallest external anchor that makes truncation detectable — a signed head, a remote counter, a periodic publish — and what does it cost in availability when the sink is down?
- Least privilege at the contract surface means the model never sees an ungranted tool. Is there a *legitimate* case for showing a model a tool it may not call (teaching it what exists, refusing gracefully), or is every such case a prompt pretending to be a permission?
- The grant file is a list, deliberately. The first real request for role hierarchies, wildcards, or time-bounded grants will arrive; what is the rule that keeps it a list rather than a policy language?
- The per-run entry bound protects against the model and not the caller. At what point does "one entry per decision" become a volume problem, and should the layer shed load under pressure — which would mean a decision with no record, and what then?
- Everything here is measured with a stub model. Which of C1–C9 are structurally independent of the model entirely, and which only *look* independent because a scripted model never escalates?
- The whole day is authorization. If Day 29 authenticates the principal, does anything here change, or is the grant file already the right artifact waiting for an identity?
