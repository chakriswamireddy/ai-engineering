# Day 28 — Production Architecture

## Objective

Understand how the system becomes production-ready.

Twenty-seven days built a machine that reads (Days 6–10), acts (11–12), fails honestly (13), computes (14–15), plans (16), remembers (17–18), splits into specialists (19), learns how it will be judged (20–22), explains one request from the inside (23) and across its boundaries (24), learned to be attacked (25), learned who may open a door (26), and yesterday learned to stop and wait for a person (27). Every one of those days added **capability or authority**, and every one of them left the same structural fact untouched: **there is one process.** One Python process holds the HTTP server, the model gateway, the token ledger, the 251 MB vector store, the provenance-checked state store, the permission layer, the approval records, and the trace — and it holds them in the same address space, with no lock between them, no queue in front of any of them, and no second copy of anything. The curriculum now supplies the day's real content, and it is a review list rather than a build list: **Docker, queues, caching, rate limiting, async workers, secrets, model fallback, retries, failure recovery, database scaling, vector storage, object storage**, with the instruction *"map the local system to a production architecture"* and the deliverable **a production architecture diagram** — the first day in the series whose output is not a module. The repo's inventory for this day is not a list of missing features; it is a list of **claims the system has never been forced to make true**, and it is more alarming than any previous day's because it is not about the model. There is no `Dockerfile` and no container. `requirements.txt` holds four dependencies (`fastapi`, `uvicorn`, `pyyaml`, `psycopg`) and no broker, no cache, no scheduler. `server.py:177–183` calls `RagStore.load(path)` inside the `_rag_store()` helper, and `server.py:198` calls that helper on every `/rag` request — so the 262,182,307-byte `data/store.json` (Day 21's 11,061 real chunks) is parsed by `json.load` on every call, and `RagStore`'s own docstring's promise that "boot = load (ms)" is false at this size. `server.py:33` builds the gateway **once at import time** and `server.py:114–116` (and `:144`) then reads `gateway.last_provider`, `gateway.last_latency_ms` and `gateway.last_attempts` *after* the call returns, while `gateway.py:197–199` writes those as instance attributes on a shared object — so under two concurrent requests the response can report **another request's provider and latency**, and there is no test anywhere that would notice. `server.py:123–152` declares `/chat/stream` `async def` at `:124` and then drives a **synchronous** generator `events()` at `:137` and then streams a **synchronous** generator inside it, — so a single slow provider stream occupies the event loop and stalls `/health` and every other request. `ledger.py:99` computes `cost_usd=self.cost(model, usage) if ok else 0.0` and `gateway.py:177–180` records failures with no token counts, so **a timed-out or 429'd provider attempt costs money at the provider and `$0.00` in the ledger** — and the ledger is the one number Day 4 built to make retry cost visible. `state.py:592–608` has `get()` mutate `accessed_at` and call `_maybe_save()`, so with the default `autosave=True` **every read rewrites the entire state file** through a tmp-file plus `os.replace` (`state.py:838–845`) with **no file lock**, which means two processes are last-writer-wins and silent. `ledger.py:65` keeps `self.records` in a per-process list, unbounded, so a restart erases the cost history and `--workers 4` produces four ledgers. `data.py:454` is `sqlite3.connect(":memory:")` seeded with `SEED_SQL`, and nothing anywhere warns when `SALEOR_READONLY_DB_URL` is unset — so **a misconfigured production process answers customer questions out of a curated fixture**, while the RAG path fails loud with a structured error naming the missing file (`server.py:202–204`). And `observability.py` has no sink, no exporter and no `to_dict` anywhere in its 62 functions: `run_rag` starts a trace (`rag.py:248`), finishes it, and returns its `trace_id` in the response body — **an identifier for a record that was never stored.**

Day 28's first principle is that **a production architecture is a set of claims about failure, not a set of boxes.** Every diagram in this genre is drawn as components and connections, and the connections are the part nobody checks, so the result is an inventory with arrows. The honest artifact labels every edge with *what happens when this one breaks*, and every label is either a mechanism that exists in this repository or a `PENDING` with an owner — and the day's first job is to write the twelve-item review list as a table of *where each item actually lives in this repo*, because nine of them already have a partial answer, four of them have a **broken** answer, and the three that do not are the three with the most honest answer available. Second principle: **the twelve items are all assertions about a process boundary, and the process boundary is the thing that does not exist.** Not "is not containerized" — *does not exist as a concept anywhere in the code*. There is no second process to reason about, so every property people attribute to a "service" is currently a property of a module: a restart is a total outage *and* a total amnesia; a scale-out is a correctness bug rather than a performance one; and a "retry" is a `time.sleep` in a worker thread. The day therefore draws **two** architectures, and says so in the title of the diagram: **the architecture that is** (one process, honest, with its failure modes named) and **the architecture that becomes necessary at two processes** (a diagram of exactly which arrow breaks first, with the three components that must change listed and the eleven that must not). That is the deliverable, and it is more useful than a single optimistic diagram because it is the one thing a diagram can be that a box list cannot: **a claim with a named failure and a named trigger.** Third principle, and the one that makes the day a measurement rather than a drawing: **every bound in this system today is a per-run or per-call constant, and a per-run constant is not a rate limit.** A rate limit is a *tuple* — who, what, over what window, and what happens when it is hit — and the repository has about twenty bounds that are all of the form "one run may do at most N" (`AGENT_MAX_STEPS = 6`, `AGENT_TOOL_TIMEOUT_S = 30.0`, `AGENT_BUDGET_USD`, `AGENT_MAX_REPLANS`, Day 27's `APPROVAL_MAX_PER_RUN = 1`, `STATE_MAX_RECORDS = 1000`, `LLM_MAX_ATTEMPTS = 3`) and **not one** of them is keyed on a principal over a window. So the day's only new module is a *bound registry* and a token bucket that answers those four questions, in exactly the register Day 26 wrote `permissions.py` in and Day 27 wrote `approval.py` in: a library of decisions, not a framework. Fourth principle: **the retries that already exist are correct and they are the reason admission control is not optional.** `gateway.py:38–48` honors the server's own `Retry-After` before applying exponential backoff with full jitter, and `gateway.py:151–152` walks an ordered provider chain with `max_attempts` each — that is good work from Day 4 and the day says so. The problem is that a retry policy is a **load multiplier** (up to `providers × max_attempts` calls for one user request, and a 429 with `Retry-After: 30` makes every waiting caller wait 30 s), and a load multiplier with no admission control in front of it is an outage with a trace attached. Worse, the ledger cannot see it: §the cost of a failed attempt is `$0.00` by construction, so the one dashboard that would show a retry storm is structurally blind to the half of the storm that matters. Fifth principle, and the one that changes what "caching" means in this repository: **a cache here is a correctness decision, not a performance one.** Day 20 pinned the golden set by content hash and made `judged ⊆ pre-registered` an invariant; Day 25 extended the pin to the *evidence* and made a changed-evidence row `unresolvable` rather than `wrong`; and `RagStore` already locks `embedding_model` and `dimension` (`rag.py:95–124`) with a `STORE_VERSION` (`rag.py:25`) that refuses a mismatched store. So a cache whose key is not the store's identity is not "a faster store" — it is a way to serve yesterday's evidence and call it today's answer, and it is exactly the failure Day 25's corpus-hash rule was written to prevent. The day's rule follows from the series: **the cache key is the store's identity — the file's content hash plus the two locked fields — and a store whose identity cannot be computed is not cacheable.** The cheapest correct fix is not a vector database; it is loading the store **once per process** behind an identity check, and the day builds that, because the alternative is parsing 251 MB of JSON per request forever. Sixth: **model fallback is a measurement event and today it is silent.** `config.py:41–51` reads one global ordered chain from `LLM_PROVIDERS` with no per-tenant and no per-cost policy, and `gateway.py:104` already puts `fallback_depth` on every attempt span — and `fallback_depth` appears in exactly two places in this repository, both inside `gateway.py`, and **nowhere in the eval harness and nowhere in the docs**. So the number is recorded, never consumed, and a golden verdict can today be issued on an answer produced by a *different model* than the one the row was pinned against. Day 25 already has the precedent and the right word for this: `unresolvable`, not `wrong`. Seventh: **secrets are Day 29's mechanism and today's is a position, and the position is measurable today.** `config.py:23–37` reads `.env` from the working directory at import and `server.py:33` builds the gateway at import, so in a container a secret is either a mounted file or an injected variable and the diagram has to say which. The measurable part is the debt Day 27 deliberately declined to touch on the grounds that a security day was the wrong day: **60 environment names are read by `ai_os/`, 21 appear in `.env.example`, and 39 are missing** — `AGENT_MAX_STEPS`, `AGENT_TOOL_TIMEOUT_S`, `AI_TRACING`, `TOOL_GATE_TAU`, `MEMORY_*` (6), `RAG_CODE_STORE_PATH`, `OPENROUTER_API_KEY`, the eight provider-template names (`config.py:60–66` reads `{PROVIDER}_API_KEY`/`_BASE_URL`/`_EMBEDDING_MODEL` for the three providers in `PROVIDER_REGISTRY`, and an AST scan of literal `os.getenv` calls alone sees only 52) and nineteen more. Day 28 is the right day, because the diagram's central claim is that *configuration is a surface*, and a surface with 39 undocumented knobs is not a surface. Eighth: **the four scaling items have no honest answer yet, and the day's discipline is to say "not yet" with a trigger attached to each.** *Database scaling* has no trigger today: one `psycopg.connect` per store instance (`data.py:528`), a read-only snapshot rolled back after every query (`549`, `566`, `576`), eight allow-listed tables, a 100-row page limit and a 2 000 ms statement timeout — the store is not too big, it is *not shared*, and the trigger is concurrency, not size. *Vector storage* is the one that is genuinely close, because 251 MB of JSON is parsed per request and `RagStore.retrieve` (`rag.py:140–153`) is a full `sorted(dot(q, c.vector) … for c in self.chunks)` over 11,061 vectors, so an order-of-magnitude corpus increase hits retrieval before it hits anything else; the day writes the migration *order* down and refuses to start it: **(1) stop parsing per request, (2) an in-process cache keyed on store identity, (3) float32 and a memory-mapped layout, (4) an ANN index, (5) a real vector store** — five steps, none of them today, because a day that builds step 5 on Day 28 has thrown away the only control that makes steps 1–4 measurable. *Object storage* is the raw source tree: `corpus/` at 2.5 MB and `corpus_code/` at 98 MB, and the honest cost is that a corpus change today means *rebuild the JSON*, which is O(store) per update — trigger: the first corpus refresh that takes longer than the deploy it rides on. Ninth, and it is the reason the day's build is a *ratchet* and not a module: **a diagram drifts toward optimism, so the only way to keep one honest is to make it falsifiable.** Day 20 made the judgment falsifiable (`judged ⊆ pre-registered`, enforced by a hash pin) and Day 19 made the architecture *comparison* falsifiable (G1–G9 as a contract). Day 28 makes the architecture *itself* falsifiable: every box in the diagram must be a file that exists, every failure claim on an arrow must be a fixture, every knob in the diagram must be in `.env.example`, and the day's control — **N9** — asserts that *the diagram and the repository are the same object*. That is the first control in the series that tests the deliverable rather than the code, and it is the reason a document can be a deliverable in an engineering series at all.

### 2. Learn: A Diagram Is a Set of Claims About Failure, Not a Set of Boxes (45 min)

- [ ] Learn what an architecture diagram is *for*, from the failure it prevents: a diagram exists so that a change can be checked against a picture of what depends on what. A picture of components alone cannot do that, because every component is a noun and every dependency is a claim about what happens when the noun is unavailable. So the day's artifact is an **edge-labelled diagram**, where each edge answers one question — *if this link is severed, what does the user see?* — and the labels are drawn from a closed vocabulary so they cannot drift into prose: `fails-loud`, `fails-quiet`, `fails-stale`, `fails-lost`, `fails-corrupt`, `fails-slow`, `duplicates`, `drops`. Seven labels, and the day insists a claim outside the vocabulary is an unfinished claim. `fails-quiet` earns its place first, because the repository already has one: `data.py:454`.
- [ ] Learn the **three things a diagram can say that a component list cannot**, and make sure the day's artifact says all three. (1) **The unit of failure** — here, the process, so every "service" boundary on the diagram is a *future* boundary and saying so on the diagram is more honest than drawing a box around each module. (2) **The unit of amnesia** — what survives a restart, which is a *different* set from what survives a crash and a *much* smaller set than what a reader assumes: the corpus (files), the RAG store (a file), the state store (a file), the audit chain (a file), the golden set (a file) — against the ledger, the trace, and the gateway's `last_*` (nothing). (3) **The trigger for each change** — not "we will need Redis eventually" but "the first day the store takes longer to parse than the deploy takes to run", which is a condition, testable, and dated by nobody.
- [ ] Learn the **single-process diagram's** most important and least comfortable property: because there is one process, **every resource bound in the system is a global bound wearing a per-run label.** `AGENT_MAX_STEPS = 6` is per run, but there is exactly one run per process at a time if the process is synchronous — so six steps *is* the throughput ceiling, and "per run" is a courtesy to a system that cannot yet run two. `LLM_MAX_ATTEMPTS = 3` is per call, and calls are serial, so the process's provider-call rate is `1 / (latency + backoff)`. `STATE_MAX_RECORDS = 1000` is a file cap, and the file is rewritten on every read (`state.py:607`). Every bound in the diagram must therefore be drawn as **either a per-run bound (a courtesy) or a per-process bound (the real ceiling)**, and the day marks which is which, because the moment a second worker appears every "per-run" bound silently becomes half the true global bound and nobody will notice for a month.
- [ ] Learn what the **process boundary actually costs** when it finally appears, so the diagram can be drawn in the right order. In this repo, going from one process to two breaks exactly three things, in this order, and the order is the argument: **(1) `StateStore`** — tmp-file plus `os.replace` with no lock (`state.py:838–845`), so two writers lose records silently and a reader can see a stale file for an unbounded time; **(2) the ledger** — a per-process list (`ledger.py:65`), so cost accounting splits N ways and a restart destroys a share of it; **(3) the audit chain and the approval store** — Day 26's hash chain and Day 27's decisions are files with an implicit single writer, so two processes interleave entries from unrelated runs and the `seq` ordering that the incident review depends on stops meaning anything. Everything else in the diagram — the corpus, the stores' *contents*, the permission file, the policy file — is already safe to share, because it is read-only after ingest. **So the migration order is: make the state store a database, then make the ledger durable, then make the chain append-only with a real lock** — and the day draws that order instead of drawing a cluster.
- [ ] Learn the **difference between a diagram that is accurate and a diagram that is useful**, because they are not the same artifact and the series has earned the right to be picky. An accurate diagram of this system today would have one box, and one box is a true and useless statement. A useful diagram has the one box, plus a second diagram of the three breakages, plus a trigger column, plus the twelve-item status table — and the honest way to present all of that under one heading is a **two-plate diagram**: *Plate I — what is*, *Plate II — what breaks, in what order, at the first trigger*. The day refuses the single optimistic plate on the specific ground that a single plate cannot be checked: there is no assertion in it that could fail.

### 3. Learn: Queues, Async Workers, and Rate Limiting — Three Different Bounds (45 min)

- [ ] Learn to **separate the three words the curriculum lists together**, because they are three different mechanisms that get confused constantly and each of them answers a different question. A **queue** answers *what happens to this unit of work while nobody is working on it* — it must be durable, it must have a depth, and it must be possible to ask how deep it is. An **async worker** answers *who drains that queue, and what happens if the drainer dies* — it must be able to stop without losing work, and the work must be safe to hand to a second drainer. A **rate limit** answers *how fast may any single caller ask* — it must be keyed on something the system can *authenticate*, and that last clause is the trap, because this repository's key would be the caller-supplied `principal` string, which Day 26 established is not an identity and Day 27 established can approve an irreversible action. The three have separate owners in the diagram and the day will not draw them as one box labelled "async".
- [ ] Learn what **this repository's queue already is**, because the answer is a surprise and it is the strongest evidence for Day 27's design: Day 27's approval store is a **durable, TTL-bounded, provenance-checked, out-of-band record with exactly one consumer and no depth bound** — that is a queue, and it was built as a side effect of refusing to block the loop. So today's queue work is not a new concept; it is the two properties the record does not have: a **depth** (how many `requested` records may exist for one principal, and what the eleventh one gets) and a **lease** (which consumer is resolving this record, and since when). The lease matters for a reason that is purely about honesty: without one, a second consumer can `decide()` a record the first consumer is mid-decision on, and Day 27's state machine would correctly refuse the *second* one as `approval_duplicate` — which is right, but it means the first consumer's work is silently discarded and the operator sees a decision by somebody else. A lease turns "who is doing this" from an assumption into a field.
- [ ] Learn the **admission-control argument** from the retries that already exist, and state it as a mechanism rather than as a best practice. `gateway.py:151–152` walks `providers × max_attempts`; `_backoff` (`38–48`) honors `Retry-After` and otherwise uses `base × 2^(n-1)` with full jitter; `LLM_TOTAL_BUDGET_S` bounds the chain when set. Under no load, that is a good retry policy. Under load it is a **load multiplier**: a provider that returns 429 with `Retry-After: 30` keeps N concurrent callers sleeping 30 s each, and the *next* wave arrives on top of them. The multiplier is bounded (`providers × max_attempts` ≈ 6 with the shipped chain) but it is applied *after* the request is admitted, so it multiplies the load that admission control was supposed to prevent. Therefore the ordering is fixed: **admission control before retries, not after**, and the day's limiter is placed in the position Day 26 placed `check_call` — before the work, at the boundary, keyed on the caller.
- [ ] Learn the **shape of a correct rate limiter here**, and the four questions it must answer, because a limiter that answers three of them is a throttle with a bug: **who** (a key the system can attribute — and today that key is `principal`, which the day marks as *unattributable in fact and usable in practice*, the same two-word verdict Day 26 used); **what** (a budget with named units — requests, or input tokens, or *dollars*, and this repository already has the last one: `AGENT_BUDGET_USD` and the ledger's `cost_of`, so "cost" is the unit the series has always measured in); **over what window** (a token bucket gives refill rate and burst capacity as two separate numbers, which is exactly right for a system with a cheap-but-bursty caller and an expensive-but-slow one); and **what happens when it is hit** (a *refusal with a code and a `retry_after`*, in the shape of Day 15's `ProviderError` taxonomy and `server.py:58–68`'s existing 429 mapping — so the day adds no new HTTP concept, it adds one error kind to an error taxonomy that already knows how to render one).
- [ ] Learn **what the limiter must not be**, in this repository, with the same seriousness as Day 27's list of what the approval mechanism must not be. Not a middleware (it cannot be attached yet — §7). Not a per-run counter (`APPROVAL_MAX_PER_RUN` already is one, and it bounds the model, not the caller). Not a token count scraped from the ledger *after* the call (that is an audit, not a limit: the money is already spent, and `ledger.py:99` shows what the ledger thinks a spent call looks like). Not a global cap (a global cap is a fairness bug: one caller can consume the whole budget and the refusal is indistinguishable from a busy system). And not a number without a consequence: **a limit that returns a slower answer instead of a refusal is not a rate limit, it is a queue you did not draw.**

### 4. Learn: Caching, Model Fallback, and Retries — the Three That Change Answers (45 min)

- [ ] Learn why **caching is the correctness item and not the performance item in this series**, and make the argument from the series' own invariants rather than from a general principle. Day 20 pinned every golden row by content hash and made `judged ⊆ pre-registered` an invariant that a hash enforces; Day 25 extended the pin to the *evidence* a row resolves against, and made a row whose evidence hash changed `unresolvable` rather than `wrong`, precisely because comparing a new answer against an old expectation is a category error. A cache whose key is not the store's identity reintroduces exactly that category error, silently, in the retrieval layer: the answer is computed from *yesterday's* store and graded against *today's* expectation, and the harness reports a pass. So the day's rule is not "cache the store"; it is **the cache key is the store's identity, and identity is `sha256(file) + embedding_model + dimension`**, with the two locked fields already present (`rag.py:95–124`) and the version check already refusing a mismatched store (`rag.py:25`, `STORE_VERSION`). A store that cannot produce its identity is **not cacheable** — and the honest consequence, which the day states, is that a rebuilt-but-equal store is a *cache miss*, because a content hash cannot tell you it is equal without reading it, and reading it is the thing being avoided. That is the real trade: identity is computed by hashing the file, so the day's cache still pays one hash per process start and then **zero parses per request** — which is the entire win, and it is a win of 251 MB per request, not 5%.
- [ ] Learn the **shape of the fallback problem**, which is not "what if the provider is down". The gateway's chain is one global ordered list (`config.py:41–51`), so *every* caller shares one fallback policy, and the policy has no cost dimension: a fallback from `gpt-4o-mini` to a frontier model is a quality change, a cost change, and a *measurement* change, and the current configuration has no way to express the difference. The day's specific finding is the quiet one: `gateway.py:104` writes `fallback_depth` onto every attempt span, and that string appears **nowhere else in the repository** — not in the eval harness, not in the golden set, not in a doc. So the system *measures* that it fell back and *never asks* what falling back means. And the answer is already written down in the series: it means the row is **`unresolvable`**, because the answer was produced by a model the expectation was not pinned against. The day adds the rule and the assertion, and adds no model and no judge.
- [ ] Learn the **retry-versus-idempotence question**, which is where "retries" on the curriculum's list actually bites, and note that the answer differs for the two halves of the system. A retried *model call* is safe-ish: the worst case is a second bill for the same tokens, and the ledger records one row per attempt so the cost is visible in principle (`ledger.py:59` — "failures included, so retry cost is visible instead of mysterious" — which is a docstring that the `ok=False` → `$0.00` rule at `ledger.py:99` quietly contradicts). A retried *tool call* is Day 13's problem and was already solved: `AGENT_TOOL_RETRIES = 1` for the same-argument case, `DEFAULT_FALLBACKS = 1` for sibling substitution, and an oscillation detector over a 4-call fingerprint window. A retried *staged effect* is Day 27's problem, and it is the only one of the three where a retry is genuinely dangerous — which is exactly why Day 27's store has no `update` method and the executor recomputes the digest. The day's contribution to the list is therefore not a new retry policy; it is the observation that **the repository already has three different retry semantics, in three different modules, and no shared vocabulary for them** — and that the production diagram's only job on "retries" is to say which is which, because a reader who assumes they are the same will design the wrong thing at the boundary.
- [ ] Learn the **cost asymmetry that makes the whole list urgent**, and get the number right: `ledger.py:99` is `cost_usd=self.cost(model, usage) if ok else 0.0`, and the failure path at `gateway.py:177–180` passes no token counts at all. So a provider attempt that consumed tokens and then timed out is recorded as a 0-token, `$0.00` row. This is not a rounding convention; it means **the ledger is structurally blind to the most expensive class of failure**, which is the class that happens *because* the system is under load. And the day must be careful about the fix: changing it would move every pinned cost number in twenty-eight days of reports, so the honest action is to **record the defect, name the owner, and refuse the fix inside a day whose deliverable is a document** — the same judgment as Day 27 declining to build the refund, and for the same reason: a measurement change is a change to the measurement.

### 5. Design: The Bound Registry, the Diagram, and the Ratchet (30 min)

- [ ] Design the record before touching the layer, because the registry *is* the mechanism and the diagram is its rendering:
  ```yaml
  # capacity.yaml — Day 28's addition. A bound is a TUPLE, and all four parts are
  #   required: a limit missing `on` or `consequence` is a number, not a bound.
  #   * `on` is a key the system can attribute. Today that key is `principal`,
  #     which is authorization without authentication (Day 26) — recorded, not fixed.
  #   * `consequence` is a code. A limiter that returns a slow answer is a queue
  #     nobody drew.
  #   * `burst` is separate from `rate` on purpose: a cheap bursty caller and an
  #     expensive slow one need the same shape and different numbers.
  bounds:
    requests_per_minute:
      on: principal
      unit: requests
      rate: 20.0             # sustained refill
      burst: 5               # bucket depth
      consequence: rate_limited          # → HTTP 429, `retry_after` in the body
    spend_per_hour_usd:
      on: principal
      unit: usd
      rate: 0.50
      burst: 0.25
      consequence: budget_exhausted      # the ledger's own unit, not a request count
    approval_queue_depth:
      on: principal
      unit: pending_records
      rate: 0                 # not a rate at all — a depth; declared as such
      burst: 3
      consequence: queue_depth_exceeded
    in_flight_runs:
      on: process
      unit: concurrent_runs
      rate: 0
      burst: 1                # the truth about this system today
      consequence: server_busy            # the honest ceiling is one
  ```
  And the refusal Day 26 built in, restated because it is load-bearing for a new reason: a bound with no `consequence` is a `ValueError` naming the bound, and a bound with no `on` is a `ValueError` naming the bound — because a limit nobody can be refused by is a comment with a number in it.
- [ ] Design decision #1 — **the registry is a library of decisions, not a framework, and it lives in one file.** `ai_os/capacity.py` with `Bound`, `TokenBucket`, `AdmissionController`, and `queue_depth`/`lease` for Day 27's records. Same register as `permissions.py` and `approval.py`: no framework, no base class, no plugin registry, no async, no threads. The reason the day builds exactly one module is the one the series has used for twenty days: **a bound nobody can name in one place is a bound nobody is administering**, and there are currently 60 environment names read across fifteen files with no index. Rejected: a settings framework or a pydantic settings object (it would make the knobs *implicit* again, discovered by import rather than by reading, and Day 28's whole claim is that configuration is a surface a reader can see).
- [ ] Design decision #2 — **the token bucket is filled by an injected clock, so the day costs 0 seconds of wall time and 0 chats.** `TokenBucket(rate, burst, clock=time.time)`: `consume(cost=1) -> bool` refills by `rate × elapsed`, capped at `burst`, and returns a refusal (never raises) carrying `retry_after = (cost − tokens) / rate`. The whole limiter is arithmetic over an injected clock, which is the reason N1–N4 are `MECH` at all, and the reason the *cost* of the day's headline mechanism is `0 chats, 0 embeds, 0 SQL, 0 rows` — a rate limiter that spent a model call to decide whether to spend a model call would be a joke, and the day notes the one place this bites: the budget bound is denominated in dollars, so a caller with a large prompt and a small `rate` can overshoot within one call, because the pre-flight estimate is an estimate. The honest handling is to **debit on completion and refuse on arrival**, so the bound is approximate in the direction of safety, and the day says "approximate" rather than claiming the precision it does not have.
- [ ] Design decision #3 — **the limiter is built but not attached, and the reason is the same shape as Day 27's CLI.** `server.py` has no authentication, no session, and no `principal` header, so a per-principal limit attached as middleware would be a limit on a string the caller chose — the same escalation path Day 27 refused for approvals, one level down. So `AdmissionController.check(principal, …)` is a library call, the fixtures drive it directly, and the **attachment point is named in the diagram as `Day 29`**, with the reason written at the seam: a rate limit is only as trustworthy as the key it counts, and the key here is a header. This is the second day running that shape (build the mechanism, refuse the surface), and the day treats the repetition as evidence that the pattern is the repository's, not a coincidence.
- [ ] Design decision #4 — **the cache is one function, keyed on identity, and it is the *first* step of the five-step vector migration rather than a shortcut past it.** `load_store_cached(path, *, clock) -> tuple[RagStore, str]` computes `sha256(file) + embedding_model + dimension` once per process, holds the store in a module-level slot, and re-hashes only when the file's `(mtime, size)` changes — a re-hash of 251 MB is ~0.2 s, which is the price of correctness and is quoted as such. Crucially the cache **also serves as step 1 and step 2 of the migration** (stop parsing per request; one in-process copy) without pretending to be step 4, and the day writes the five steps into the diagram so nobody can later point at the cache and say the hard part is done.
- [ ] Design decision #5 — **fallback becomes a first-class refusal in the evaluation lane, and it is the only new rule in Days 20–22 that the day adds.** A golden verdict on a run whose `fallback_depth > 0` is **`unresolvable`**, carrying the depth and the model that answered — Day 25's `unresolvable` for changed evidence, applied to a changed *model*. The rule is implemented in the bench's judge path as a pre-check on the trace, and asserted by a fixture that constructs a fallback run by hand. No model is called; no new judge lane; no semantic grade. And the reason it belongs on this day rather than Day 25 is that it is a *deployment-topology* concern: a single-provider deployment has `fallback_depth = 0` always, so the rule is invisible until someone configures a second provider — which is a Day 29 event.
- [ ] Design decision #6 — **the diagram is two plates, one table, and one trigger column, and the trigger column is mandatory.** Plate I: what is, one process, every box a file:line. Plate II: what breaks, in order, at the first trigger. Table: the twelve items with status, where, and owner. Triggers: *first request that must be served while another is in flight* (→ the process splits), *corpus × 10* (→ retrieval), *corpus refresh longer than the deploy* (→ object storage), *second provider configured* (→ fallback grading), *an authenticated caller* (→ the limiter attaches). Five triggers, all conditions rather than dates, and the day refuses to write a roadmap because a roadmap is a list of hopes with quarters attached.
- [ ] Design decision #7 — **the ratchet is the deliverable, and it is three assertions with names.** `N-diagram`: every component id in the diagram resolves to a file that exists, and every file the diagram names is one the code actually uses (both directions, because a diagram with a phantom box and a diagram missing a box are the same defect seen from opposite ends). `N-claims`: every failure claim on every arrow is a fixture id, and every fixture id in the report appears on an arrow — so an unfalsifiable claim cannot enter the diagram, and an unclaimed fixture cannot hide in the harness. `N-config`: every `os.getenv`/`_env_int`/`_env_float` name in `ai_os/` appears in `.env.example` or in a named exception list, which today means **writing the 39 missing names and recording the one name that is a genuine exception** — `CMD_ZDR`, which is documented, read by no code in any file, and which Day 27 already flagged. The other three documented-but-unread names (`ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL`, `OPENAI_BASE_URL`) are **not** exceptions: a literal-name scan misses them because `config.py:60–66` builds them by f-string from the provider name, which is exactly why the census counts template-expanded names and not just literals. The three are cheap, deterministic, and impossible to satisfy by editing the document alone — which is the property that makes them a ratchet rather than a promise.
