# Day 29 — Deployment

## Objective

Deploy a working version.

Twenty-eight days built a machine that reads (Days 6–10), acts (11–12), fails honestly (13), computes (14–15), plans (16), remembers (17–18), splits into specialists (19), learns how it will be judged (20–22), explains one request from the inside (23) and across a process boundary (24), learned to be attacked (25), learned who may open a door (26), learned to stop and wait for a person (27), and yesterday learned to draw a map of what breaks first (28). The curriculum now hands the day a deployment list: **containerization, environment variables, secrets, application deployment, database, observability, health checks**, with the note that *AWS can be introduced at architectural depth first and implemented where practical*, and the deliverable **an accessible deployed AI OS or a production-like local deployment**. The inventory for this day is short and the repo's answers to it are worse than Day 28's list, because six of the seven items are not about the model and are not about architecture either: there is no `Dockerfile`, no compose file, no `.dockerignore`, no `HEALTHCHECK`, no image, and no deployed anything. `requirements.txt` holds four dependencies (`fastapi`, `uvicorn`, `pyyaml`, `psycopg[binary]`) and no HTTP client, so there is not even a way to ask a remote instance a question. The repo's only documented run command is the module docstring at `server.py:3–4` — `uvicorn ai_os.server:app` — with no `--host`, no `--port`, and no container around it. The corpus and the stores are on the host filesystem (`corpus/` 2.5 MB, `corpus_code/` 98 MB, `data/store.json` 262,182,307 bytes, `data/code_store.prev-5domains.json` 190,543,227 bytes), the state store is a JSON file with no lock, the ledger is a per-process list (`ledger.py:65`), the trace store is a per-process `OrderedDict` capped at 256 traces (`observability.py:706–716`, the cap at `:714`), and the secrets are in a `.env` file **in the working directory** that `config.py:23–37` reads at import and that `server.py:35` triggers at module load.

Day 29's first principle is that **a deployment is not a claim that the system runs, it is a claim about what happens to its state when the process is replaced** — and this repository has never had a second copy of itself, so it has never had to answer that question. The day therefore treats the container as what it is: the *first* second process in twenty-nine days, and the first time Day 28's Plate II stops being a drawing. The measurements are already in hand, and they are not what the plan expected. Two containers on one shared volume, each with the state store in memory, lose records with **zero exceptions**: writer A holds 40 records, writer B boots holding 31, B's first write rewrites the whole file from B's copy, and the file ends with 31 — A's 10 later records are gone and B reported success (`state.py:838–845` rewrites the entire file from `self.records` on every `put`, and there is no lock anywhere in the path). Worse, the corruption is *mutual and ongoing*: a `get()` in container A rewrites the file from A's memory (`state.py:607` calls `_maybe_save()` on a read), so the file flips between 21 and 30 records depending on which container last read or wrote — and each flip deletes the other container's newest record. And in the other interleaving, two genuinely concurrent writers **crash**: both compute the same tmp path (`state.py:843`), one's `os.replace` renames the other's tmp file away, and the loser dies with `FileNotFoundError` at `state.py:845` after 12 of 40 writes. So Day 28's plate said "two writers lose records silently" and the honest correction is that the shipped code does **both**: it loses records silently in the read-modify-write order, and it crashes in the truly concurrent order. Day 29 records the correction and builds the smallest thing that makes the precondition checkable rather than assumed: a **single-writer guard** that takes an exclusive lock on the state path at boot and refuses to start if another process holds it — because `WORKERS=1` is a hope and a lock is a check. Second principle: **a health check is a function of the dependencies it chooses to touch, and here both obvious choices are wrong.** The cheap probe — today's `/health` (`server.py:77–92`) — touches nothing: the container answers `200` in **1.87 s** at **35.6 MiB**, which is fast, cheap, and a lie, because the same process answers `POST /chat` with `200 {"error": "missing API key(s) for providers: openai…"}` and `ok: false` sits in the body where no orchestrator looks (`server.py:79`, `:97`, `:187`). The honest probe must load the store, and the store costs **4.94 s and 705 MB** to load (`data/store.json`, 11,061 chunks, dim 768) — measured inside the image at 7.06 s with a 1 GB limit, 12.67 s at 512 MB, 19.94 s at 384 MB, and **SIGKILL (exit 137) at 320 MB and 256 MB**. So a readiness probe that tells the truth and a 256 MB memory limit is a container that is killed by its own health check and restarted forever, and a probe that stays cheap is a container that reports ready while unable to answer. The answer is the split every platform has and this repository does not: **liveness** (process up, touches nothing, must never depend on anything external) and **readiness** (can *this* instance serve *this* class of request — store loadable, database URL present or the stub acknowledged, ledger writable-or-declared), each with a status code, and the day measures and prints what each one costs. Third principle, and the one that produces the day's only genuinely urgent finding: **a secret is a file, and a build context will ship that file without being asked.** `COPY . .` with no `.dockerignore` produced, in this repository, a **1.05 GB image containing `/app/.env` at 1,026 bytes — the real file, with all four live credentials** — plus `.git`, a 34 MB `.venv` built for a different Python, and 94 `__pycache__` directories. Adding `RUN rm -f /app/.env` in the *next* layer does not fix it: `docker run` shows the file gone, and `docker save` shows layer `0330bff71c63` still holding `app/.env` at 1,026 bytes, with the layer above containing exactly two entries, one of which is the whiteout `app/.wh..env`. A whiteout hides a file from the merged view; it does not remove a byte from the image. A twenty-line `.dockerignore` takes the same build from **1.05 GB to 587 MB** and puts the secrets outside the image — which is the whole day in one measurement: *the difference between a deployed AI OS and a deployed set of credentials is one file, and it is not in the repository.*

## Duties Outline

### 1. Learn: The Loaded Objective — "Deploy a Working Version" (45 min)

- [ ] Parse the objective as a claim about **replacement, not operation**, because "deploy a working version" contains a hidden word: *version*. A version is the thing that gets replaced; a working process is what gets replaced *with*. So the question is not "does it run" — it demonstrably runs, twenty-nine days of fixtures prove it — but **what does this system still know after the process that learned it is gone, and what does it forget silently.** The useful reformulation, and the day's working definition: **for every piece of state the system holds, name where it lives, whether it survives a restart, and whether a second instance may touch it** — and if any of those three cannot be answered from the code, that is a finding, not a blank.
- [ ] Take the delivery honestly, because the curriculum offers two and they are not the same work: *"an accessible deployed AI OS **or** a production-like local deployment."* The day takes the second and says why out loud: this environment has a Docker daemon and no cloud account, so the honest deliverable is a **real image, a real container, a real published port, and a real probe** — which is the same artifact AWS would run, minus the twelve services around it. The curriculum's own escape hatch ("implemented where practical") is what makes this legitimate rather than a dodge, and the day's discipline is that **the AWS mapping is not optional filler**: §7 maps every one of today's findings to a named service and states what that service does *not* fix, so the architectural depth the curriculum asks for is delivered as a table with owners rather than as a wish.
- [ ] Inventory the **deployment surface as it exists**, item by item, because the honest statuses are what make the day: `containerization` — **absent**: no `Dockerfile`, no compose file, no image, and (measured) the naive `COPY . .` build **leaks the live `.env`**. `environment variables` — **present and the best-configured thing in the repository**: 64 names read through one pattern (`os.getenv` / `_env_int` / `_env_float`, never a constant buried in a module), 26 documented in `.env.example`. `secrets` — **a file read at import** (`config.py:23–37` via `:76`, called from `server.py:35`), correctly git-ignored (`.gitignore:1`) and correctly warned about in the template (`.env.example:1`, *"Never commit a real key"*) — **and shipped into the image anyway**, because git and Docker have different definitions of the build context. `application deployment` — **absent**: no process manager, no service unit, no reverse proxy, no TLS. `database` — **two backends behind one silent seam** (`data.py:798–806`: Postgres when `SALEOR_READONLY_DB_URL` is set, otherwise `sqlite3.connect(":memory:")` seeded with `SEED_SQL` at `data.py:455–458`, with no warning at the substitution). `observability` — **present and honest about itself**: `/metrics` returns a Prometheus rendering *and* a note saying it is "a local development surface, not a production metrics stack" (`server.py:249–255`), `/logs` returns a hint when `structured_logging.setup()` was never called (`server.py:258–266`), and `POST /ingest/span` is **404 by default** with a refusal that names the reason ("unauthenticated ingest is a Day-26 boundary", `server.py:270–288`). That is a *good* day-24 result and it is also three surfaces a container must decide about. `health checks` — **present, and structurally unable to fail**: `server.py:77–92` returns a dict, so FastAPI answers `200` in both branches, and the unconfigured branch is the one an orchestrator must act on.
- [ ] Answer the hard question first, before any file is written: **what is the deliverable, and what makes it worth a day?** Three candidates. (a) *Put it on AWS.* Verdict: **rejected** — no account, no credentials, and a day that produces twelve cloud resources it cannot run is the same unfalsifiable artifact Day 28 refused to draw. (b) *Write a Dockerfile.* Verdict: **necessary and insufficient** — a Dockerfile is a claim, and the day begins by falsifying the most obvious one in this repository. (c) **Make the deployment falsifiable**: an image whose file list is asserted, a probe whose status codes are asserted, a two-writer precondition that is *refused* rather than assumed, a secret that is proven absent from the image, and a manifest that names every item the deployment does not have. Verdict: **chosen** — and it is the only one of the three that survives contact with the next contributor, which is the test every deliverable in this series has been held to since Day 7.
- [ ] Pre-commit the day's split before any build. **`MECH`:** the image file list; the `.dockerignore` rule set; the absence of the secret from the image; the liveness/readiness status codes and their bodies; the single-writer refusal; the census (64/26/39 → 66/33/35); the `0.0.0.0` bind contract; the environment/image parity; and the on/off equivalence. **Not `MECH`:** whether 587 MB is an acceptable image size; whether 4.94 s is an acceptable cold start; whether 705 MB is the right memory request; whether ECS is the right compute primitive; whether one replica is the right number; whether S3 is the right home for a 262 MB store; and every claim about what a *managed* platform does with a probe it considers failing — all of which are sizing and policy, and which the day will not claim.
- [ ] Pre-commit nine invariants: **(a) the image is a manifest, not a folder** — every path in it is enumerated, and a file that exists in the repository but is absent from the image is `PENDING` with an owner, not an oversight; **(b) a secret is never in the image** — asserted against the built image, not against the Dockerfile's good intentions; **(c) a health check either fails or is not one** — status codes are the contract, and `ok: false` in a `200` body is the specific anti-pattern the day deletes; **(d) liveness touches nothing external** — a probe that can be killed by a dependency is a probe that restarts a healthy process; **(e) readiness is per-class** — "can serve a RAG question" is a different claim from "can serve a chat message", and a single boolean over both is a boolean over neither; **(f) one writer is enforced, not documented** — a `WORKERS=1` comment is a hope, an exclusive lock at boot is a check; **(g) the container is the same system** — a fixture runs on the host and in the container and requires identical verdicts, because the most expensive deployment bug is a difference nobody is looking for; **(h) "not deployed" is an answer** — every deferred item carries a trigger and an owner; **(i) the refusal is the deliverable** — N4 asserts the *defect exists* and the *guard refuses it*, which is the first time in the series a control tests a safety property rather than a behaviour.
- [ ] Name the negatives with owners, carried from Day 28 and closed today: **the second process** is now *built and bounded* — one replica, one lock, and the lock's refusal is a refusal, not a migration; **identity, transport, and TLS** are *mapped, not built* (ACM + ALB in §7), and the limiter's attachment stays `PENDING` behind them because the key it counts is a header; **the external anchor for the audit chain** is mapped to a KMS + append-only store and stays `PENDING`; **the connection pool and the read replica** stay `PENDING` behind the trigger "two processes", which today's single-writer lock *delays* rather than removes; **the trace sink and its retention** stay `PENDING` because the sink does not exist; **ANN / a real vector store** stay `PENDING` at "corpus × 10"; and **object storage** stays `PENDING` at "corpus refresh slower than the deploy" — a trigger that a 262 MB store inside a 587 MB image makes *more* likely, not less, and the day says so instead of pretending the image solved it.

### 2. Learn: What an Image Is, and What a Container Is Not (45 min)

- [ ] Learn the **three things an image is**, because the word is used for three different things and only the third one matters today. (1) *A file list* — the union of the layers, which is what `docker run` shows. (2) *A set of layers*, each an immutable diff, which is what `docker save`, `docker push`, and a registry store. (3) *A configuration* — the `ENTRYPOINT`/`CMD`/`ENV`/`EXPOSE`/`USER` metadata, which is a **separate JSON document from the layers** and is exactly as much a part of the image. The mistake everyone makes once is treating (1) as the image: you delete a file, the container no longer has it, and the image still has it, because deleting creates a whiteout rather than editing the layer. Today's measurement is the proof and it is the day's centerpiece: `RUN rm -f /app/.env` produced a container with no `.env`, and an image with 1,026 bytes of `.env` still in layer `0330bff71c63` and a two-entry whiteout layer above it.
- [ ] Learn **why the repository is an unusually good place to learn this**, because its build context is 578 MB and *nothing in it is needed at runtime except four things*: `data/` 432 MB, `corpus_code/` 98 MB, `.venv/` 34 MB, `.git/` 5.7 MB, then `docs/` 2.7 MB, `corpus/` 2.5 MB, `ai_os/` 2.0 MB, `tools/` 1.5 MB. The runtime needs `ai_os/`, `policy.yaml`, `.env.example` (as the contract, not as the source of values), `requirements.txt`, and `data/store.json` (262,182,307 B) for the docs corpus. It does **not** need the corpora (they are ingest-time inputs), the venv (the image installs its own), the git history, the docs, the tests, or the `__pycache__` of a different interpreter. That is a 20-line `.dockerignore` and a 463 MB saving, and the day states the general rule it illustrates: **an image is a subset of a repository, and the interesting work is deciding which subset — a decision that is easy to get wrong silently, because the wrong answer is a working container.**
- [ ] Learn **what a container is not**, in this repository's own terms, because the temptation on a deployment day is to call the container a *deployment*. A container is a **process with a filesystem and a namespace**, and this application is a process whose entire state story is *in that process* — the gateway's `last_provider`/`last_latency_ms`/`last_attempts` are module-level fields on a shared global (`gateway.py:80–82`, read after the call at `server.py:125–126`), the ledger is a list in that process (`ledger.py:65`), the trace store is an `OrderedDict` in that process capped at 256 (`observability.py:706–716`, the cap at `:714`). So "containerized" here means **the same single-process application, with a filesystem, under a restart policy** — and the honest sentence is that a container does not make this system distributed, it makes the *absence* of a process boundary visible for the first time. What a container genuinely buys, and what the day will claim: a reproducible file list, a declared dependency set (`pip freeze` inside the image is 18 packages and includes `psycopg` 3.3.6, so the Postgres path is *reachable* even offline), an isolated environment variable set, a memory ceiling that can be *declared and violated measurably*, and a process that can be killed and restarted. What it does not buy: durability, identity, a second reader, or a health signal.
- [ ] Learn the **`0.0.0.0` fact**, because it is the single most common container failure and this repository's own documented command causes it. `uvicorn ai_os.server:app` (`server.py:3–4`) binds `127.0.0.1` by default. Measured: `ss -ltnp` shows `LISTEN 127.0.0.1:8111`, a loopback request answers `200`, and the same port on the host's routable address `192.168.1.46:8112` refuses the connection. Inside a container that is fatal in a specific way: `docker run -p 8000:8000` publishes the *container's* `eth0`, and a server listening on the container's loopback is unreachable from the host no matter what the port mapping says. The day therefore treats the bind address as a **contract with three copies** — the Dockerfile's `CMD`, the README's run command, and the fixture that asserts both name `--host 0.0.0.0` — because a contract documented in one place is a comment.

### 3. Learn: Secrets Are a File the Build Context Will Ship (45 min)

- [ ] Learn **the two doors into a repository**, because this repository has closed one and never knew the second existed. Git's door: `.gitignore:1` lists `.env`, and `git ls-files` confirms the real file is untracked while `.env.example` is tracked. Docker's door: the build context is the **directory**, and nothing in a directory is secret by default. Both are correct and they are not the same rule, and the consequence is that **the honest statement about this repository's secrets is not "our keys are safe" but "our keys are safe from git and one `docker build` away from being in a layer."** The `.env` on disk holds 13 names, three of them credentials (`OPENAI_API_KEY` 73 chars, `CLOUDFLARE_API_KEY` 53, `CLOUDFLARE_ACCOUNT_ID` 32) plus the 28-char base URL, and the day's measurement copies all 1,026 bytes of it into an image without any human decision.
- [ ] Learn **why "delete it in a later layer" is not remediation**, from the mechanism rather than from a rule. A layer is a diff; `rm` in a later layer writes a *whiteout* entry (`.wh.<name>`) that tells the union filesystem "pretend this is not here." The bytes of the earlier layer are still in the image's content-addressed store, and they are still in `docker save`, and they are still in whatever registry the image was pushed to. Measured: `docker save` of the `RUN rm` image produced 9 layers; the 8th contains `app/.env` at 1,026 bytes with mode `0o664`; the 9th contains two entries, one of which is `app/.wh..env`. The general rule the day takes away: **the only way to keep a secret out of an image is to never let the build context contain it**, which is exactly what `.dockerignore` is, and it is also why `ARG`/`ENV` is the wrong channel (below).
- [ ] Learn **why `ARG`/`ENV` is the wrong channel for a key, measured rather than asserted**, because this is the reflex fix and it is wrong. Passing `--build-arg OPENAI_API_KEY=…` and `ENV OPENAI_API_KEY=$OPENAI_API_KEY` produces two warnings from Docker's own linter — `SecretsUsedInArgOrEnv: Do not use ARG or ENV instructions for sensitive data (ARG "OPENAI_API_KEY") (line 2)` and the same for `ENV` (line 3) — and the value is then readable from `docker inspect` (the image config's `Env` array, which is document (3) above) *and* from `docker history --no-trunc`. So the key is not in a layer but in the image's **configuration**, which is the part that gets pushed, described, and printed by every platform's "show me this deployment" screen. The correct channels are the ones that keep the value out of the artifact: inject at **run** time (`docker run -e`, or `--env-file` pointing at a file that is itself not in the context), and in a managed platform, a secrets manager the platform reads at start. The rule the day writes down: **a secret belongs to the process's environment, not to the artifact that starts the process.**
- [ ] Learn **the seam this repository actually needs**, and notice that it is one line of code away from already being right. `config.py:23–37` reads `.env` from the working directory at import; `config.py:76` calls it inside `build_gateway_from_env`; `server.py:35` calls that at module load. So the process *works* with no environment at all — which is excellent for a laptop and **actively dangerous in a container**, because a container whose image contains `.env` needs no secrets injected and therefore will happily start with yesterday's keys in production. `llm_client.py:22–45` has a second, independent loader with its own `LLM_BASE_URL`/`LLM_MODEL`/`API_KEY` chain, so a container that fixes the first loader can still be configured by the second. Therefore the day's secret contract has **three** parts: (1) `.dockerignore` names `.env` and the image is asserted not to contain it; (2) the run command injects the environment and the process is *allowed* to fall back to a file only when one is explicitly mounted, never from the image; (3) a fixture asserts the number of *secret-shaped* names in the image is zero, so a future `.env.production` or `.netrc` or `*.pem` is caught by the same rule rather than by luck.

### 4. Learn: Health Checks Are Claims About Dependencies, and Both Obvious Ones Are Wrong Here (45 min)

- [ ] Learn **what a health check is for**, which is not "is the process running" — that is what a supervisor is for. A health check is the input to a *routing decision*: an instance that cannot serve should not receive traffic, and an instance that is fine should not be restarted. That makes it a claim about **dependencies**, and the claim has to be *per class of request*, because this application serves at least four that fail independently: a chat message (needs a gateway, i.e. a key and a provider), a RAG question (needs a gateway *and* a 262 MB store), a data question (needs a database URL, or it silently answers from `SEED_SQL` — `data.py:798–806`), and an observability query (needs the trace store, which is in this process and gone on restart). One boolean over all four is a boolean over none.
- [ ] Learn **the current probe's specific defect**, because it is a better lesson than a generic "add status codes": `server.py:77–92` returns a `dict`, so FastAPI sends `200` in *both* branches, and the unconfigured branch puts `ok: false` in the body. Every orchestrator in the world — Docker's `HEALTHCHECK`, Kubernetes' readiness probe, an ALB target group, a uptime monitor — keys on the status code. Measured in the built image: `/health` → `200 {"ok":false,"error":"missing API key(s) for providers: openai — set OPENAI_API_KEY in .env"}`, `POST /chat` → `200 {"error":"missing API key(s) for providers: openai…"}`, `GET /ledger` → `200 {"error":…}`, `POST /rag` → `200 {"error":…}`. So a process that cannot answer a single question is *maximally healthy* by the only signal a platform reads. The only route in the application that can return a non-200 on purpose is `POST /ingest/span`, which returns `404` when `TRACE_INGEST` is off (`server.py:282–288`) — which is the correct behaviour, and the day's control is that it stays correct.
- [ ] Learn **the two probes and what each costs, measured**, because the trade is not "cheap vs correct" but "cheap and lying vs correct and expensive", and the numbers decide which one you can afford. | probe | touches | measured cost | what it misses | **liveness** | nothing external | `200` in **1.87 s** at **35.6 MiB** RSS | a wedged event loop, a dead provider chain, an unopenable state file | **readiness** | gateway buildable, store loadable, database mode named, state writable-or-declared | store load is **4.94 s** and **705 MB** peak RSS; the whole check must be cached or it is paid per probe | nothing, at the price of the memory floor | The asymmetry is the lesson: **liveness is cheap because it is allowed to be shallow, and readiness is expensive because it is not.** A deployment that collapses the two (today's state) is paying the liveness price and calling it the readiness claim.
- [ ] Learn **the memory floor, and why it is a deployment decision rather than a code decision.** Measured in the image, loading `data/store.json`: unlimited **4.94 s**; `--memory=1g` **7.06 s**; `--memory=512m` **12.67 s**; `--memory=384m` **19.94 s** (survives, thrashing — 4× slower); `--memory=320m` and `--memory=256m` **exit 137, SIGKILL**. Two consequences, and the day takes both. (1) *Time-to-load degrades non-linearly as the limit approaches the floor* — a container that is merely slow at 384 MB looks like a slow application, not like a memory-starved one, which is the most common way this is misdiagnosed. (2) *A readiness probe that loads the store, under a 256 MB limit, is a crash loop caused by the health check* — the probe kills the container, the restart policy restarts it, the probe kills it again, and the observable symptom is a flapping service whose logs show nothing wrong. So the day writes the floor into the deployment as a **declared precondition with a measured value and a refusal**: the manifest states `memory_limit: 1g` with the reason (705 MB measured peak for the store, plus interpreter, plus headroom), and the fixture refuses a limit below the measured floor.
- [ ] Learn **what a health check must never do**, in this repository, with the same seriousness as Day 27's list of what an approval must not be. It must not **call a model** (a probe that spends a token per poll is a probe that costs money and can be rate-limited into failing). It must not **write state** — a probe that calls `get()` on the state store *rewrites the file* (`state.py:607`), so a readiness probe on a shared volume is a writer, and a read-only probe must construct its store with `autosave=False`. It must not **hold the single-writer lock** (a liveness probe that takes the lock would make the process unprobeable while the probe runs). And it must not **depend on a network call it does not control** — the provider chain is reported as *configuration*, not as a round trip, which is what today's `/health` already gets right at `server.py:83–86` and should keep.

### 5. Design: The Manifest, the Split, and the Refusal Register (30 min)

- [ ] Design the record before touching the deployment, because the manifest *is* the deployment's contract:
    ```yaml
    # docs/deployment.yaml — Day 29's addition. An image is a subset of a
    #   repository, and the interesting part is the subset.
    #   * `why` is required per entry: a file nobody can justify is a file that
    #     should not ship (measured: 578 MB context -> 587 MB image).
    #   * `absent` is a first-class section. A deployment doc that lists only
    #     what exists is a brochure.
    image:
      base: python:3.12-slim
      runtime_user: ai-os            # never root; the store is 0644 and read-only
      exposes: [8000]
      healthcheck:                   # the *contract*, mirrored by ai_os/health.py
        liveness:  { path: /healthz,  touches: [],              timeout_s: 2 }
        readiness: { path: /readyz,   touches: [gateway, store, database, state],
                     timeout_s: 30 }
    include:
      - path: ai_os/            why: the application
      - path: tools/            why: the offline fixtures the N-set runs inside the image
      - path: policy.yaml       why: Day 15's SQL policy the data layer enforces
      - path: .env.example      why: the configuration *contract*; never a value source
      - path: requirements.txt  why: four dependencies, resolved at build
      - path: data/store.json   why: 262,182,307 B · 11,061 chunks · dim 768
    absent:
      - path: .env               why: secrets come from the run environment  (BUILT, ASSERTED)
      - path: .git/              why: history is not a runtime dependency
      - path: .venv/             why: the image installs its own; this one is py3.14
      - path: corpus/            why: ingest-time input; `data/store.json` is the artifact
      - path: corpus_code/       why: ditto — 98 MB of source the image does not serve
      - path: **/__pycache__/    why: another interpreter's bytecode
      - path: docs/              why: 2.7 MB of prose; the deployment doc is in git
    limits:
      memory: 1g                  # measured floor 384m (survives), SIGKILL at 320m
      workers: 1                  # one process; the single-writer lock enforces it
    ```
  - [ ] Design decision #1 — **the manifest is a file, and the image is checked against it**, because Day 28's ratchet was "every box in the diagram is a file" and today's is the same idea one level up: the deliverable ships with a fixture that parses `docs/deployment.yaml`, resolves every `include` path against the filesystem, and asserts **both directions** — every listed path exists, and every path in the build context that is not listed appears in `absent` with a reason. A manifest with a phantom entry and a manifest missing an entry are the same defect from opposite ends, and the second one is the one that ships the secret.
- [ ] Design decision #2 — **the two probes are two functions in one module**, `ai_os/health.py`, in the same register as `permissions.py` and `approval.py`: decisions, not infrastructure. `liveness()` returns `(200, {"ok": True, "checks": {}})` and touches nothing — it cannot fail on a dependency, which is the property that makes it safe to restart on. `readiness()` returns `(200 | 503, {"checks": {...}, "ok": bool})` where each check is a **named tuple of `(name, ok, detail, cost_ms)`**, so the body is a table rather than a boolean, and `503` is returned the moment any check fails. Four checks, in the order they matter: `gateway` (was `build_gateway_from_env()` constructible — a *local* fact, no network), `store` (is the store file present and loadable — cached after first success, and the cache is what makes the probe affordable), `database` (`postgres` or `stub (SEED_SQL)`, named explicitly, because the silent substitution at `data.py:798–806` is the one thing in this repository that produces a *confidently wrong* answer), and `state` (writable, or explicitly disabled). Rejected: a `readyz` that pings the provider (costs money, can be rate-limited, and a provider outage is not a reason to remove an instance from a pool that has a cache), and a probe framework.
- [ ] Design decision #3 — **the readiness store check is cached, and the cache is what the day argues for**, because it resolves the tension in §4 without lying: the *first* readiness call pays 4.94 s and 705 MB and then the process holds the store, so every later probe is a dictionary lookup. This is Day 28's identity-keyed cache idea arriving at its first real use — and the day states the cost honestly: the readiness probe converts a per-request 4.94 s parse (`server.py:192–197`, called at `:217`) into a once-per-process cost, and the memory becomes *resident* rather than *transient*, which is why `memory: 1g` is in the manifest and not `512m`. Day 28 said the cache was a correctness decision; Day 29 says it is also the difference between a probe that can be polled every 10 s and one that cannot.
- [ ] Design decision #4 — **the single-writer guard is an exclusive lock taken at boot, refusing the second process by name**, and it is the day's one new mechanism. `SingleWriter(path)` opens `<state>.lock`, takes `fcntl.flock(LOCK_EX | LOCK_NB)`, and on failure raises `SecondWriter(pid=…, path=…)` — a refusal that names the holder. Wired into `readiness()`'s `state` check and into the process's start-up, so `uvicorn --workers 2` or a second replica on a shared volume **fails at boot with a sentence** instead of corrupting a file over the next hour. The honest limits, stated in the same breath: `flock` is **advisory** (every writer must take it — the state store is the only writer today, and the day is the only thing that can make that true), and it is **filesystem-dependent** (it works on a local volume and a bind mount; NFS semantics vary and the day will not claim otherwise). What it buys is enormous and specific: the day converts Day 28's "two writers lose records silently" from a *drawing* into a *refusal*, which means the container can honestly be scaled to exactly one.
- [ ] Design decision #5 — **the run environment is the secret channel and the image is not**, written as a command a reader can paste: `docker run --rm -p 8000:8000 --memory=1g --env-file /secure/ai-os.env d29:honest` with the `CMD` already carrying `--host 0.0.0.0 --port 8000`. Three deliberate omissions: no `-v` for the store (it is in the image; a volume mount for `data/` exists for the *corpus refresh* trigger and is named as such), no `--restart` in the documented command (a restart policy hides the crash loop that §4's memory floor predicts, and the day wants it visible), and no `--name`-based discovery. And one addition: `--read-only` is **not** claimed, because the process writes `data/` state and the ledger's companions; the day records the paths that would need to be tmpfs instead of pretending.
- [ ] Design decision #6 — **AWS is mapped per finding, with what each service does not fix**, because the curriculum asks for architectural depth first and a table with a "does not fix" column is the only form of depth that cannot become a wish. Seven rows, in the order the findings appear: *ECR* ← the image, and it does not fix a secret already in a layer. *ECS/Fargate* ← the process and its memory limit, and it does not fix a readiness probe that lies, nor a second replica on a shared file. *Secrets Manager / SSM Parameter Store* ← the key at run time, and it does not fix a key that is in the image. *RDS Postgres* ← `SALEOR_READONLY_DB_URL` and the `saleor_read_only` role the platform already provisions, and it does not fix the two-writer problem for `state.json` (that is a different store). *S3* ← the corpus and both store files, and it does not fix the fact that a corpus change is a rebuild today. *ALB* ← the health check that can actually fail plus TLS termination, and it does not fix identity. *CloudWatch* ← the shape `/metrics` and `/logs` already have, and it does not fix retention, sampling, or a sink that does not exist. Every row carries the local mechanism that stands in for it today, so the day ships a working deployment *and* the map.
